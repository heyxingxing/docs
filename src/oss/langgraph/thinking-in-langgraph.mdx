从普通应用开发切换到 LangGraph 时，最重要的变化不是学习新的 API，而是改变你对程序结构的理解。传统程序通常围绕函数调用和控制流来组织；LangGraph 更适合把智能体系统拆成：**State、Node、Transition，以及失败后如何恢复**。

本指南通过一个邮件支持智能体，展示如何把一个真实问题逐步转换成 LangGraph。

## 从业务流程开始，而不是从 Graph API 开始

假设我们要实现一个客户支持智能体：

1. 接收客户邮件。
2. 对邮件进行分类。
3. 如果问题与产品使用有关，搜索知识库。
4. 如果是 Bug，查询 Bug Tracking System。
5. 草拟回复。
6. 高风险情况交给人工审核。
7. 最后发送邮件。

先不要急着写 `StateGraph`。第一步应把业务流程画成一个**决策流程**：哪些步骤是确定性的，哪些步骤由模型判断；哪些步骤可能失败，哪些步骤必须可重试；哪里需要人工参与。

这正是 LangGraph 的核心抽象：

```text
输入
 ↓
分类
 ├─ 一般问题 ───────┐
 ├─ 文档问题 → 搜索知识库 ─┤
 └─ Bug → 查询 Bug Tracker ─┤
                           ↓
                        草拟回复
                           ↓
                      是否人工审核？
                       /          \
                     是            否
                     ↓             ↓
                   人工审核       发送回复
                     ↓
                   发送回复
```

## 第 1 步：识别 State

State 应保存**后续步骤真正需要知道的事实**，而不是把整个应用的所有局部变量都塞进去。

对于邮件 Agent，可以包括：

- 原始邮件内容；
- 分类结果；
- 检索到的文档；
- Bug 信息；
- 草稿回复；
- 是否需要人工审核；
- 最终回复。

### State 不是数据库

State 更像是**一次 Agent Execution 的工作记忆与控制平面**。用户长期偏好、跨 Thread 知识等信息通常更适合放入 [Store](/oss/langgraph/stores)，外部业务系统中的权威数据则应继续保存在数据库或 API 中。

一个实用判断：

- “下一 Node 需要它来决定怎么执行吗？” → 放 State。
- “不同会话都要长期记住吗？” → 放 Store。
- “它是业务系统权威记录吗？” → 留在数据库 / 外部系统。

## 第 2 步：识别 Runtime Context

有些东西 Node 需要使用，但不属于 Graph State，例如：

- 当前用户 ID；
- 数据库连接；
- API Client；
- Model / Provider 配置；
- 租户信息。

这类信息应该通过 Runtime Context 注入，而不是持久化到 State。


## 第 3 步：把业务阶段定义为 Node

一个好的 Node 通常对应一个**有明确输入、输出和失败边界的业务动作**。

不要机械地把每一行代码变成 Node，也不要把整个系统塞进一个巨型 Node。

可以问三个问题：

1. 这个步骤是否需要独立观察 / Trace？
2. 这个步骤失败后，是否希望单独 Retry 或 Resume？
3. 这个步骤是否是一个有意义的业务阶段？

如果答案大多是“是”，它通常值得成为独立 Node。

## 第 4 步：把决策建模为 Transition

LangGraph 中，Node 负责“做什么”，Edge / Conditional Edge 负责“接下来去哪”。

典型决策包括：

- 分类后进入哪条处理路径；
- 是否需要人工审核；
- Tool 结果是否足够；
- 是否需要 Retry / Rewrite / Escalate。

如果 Routing 本身不更新 State，优先使用 Conditional Edge；如果需要在同一步同时更新 State 和跳转，可以使用 [`Command`](/oss/langgraph/graph-api#command)。

## 第 5 步：显式设计错误策略

真实 Agent 最大的问题往往不是 Happy Path，而是失败。

不要把所有异常都统一处理。先按失败类型分类：

| 失败类型 | 示例 | 推荐策略 |
| --- | --- | --- |
| 瞬时错误 | API 429、网络抖动 | Retry Policy |
| LLM 可恢复错误 | 输出格式错误、信息不足 | 写入 State，重新进入 Agent Loop |
| 业务条件 | 权限不足、操作不可执行 | 显式分支到替代流程 |
| 需要人工判断 | 高风险退款、模糊 Bug | `interrupt()` |
| 编程错误 | `TypeError`、逻辑 Bug | 让异常暴露，修代码后 Resume |

这比 `try/except Exception: ...` 更可靠。LangGraph 的 Checkpoint 允许你在修复问题后，从失败位置附近继续，而不是重新执行整个长任务。

发送邮件、扣款、写数据库、创建工单等都是副作用。因为 Node 可能在 Resume / Retry 时重新执行，所以副作用必须：

- 尽量放在明确的 Node / Task 中；
- 使用 Idempotency Key；
- 或确保操作天然幂等；
- 在高影响副作用前先完成 Interrupt / Approval。

生产级 Agent 应把可观测性当作系统设计的一部分，而不是上线后的补丁。至少应该能够回答：

- 当前 Run 在哪个 Node？

- 模型看到了什么 Context？
- 调用了哪些 Tool？
- 哪个步骤失败 / Retry 了？
- State 在每个 Step 如何变化？
- 人工审核为什么被触发？

[LangSmith](/langsmith/observability) 可以 Trace 整个 Graph Execution。

## 如何判断 Node 粒度

Node 太细：

```text
parse_email
↓
extract_subject
↓
extract_sender
↓
normalize_text
↓
...
```

这种设计会产生大量没有独立业务意义的 Runtime Boundary。

Node 太粗：

```text
handle_entire_email
```

这种设计又失去了独立 Retry、Checkpoint、Trace 和 Routing 的能力。

更合理的划分通常是：

```text
classify_intent
search_knowledge_base
lookup_bug
compose_response
human_review
send_reply
```

即：**一个 Node 对应一个值得独立观察、恢复或路由的业务阶段。**

## Node 与 Task 的选择

如果一个业务阶段内部包含多个操作，但你不希望把它们暴露成 Graph Topology，可以在 Node 内使用 [Task](/oss/langgraph/functional-api#task)。

例如：

```text
Node: prepare_response
├── Task: fetch_customer_profile
├── Task: fetch_order_history
└── Task: call_model
```

这样 Graph 仍然简洁，而长时间 / 非确定性操作又可以被单独 Checkpoint。

## 确定性与 Agentic 的混合

LangGraph 的价值并不是把每个步骤都交给 LLM。更好的设计通常混合：

- **确定性步骤**：权限检查、Schema Validation、状态转换、数据库读取；
- **Agentic 步骤**：分类、规划、信息综合、Tool Selection；
- **人工步骤**：高风险决策、责任确认、模糊案例。

例如：

```text
确定性权限检查
      ↓
LLM 判断意图
      ↓
确定性路由
      ↓
LLM + Tools 搜索信息
      ↓
确定性 Policy Check
      ↓
必要时人工审批
      ↓
确定性执行副作用
```

这种结构通常比“一个万能 Agent 自己决定一切”更可控、更容易测试。

## 设计 State 的原则

### 保存事实，不保存可以重新计算的派生数据

如果某个字段很容易从其他 State Key 计算出来，通常没必要持久化。State 越简单，迁移和调试越容易。

### 为并行更新设计 Reducer

如果多个 Node 可以在同一 Super-step 更新同一个 State Key，必须明确 Reducer 语义：追加、Merge、Last-write-wins，还是显式覆盖。

### State 应支持向后兼容

生产系统中的 Thread 可能持续数小时、数天甚至更久。发布新版本时，旧 Checkpoint 仍会被新代码加载。新字段尽量设计为 Optional / 有 Default；删除或重命名字段需要考虑[向后兼容](/oss/langgraph/backward-compatibility)。

## 设计恢复路径

每一个长程任务都应该能回答：

> “如果这里进程挂了，下次从哪里继续？”

Checkpoint Boundary 默认位于 Super-step 之间。对于 Node 内部昂贵操作，可以拆成 Task，以获得更细粒度的恢复。

需要关注：

- Node 是否幂等；
- Tool / API 副作用能否安全重试；
- Interrupt 前后代码会不会重复执行；
- 是否需要独立 Subgraph Checkpointer；
- State 是否足以支持 Resume。

## 一个实用的设计清单

在真正实现 LangGraph Agent 前，可以逐项确认：

1. **业务目标**：Agent 最终要完成什么？
2. **State**：哪些信息必须跨 Step 保存？
3. **Node**：哪些阶段值得独立 Trace / Retry / Resume？
4. **Edge**：哪些跳转是固定的，哪些依赖 Runtime State？
5. **LLM**：哪些决策真正需要模型？
6. **Tool**：哪些能力需要访问外部世界？
7. **副作用**：哪些操作不可逆，如何做到幂等？
8. **Retry**：哪些 Error 是瞬时错误？
9. **Interrupt**：哪里应该由人确认？
10. **Memory**：哪些是 Thread 内短期 State，哪些需要跨 Thread Store？
11. **Observability**：如何知道系统为什么做出某个动作？
12. **Backward Compatibility**：已有 Thread 如何在新版本代码下继续？
