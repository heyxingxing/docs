智能体的“记忆”通常包含两个不同问题：

- **短期记忆（Short-term memory）**：同一个对话 / Thread 内保存当前上下文，例如消息历史、计划和中间状态。
- **长期记忆（Long-term memory）**：跨 Thread 保存用户偏好、长期事实、知识和经验。

LangGraph 分别用两个 Runtime Primitive 解决它们：

```text
同一 Thread 内
    ↓
Checkpointer
    ↓
短期 Graph State

跨 Thread
    ↓
Store
    ↓
长期 Memory
```

这两个机制可以同时使用，但不要混为一谈。

<a id="add-short-term-memory"></a>
## 添加短期记忆

短期记忆本质上就是**持久化 Graph State**。使用 Checkpointer 编译 Graph 后，LangGraph 会在每个 Super-step 保存 Checkpoint；后续使用相同 `thread_id` 调用时，会在原 State 基础上继续执行。

:::python
```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import MessagesState, StateGraph, START, END

checkpointer = InMemorySaver()


def call_model(state: MessagesState):
    response = model.invoke(state["messages"])
    return {"messages": [response]}

builder = StateGraph(MessagesState)
builder.add_node("call_model", call_model)
builder.add_edge(START, "call_model")
builder.add_edge("call_model", END)

graph = builder.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "1"}}

graph.invoke(
    {"messages": [{"role": "user", "content": "Hi! I'm Bob."}]},
    config,
)

graph.invoke(
    {"messages": [{"role": "user", "content": "What's my name?"}]},
    config,
)
```
:::

:::js
```typescript
import {
  StateGraph,
  StateSchema,
  MessagesValue,
  START,
  END,
  MemorySaver,
} from "@langchain/langgraph";

const State = new StateSchema({ messages: MessagesValue });
const checkpointer = new MemorySaver();

const graph = new StateGraph(State)
  .addNode("callModel", async (state) => ({
    messages: [await model.invoke(state.messages)],
  }))
  .addEdge(START, "callModel")
  .addEdge("callModel", END)
  .compile({ checkpointer });

const config = { configurable: { thread_id: "1" } };

await graph.invoke(
  { messages: [{ role: "user", content: "Hi! I'm Bob." }] },
  config,
);

await graph.invoke(
  { messages: [{ role: "user", content: "What's my name?" }] },
  config,
);
```
:::

第二次 Invocation 使用同一个 Thread，因此模型可以看到前一轮消息。

<Info>
`InMemorySaver` 适合本地开发和测试。生产环境应使用持久化 Checkpointer，例如 PostgreSQL、MongoDB、Redis 或其他官方集成。参阅 [Checkpointer](/oss/langgraph/checkpointers)。
</Info>

## Thread 是短期记忆的边界

`thread_id` 决定哪些 Invocation 共享短期 State：

```text
thread_id = "conversation-1"
  ├─ turn 1
  ├─ turn 2
  └─ turn 3

thread_id = "conversation-2"
  ├─ turn 1
  └─ turn 2
```

不同 Thread 默认不会看到彼此的 State。如果要跨 Thread 共享信息，应使用长期 [Store](#add-long-term-memory)，而不是人为复用 Thread ID。

## 查看短期记忆

:::python
```python
snapshot = graph.get_state(config)
print(snapshot.values)

for checkpoint in graph.get_state_history(config):
    print(checkpoint.values)
```
:::

:::js
```typescript
const snapshot = await graph.getState(config);
console.log(snapshot.values);

for await (const checkpoint of graph.getStateHistory(config)) {
  console.log(checkpoint.values);
}
```
:::

可以使用 [时间旅行](/oss/langgraph/use-time-travel) Replay 或 Fork 历史 Checkpoint。

## 为什么需要管理消息历史

长期对话中，如果每一轮都把完整消息历史发送给模型，会出现几个问题：

- 超过模型 Context Window；
- Token 成本持续增长；
- 历史噪声越来越多；
- 模型对早期关键约束的注意力下降；
- 延迟增加。

因此，短期记忆不是“无限保存所有消息”，而是需要**上下文管理策略**。

常见方法：

1. 裁剪旧消息；
2. 删除不重要消息；
3. 摘要历史；
4. 把稳定事实提取到长期 Store；
5. 只在 Prompt 中注入当前任务真正需要的信息。

<a id="trim-messages"></a>
## 裁剪消息

可以在模型调用前只选取符合 Token Budget 的最近消息，而不修改 Checkpoint 中保存的完整 State。

:::python
```python
from langchain_core.messages.utils import trim_messages


def call_model(state: MessagesState):
    messages = trim_messages(
        state["messages"],
        strategy="last",
        token_counter=model,
        max_tokens=4000,
        start_on="human",
        include_system=True,
        allow_partial=False,
    )
    response = model.invoke(messages)
    return {"messages": [response]}
```
:::

这种方式的优点是：

- Checkpoint 仍保存完整对话历史；
- 每次模型调用只发送必要上下文；
- 可以随时改变 Context Policy，而不需要迁移历史数据。

<Warning>
简单“只保留最后 N 条消息”可能破坏 Tool Call / Tool Result 配对。优先使用 Message-aware 的裁剪工具，并确保生成的消息序列符合 Provider 的 Chat Protocol。
</Warning>

<a id="delete-messages"></a>
## 删除消息

如果希望真正从 Graph State 中删除旧消息，可以返回 `RemoveMessage`。

:::python
```python
from langchain.messages import RemoveMessage


def delete_old_messages(state: MessagesState):
    messages = state["messages"]
    if len(messages) <= 6:
        return {}

    return {
        "messages": [
            RemoveMessage(id=m.id)
            for m in messages[:-6]
        ]
    }
```
:::

`MessagesState` 使用 `add_messages` Reducer，因此 `RemoveMessage` 会按 ID 删除已有消息。

删除是 State Update，会进入新的 Checkpoint。历史 Checkpoint 仍然可以通过时间旅行查看过去状态，但最新 State 中这些消息已经不存在。

<a id="summarize-messages"></a>
## 摘要消息

相比直接丢弃旧消息，更常见的方法是把较早对话压缩成摘要，并保留最近几轮原始消息。

State 可以增加 `summary` 字段：

:::python
```python
from typing import NotRequired
from langgraph.graph import MessagesState

class State(MessagesState):
    summary: NotRequired[str]
```
:::

然后定期更新摘要：

:::python
```python
from langchain.messages import HumanMessage, RemoveMessage


def summarize_conversation(state: State):
    summary = state.get("summary", "")

    if summary:
        prompt = (
            f"Existing summary:\n{summary}\n\n"
            "Extend the summary using the conversation above."
        )
    else:
        prompt = "Create a concise summary of the conversation above."

    response = model.invoke(
        state["messages"] + [HumanMessage(content=prompt)]
    )

    # Keep the latest messages and delete older raw history.
    delete_messages = [
        RemoveMessage(id=m.id)
        for m in state["messages"][:-4]
    ]

    return {
        "summary": response.content,
        "messages": delete_messages,
    }
```
:::

后续模型调用时，把摘要重新注入上下文：

```python
def call_model(state: State):
    messages = state["messages"]
    if summary := state.get("summary"):
        messages = [
            {"role": "system", "content": f"Conversation summary: {summary}"},
            *messages,
        ]
    response = model.invoke(messages)
    return {"messages": [response]}
```

### 摘要策略的权衡

摘要可以大幅降低 Context 长度，但会带来信息损失。不要把：

- 精确 ID；
- 数值；
- 合同条款；
- 用户明确约束；
- 尚未完成的 Task State；

只保存在自由文本摘要中。对这类信息，最好使用结构化 State Field 或长期 Memory。

## 在 Node 内读取短期 State

所有 Node 都可以读取当前 State，因此短期记忆并不限于消息：

```python
class State(MessagesState):
    current_plan: list[str]
    selected_tool: str | None
    retry_count: int
```

这使 LangGraph 能保存计划、Tool Result、Workflow Position 等结构化状态，而不仅是 Chat History。

<a id="add-long-term-memory"></a>
## 添加长期记忆

长期记忆使用 [Store](/oss/langgraph/stores)。Store 的数据独立于 Thread，因此不同对话可以访问同一份用户 Memory。

:::python
```python
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
graph = builder.compile(
    checkpointer=checkpointer,
    store=store,
)
```
:::

:::js
```typescript
import { MemoryStore } from "@langchain/langgraph";

const store = new MemoryStore();
const graph = builder.compile({
  checkpointer,
  store,
});
```
:::

生产环境应使用持久化 Store 后端。

## Namespace

Store 中的每条 Memory 都由：

- Namespace；
- Key；
- Value；

共同定位。

常见设计：

```python
namespace = (user_id, "memories")
```

也可以加入更多层级：

```python
(user_id, "preferences")
(user_id, "projects", project_id)
(organization_id, "shared_knowledge")
```

Namespace 是长期 Memory 的数据模型设计，不要把所有信息都扔到一个扁平空间。

## 写入长期 Memory

:::python
```python
import uuid
from langgraph.runtime import Runtime


def save_memory(state: State, runtime: Runtime):
    user_id = runtime.context.user_id
    namespace = (user_id, "memories")

    memory_id = str(uuid.uuid4())
    runtime.store.put(
        namespace,
        memory_id,
        {"memory": "The user prefers concise answers."},
    )
    return {}
```
:::

:::js
```typescript
const saveMemory = async (state, runtime) => {
  const namespace = [runtime.context.userId, "memories"];
  await runtime.store.put(
    namespace,
    crypto.randomUUID(),
    { memory: "The user prefers concise answers." }
  );
  return {};
};
```
:::

## 读取长期 Memory

:::python
```python

def call_model(state: State, runtime: Runtime):
    user_id = runtime.context.user_id
    namespace = (user_id, "memories")

    memories = runtime.store.search(namespace, limit=10)
    memory_text = "\n".join(item.value["memory"] for item in memories)

    prompt = f"Known user memories:\n{memory_text}"
    response = model.invoke([
        {"role": "system", "content": prompt},
        *state["messages"],
    ])
    return {"messages": [response]}
```
:::

这允许新 Thread 使用旧 Thread 保存的信息。

<a id="manage-long-term-memory"></a>
## 管理长期记忆

长期 Memory 并不是越多越好。应考虑：

- 什么信息值得长期保存？
- 是否存在过期时间？
- 新事实与旧事实冲突时如何更新？
- 是保存原始 Episode，还是提炼后的 Semantic Fact？
- 是否需要用户查看和删除 Memory？
- 如何避免把未经验证的模型推断永久写入 Memory？

一种实用分类：

### Semantic Memory

结构化事实和知识，例如：

```json
{
  "preferred_language": "zh-CN",
  "preferred_editor": "VS Code"
}
```

适合持续更新和直接检索。

### Episodic Memory

过去发生过的事件或成功 / 失败经验，例如：

```json
{
  "task": "deploy service",
  "outcome": "failed",
  "lesson": "database migration must run before traffic switch"
}
```

适合 Agent 从历史经验中学习。

### Procedural Memory

“应该怎么做”的规则，例如 Workflow、Skill、Prompt 或操作规范。这类 Memory 往往不应该由普通对话模型直接随意修改，而需要更严格的验证与版本控制。

## 语义搜索长期 Memory

Store 可以配置 Embedding，实现语义搜索。

:::python
```python
from langchain.embeddings import init_embeddings
from langgraph.store.memory import InMemoryStore

store = InMemoryStore(
    index={
        "embed": init_embeddings("openai:text-embedding-3-small"),
        "dims": 1536,
        "fields": ["memory"],
    }
)
```

```python
results = store.search(
    (user_id, "memories"),
    query=state["messages"][-1].content,
    limit=3,
)
```
:::

这样不需要把全部 Memory 都塞进 Context，只检索当前问题最相关的几条。

## 精确读取与更新 Memory

如果已经知道 Key，直接使用 `get`：

```python
item = store.get((user_id, "preferences"), "response_style")
```

更新同一个 Namespace + Key 会覆盖原 Value：

```python
store.put(
    (user_id, "preferences"),
    "response_style",
    {"style": "concise"},
)
```

这比每次创建新 Memory 更适合“当前用户偏好”这类单值事实。

## 删除 Memory

```python
store.delete((user_id, "memories"), memory_id)
```

生产系统应提供 Memory 生命周期管理，而不是只会添加、永不删除。

## 在 Hot Path 中更新 Memory

**Hot Path** 指用户请求执行过程中立即写 Memory：

```text
用户输入
 ↓
Agent 识别重要事实
 ↓
立即写 Store
 ↓
继续回答
```

优点：

- 新信息立即可用；
- 实现简单；
- 无需额外后台系统。

缺点：

- 增加用户请求延迟；
- 模型容易把不成熟推断直接长期化；
- Memory Extraction 会占用主 Context 和 Token。

## 在后台更新 Memory

另一种方式是在主请求结束后异步抽取 Memory：

```text
用户请求 → 正常回答
              ↓
          后台 Memory Job
              ↓
          提取 / 合并 / 去重
              ↓
             Store
```

优点：

- 不阻塞用户请求；
- 可以批量处理、去重、冲突解决；
- 可以使用专用 Memory Model / Prompt；
- 更容易加入审核和质量控制。

缺点是新 Memory 不会立即可用，系统也更复杂。

真实生产系统经常混合两者：关键显式偏好在 Hot Path 立即写入，其余对话经验后台整理。

## Memory Extraction

不要简单把每条用户消息都存进长期 Store。更合理的做法是让模型先判断：

1. 这是稳定事实还是当前临时上下文？
2. 是否已经存在同类 Memory？
3. 应新增、更新、合并还是忽略？
4. Memory 是否来自用户明确陈述，还是模型推断？

例如可以要求模型输出结构化操作：

```json
{
  "operation": "update",
  "key": "preferred_language",
  "value": "Chinese",
  "confidence": 1.0
}
```

随后由确定性代码执行 Store Mutation，而不是让模型直接自由写数据库。

## 在 Tool 中访问 Memory

Tool 也可以使用 Runtime Store。例如搜索用户偏好：

:::python
```python
from langchain.tools import tool, ToolRuntime

@tool
def get_user_preferences(runtime: ToolRuntime) -> str:
    user_id = runtime.context.user_id
    memories = runtime.store.search((user_id, "preferences"))
    return str([m.value for m in memories])
```
:::

这让 Tool 可以访问长期上下文，而不需要把全部 Memory 放入模型 Prompt。

## Store 与 State 的选择

| 数据 | 推荐位置 |
| --- | --- |
| 当前对话消息 | Graph State / Checkpointer |
| 当前计划和中间结果 | Graph State |
| 当前 Run 的 Retry Counter | Graph State |
| 用户长期偏好 | Store |
| 跨对话知识 | Store |
| 组织共享知识 | Store / 外部知识库 |
| 权威业务记录 | 外部数据库 / API |
| API Client / 数据库连接 | Runtime Context |

不要用 Store 代替业务数据库，也不要用 Graph State 代替长期知识库。

## Memory 与 RAG 的区别

RAG 通常检索一个相对稳定、外部构建的知识库；Agent Memory 通常来自智能体与用户过去的交互，并会持续演化。

二者可以使用类似的 Embedding / Vector Search 技术，但数据来源与生命周期不同：

```text
RAG
文档 → 索引 → 检索 → Context

Memory
交互 → 提取 / 合并 → Store → 检索 → Context
```

很多生产 Agent 会同时使用 RAG 和 Memory。

## Memory 与 Context Engineering

保存 Memory 只是第一步。真正决定智能体行为的是**什么时候把什么 Memory 放回 Context**。

常见 Context Policy：

- 每次固定注入少量 Profile；
- 根据当前 Query 语义检索 Top-k Memory；
- 针对不同 Node 使用不同 Memory Namespace；
- 对高优先级规则使用结构化字段 / System Prompt，而不是依赖语义检索；
- 限制 Memory Token Budget。

这可以避免长期 Store 变成新的“上下文垃圾场”。

## 生产环境注意事项

### 隔离

Namespace 必须包含可靠的 Tenant / User Boundary。不要让模型自己提供未验证的用户 ID，从而访问其他用户 Memory。

### 隐私

长期 Memory 可能包含用户数据。应设计：

- 删除与导出能力；
- 数据保留周期；
- 敏感字段分类；
- Encryption；
- Audit Log。

### 冲突解决

用户偏好可能改变：

```text
旧：用户喜欢每天早上 8 点提醒
新：用户改成 9 点
```

这类数据应更新同一个稳定 Key，而不是累积两个互相冲突的事实。

### 可信度

区分：

- 用户明确陈述；
- 外部系统验证事实；
- 模型推断。

不要把低置信度推断当作永久事实。

## 与 LangSmith 配合

[LangSmith](/langsmith/observability) 可以帮助你检查：

- 每次模型调用使用了哪些历史消息；
- 检索了哪些长期 Memory；
- 哪个 Node 写入了 Memory；
- Memory 是否真正改善结果；
- Context 长度与 Token 成本如何变化。

Memory 系统应该被评估，而不是仅凭“看起来更个性化”判断效果。

## 推荐架构

一个常见生产 Agent Memory 架构：

```text
                    ┌───────────────┐
用户请求 ──────────→│   LangGraph    │
                    │               │
                    │ Short-term    │←→ Checkpointer
                    │ State         │
                    │               │
                    │ Memory Search │←→ Store
                    └───────┬───────┘
                            │
                            ↓
                       Model / Tools
                            │
                            ↓
                    Memory Extraction
                            │
                     ┌──────┴──────┐
                     ↓             ↓
                  Hot Path      Background
                     └──────┬──────┘
                            ↓
                           Store
```
