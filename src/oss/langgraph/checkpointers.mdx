Checkpointer 会在每个 **Super-step（超步）**保存一份 Graph State Snapshot，并按 **Thread（线程）**组织这些检查点。使用 Checkpointer 编译图后，就可以实现人在回路、时间旅行调试、故障恢复以及对话记忆。

![Checkpoints](/oss/images/checkpoints.jpg)

<Info>
**Agent Server 会自动处理 Checkpoint**

使用 [Agent Server](/langsmith/agent-server) 时，无需手动实现或配置 Checkpointer。服务器会在后台处理持久化基础设施。
</Info>

<Tip>
可以使用 [LangSmith](https://smith.langchain.com) 追踪 Checkpoint State，并调试智能体如何跨会话恢复执行。参阅 [Tracing 快速入门](/langsmith/trace-with-langgraph)。
</Tip>

## 为什么需要 Checkpointer

以下功能依赖 Checkpointer：

- **人在回路**：允许人工检查、暂停、审批和修改 Graph State；修改完成后，图可以从保存的状态继续执行。参阅[中断](/oss/langgraph/interrupts)。
- **记忆**：同一 Thread 中后续交互可以继续使用此前保存的状态，从而形成对话记忆。参阅[添加记忆](/oss/langgraph/add-memory)。
- **时间旅行**：可以重放以前的执行、检查某个 Graph Step，或者从任意 Checkpoint Fork 出另一条执行路径。参阅[时间旅行](/oss/langgraph/use-time-travel)。
- **容错**：如果某个 Super-step 中的一个或多个 Node 失败，可以从上一个成功的 Checkpoint 恢复。
<a id="pending-writes"></a>
- **Pending Writes**：如果同一个 Super-step 中某个 Node 失败，而其他 Node 已成功执行，LangGraph 会保存这些成功 Node 的中间写入。恢复时不必重复运行已经成功的 Node。

## 核心概念

### Thread

Thread 是用于组织一系列 Run 的持久化执行上下文。Checkpointer 保存的每个 Checkpoint 都属于某个 `thread_id`。

使用带 Checkpointer 的图时，必须在 Config 的 `configurable` 中指定 `thread_id`：

:::python
```python
{"configurable": {"thread_id": "1"}}
```
:::

:::js
```typescript
{
  configurable: {
    thread_id: "1";
  }
}
```
:::

Checkpointer 使用 `thread_id` 作为保存和加载 Checkpoint 的主索引。如果没有 `thread_id`，就无法持久化 State，也无法在 [Interrupt](/oss/langgraph/interrupts) 后恢复执行。

### Checkpoint

Thread 在某一时刻的 State 称为 **Checkpoint**。LangGraph 在每个 [Super-step](#super-steps) 边界保存一份 Graph State Snapshot，并通过 `StateSnapshot` 表示。

#### Super-step

一个 Super-step 可以理解为 Graph Runtime 的一轮“Tick”：这一轮中被调度的所有 Node 都会执行，其中一些 Node 可能并行运行。对于 `START -> A -> B -> END` 这样的顺序图，Input、A 和 B 分别位于不同的 Super-step，因此每个阶段结束后都会形成 Checkpoint。

这对于[时间旅行](/oss/langgraph/use-time-travel)很重要：图只能从 Checkpoint，也就是 Super-step Boundary 恢复执行。

除了完整的 Super-step Checkpoint，LangGraph 还会在 **Node / Task 粒度**保存 Write。某个 Node 完成后，它的输出就会写入 Checkpointer；因此同一 Super-step 中如果另一个并行 Node 失败，已成功 Node 的结果仍然是持久化的。这正是 [Pending Writes](#pending-writes) 容错机制的基础。

下面是一个简单示例：

:::python
```python
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langchain_core.runnables import RunnableConfig
from typing import Annotated
from typing_extensions import TypedDict
from operator import add

class State(TypedDict):
    foo: str
    bar: Annotated[list[str], add]

def node_a(state: State):
    return {"foo": "a", "bar": ["a"]}

def node_b(state: State):
    return {"foo": "b", "bar": ["b"]}

workflow = StateGraph(State)
workflow.add_node(node_a)
workflow.add_node(node_b)
workflow.add_edge(START, "node_a")
workflow.add_edge("node_a", "node_b")
workflow.add_edge("node_b", END)

checkpointer = InMemorySaver()
graph = workflow.compile(checkpointer=checkpointer)

config: RunnableConfig = {"configurable": {"thread_id": "1"}}
graph.invoke({"foo": "", "bar":[]}, config)
```
:::

:::js
```typescript
import { StateGraph, StateSchema, ReducedValue, START, END, MemorySaver } from "@langchain/langgraph";
import { z } from "zod/v4";

const State = new StateSchema({
  foo: z.string(),
  bar: new ReducedValue(
    z.array(z.string()).default(() => []),
    {
      inputSchema: z.array(z.string()),
      reducer: (x, y) => x.concat(y),
    }
  ),
});

const workflow = new StateGraph(State)
  .addNode("nodeA", (state) => ({ foo: "a", bar: ["a"] }))
  .addNode("nodeB", (state) => ({ foo: "b", bar: ["b"] }))
  .addEdge(START, "nodeA")
  .addEdge("nodeA", "nodeB")
  .addEdge("nodeB", END);

const checkpointer = new MemorySaver();
const graph = workflow.compile({ checkpointer });

const config = { configurable: { thread_id: "1" } };
await graph.invoke({ foo: "", bar: [] }, config);
```
:::

这次执行会形成四个完整 Checkpoint：

1. 空 Checkpoint，下一步为 `START`。
2. 保存用户 Input，下一步执行 `node_a`。
3. 保存 `node_a` 输出，下一步执行 `node_b`。
4. 保存 `node_b` 输出，且没有后续 Node，表示 Graph 完成。

`bar` 最终会同时包含 `a` 与 `b`，因为该 Channel 配置了累加 Reducer。

#### Checkpoint Namespace

每个 Checkpoint 都包含 `checkpoint_ns`，用来标识它属于哪个 Graph / Subgraph：

- `""`：根图。
- `"node_name:uuid"`：作为某个 Node 调用的 Subgraph。
- 嵌套 Subgraph 会通过 `|` 拼接多级 Namespace。

Node 内可以从 Config 中获取 Namespace：

:::python
```python
from langchain_core.runnables import RunnableConfig

def my_node(state: State, config: RunnableConfig):
    checkpoint_ns = config["configurable"]["checkpoint_ns"]
```
:::

:::js
```typescript
import { RunnableConfig } from "@langchain/core/runnables";

function myNode(state: typeof State.Type, config: RunnableConfig) {
  const checkpointNs = config.configurable?.checkpoint_ns;
}
```
:::

更多信息参阅[子图](/oss/langgraph/use-subgraphs)。

## 获取和更新 State

### 获取当前 State

与持久化 Graph State 交互时，必须指定 Thread ID。

:::python
```python
# Latest checkpoint
config = {"configurable": {"thread_id": "1"}}
graph.get_state(config)

# Specific checkpoint
config = {
    "configurable": {
        "thread_id": "1",
        "checkpoint_id": "1ef663ba-28fe-6528-8002-5a559208592c"
    }
}
graph.get_state(config)
```
:::

:::js
```typescript
const config = { configurable: { thread_id: "1" } };
await graph.getState(config);

const specificConfig = {
  configurable: {
    thread_id: "1",
    checkpoint_id: "1ef663ba-28fe-6528-8002-5a559208592c",
  },
};
await graph.getState(specificConfig);
```
:::

返回值是 `StateSnapshot`。

### `StateSnapshot` 字段

:::python
| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `values` | `dict` | 当前 Checkpoint 中各 State Channel 的值。 |
| `next` | `tuple[str, ...]` | 下一步要执行的 Node；空元组表示图已结束。 |
| `config` | `dict` | 包含 `thread_id`、`checkpoint_ns`、`checkpoint_id`。 |
| `metadata` | `dict` | 执行元数据，包括 `source`、Node `writes` 和 Super-step `step`。 |
| `created_at` | `str` | Checkpoint 创建时间。 |
| `parent_config` | `dict \| None` | 上一个 Checkpoint 的 Config。 |
| `tasks` | `tuple[PregelTask, ...]` | 当前 Step 的 Task，包括名称、Error、Interrupt 和可选 Subgraph State。 |
:::

:::js
| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `values` | `object` | 当前 Checkpoint 中各 State Channel 的值。 |
| `next` | `string[]` | 下一步要执行的 Node；空数组表示图已结束。 |
| `config` | `object` | 包含 `thread_id`、`checkpoint_ns`、`checkpoint_id`。 |
| `metadata` | `object` | 执行元数据。 |
| `createdAt` | `string` | Checkpoint 创建时间。 |
| `parentConfig` | `object \| null` | 上一个 Checkpoint 的 Config。 |
| `tasks` | `PregelTask[]` | 当前 Step 的 Task。 |
:::

### 获取 State History

使用 `get_state_history` / `getStateHistory` 可以读取一个 Thread 的历史 Checkpoint。历史通常按从新到旧的顺序返回。

:::python
```python
history = list(graph.get_state_history(config))

# Find checkpoint before a node
before_node_b = next(s for s in history if s.next == ("node_b",))

# Find by step
step_2 = next(s for s in history if s.metadata["step"] == 2)

# Find forks created by update_state
forks = [s for s in history if s.metadata["source"] == "update"]

# Find an interrupt checkpoint
interrupted = next(
    s for s in history
    if s.tasks and any(t.interrupts for t in s.tasks)
)
```
:::

:::js
```typescript
const history = [];
for await (const state of graph.getStateHistory(config)) {
  history.push(state);
}

const beforeNodeB = history.find((s) => s.next.includes("nodeB"));
const step2 = history.find((s) => s.metadata.step === 2);
const forks = history.filter((s) => s.metadata.source === "update");
const interrupted = history.find(
  (s) => s.tasks.length > 0 && s.tasks.some((t) => t.interrupts.length > 0)
);
```
:::

### Replay

Replay 会从历史 Checkpoint 重新执行后续步骤。Checkpoint 之前的 Node 不会重新运行，因为其结果已保存；Checkpoint 之后的 Node 会重新执行，包括 LLM 调用、API 请求和 [Interrupt](/oss/langgraph/interrupts)。

完整说明参阅[时间旅行](/oss/langgraph/use-time-travel)。

![Replay](/oss/images/re_play.png)

### 更新 State

`update_state` / `updateState` 会基于当前 Checkpoint 创建一个新的 Checkpoint，而不是原地修改历史。更新仍然会经过对应的 [Reducer](/oss/langgraph/graph-api#reducers)。因此，如果某个 Channel 使用累加 Reducer，新值会与旧值合并，而不是简单覆盖。

还可以通过 `as_node` / `asNode` 指定“这次 Update 被视为来自哪个 Node”，从而影响下一步执行位置。参阅[从指定 Node 开始时间旅行](/oss/langgraph/use-time-travel#from-a-specific-node)。

![Update](/oss/images/checkpoints_full_story.jpg)

## Durability Mode

LangGraph 支持三种 Durability Mode，用于权衡性能与数据一致性：

:::python
```python
graph.stream({"input": "test"}, durability="sync")
```
:::

:::js
```typescript
await graph.stream(
  { input: "test" },
  { durability: "sync" }
)
```
:::

从性能高、持久性低到持久性高依次为：

- **`"exit"`**：只在 Graph Execution 退出时持久化，包括成功、Error 或人在回路 Interrupt。性能最好，但进程中途崩溃时无法恢复中间 State。
- **`"async"`**：下一 Step 执行时异步保存上一 Step。性能与持久性之间比较均衡，但进程恰好在写入前崩溃时存在极小的数据丢失窗口。
- **`"sync"`**：下一 Step 开始前同步完成 Checkpoint 写入。持久性最高，但有额外 I/O 开销。

## 优化 Checkpoint 存储

:::python
默认情况下，每个 Super-step 都会保存各 State Channel 的完整 Value。对于长时间运行、持续累积大量消息的 Thread，这可能导致存储量持续增长。

@[`DeltaChannel`] 只保存增量 Delta，而不是每次都保存完整累计值，因此特别适合追加型 Channel。参阅 [DeltaChannel](/oss/langgraph/pregel#deltachannel)。

<Warning>
`DeltaChannel` 需要 `langgraph>=1.2`，目前仍为 Beta，未来 API 可能变化。
</Warning>
:::

### Checkpointer 接口

:::python
`BaseCheckpointSaver` 的主要方法：

- `.put`：保存 Checkpoint 以及 Config / Metadata。
- `.put_writes`：保存与 Checkpoint 关联的中间 Write，即 [Pending Writes](#pending-writes)。
- `.get_tuple`：通过 `thread_id` / `checkpoint_id` 读取 Checkpoint Tuple。
- `.list`：列出符合 Config 与过滤条件的 Checkpoint。

异步图执行会使用对应异步方法 `.aput`、`.aput_writes`、`.aget_tuple`、`.alist`。
:::

:::js
JavaScript 中对应接口包括 `.put`、`.putWrites`、`.getTuple` 与 `.list`。
:::

:::python
## Serializer

Checkpointer 保存 Graph State 时需要序列化各 Channel Value。`langgraph_checkpoint` 定义 @[SerializerProtocol]，并提供默认 @[JsonPlusSerializer]，支持 LangChain / LangGraph Primitive、Datetime、Enum 等多种类型。

### Pickle Fallback

默认 @[JsonPlusSerializer] 使用 ormsgpack 和 JSON。如果需要保存 msgpack 暂不支持的对象，例如 Pandas DataFrame，可以启用 `pickle_fallback`：

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.checkpoint.serde.jsonplus import JsonPlusSerializer

graph.compile(
    checkpointer=InMemorySaver(
        serde=JsonPlusSerializer(pickle_fallback=True)
    )
)
```

### 加密

可以向任何 @[BaseCheckpointSaver] 传入 @[EncryptedSerializer] 来加密持久化 State。最简单的方式是使用 AES，并通过 `LANGGRAPH_AES_KEY` 提供密钥：

```python
import sqlite3
from langgraph.checkpoint.serde.encrypted import EncryptedSerializer
from langgraph.checkpoint.sqlite import SqliteSaver

serde = EncryptedSerializer.from_pycryptodome_aes()
checkpointer = SqliteSaver(sqlite3.connect("checkpoint.db"), serde=serde)
```

在 LangSmith 中，只要设置 `LANGGRAPH_AES_KEY`，Checkpoint Encryption 会自动启用。
:::

## 构建自定义 Checkpointer

:::python
<Tip>
建议使用 [`langgraph-checkpoint-conformance`](#使用一致性测试套件)持续验证自定义实现，并在 CI 中运行。
</Tip>

自定义后端需要继承 `BaseCheckpointSaver`。持久化层主要包含两种存储抽象：

- **Checkpoints**：每个 Super-step 一条记录，保存序列化 Graph State、Channel Version，以及 Parent Checkpoint。
- **Writes**：每个 Node Output 一条或多条记录，保存与 Checkpoint 关联的 `(task_id, channel, value)`。

### 基础契约

需要实现同步或异步版本的核心操作：

- `put` / `aput`
- `put_writes` / `aput_writes`
- `get_tuple` / `aget_tuple`
- `list` / `alist`
- `delete_thread` / `adelete_thread`

实现时要特别保证**按具体 Checkpoint ID 直接查询**的路径正确。Graph 恢复、Subgraph、Delta Channel 等机制都依赖 `(thread_id, checkpoint_ns, checkpoint_id)` 精确定位历史记录。

### 推荐数据库 Schema

```sql
CREATE TABLE checkpoints (
    thread_id          TEXT NOT NULL,
    checkpoint_ns      TEXT NOT NULL DEFAULT '',
    checkpoint_id      TEXT NOT NULL,
    parent_checkpoint_id TEXT,
    type               TEXT,
    checkpoint         BYTEA,
    metadata           JSONB,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)
);

CREATE TABLE writes (
    thread_id     TEXT NOT NULL,
    checkpoint_ns TEXT NOT NULL DEFAULT '',
    checkpoint_id TEXT NOT NULL,
    task_id       TEXT NOT NULL,
    task_path     TEXT NOT NULL DEFAULT '',
    idx           INTEGER NOT NULL,
    channel       TEXT NOT NULL,
    type          TEXT,
    value         BYTEA,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id, task_id, task_path, idx)
);
```

`checkpoint_id` 是可按字典序排序的 ULID，因此可以高效实现“最新 Checkpoint”和“按 ID 精确查找”。非 SQL 后端也应该保证 `(thread_id, checkpoint_ns, checkpoint_id)` 能接近 O(1) 查询，而不是扫描整个 Thread。

### 序列化

应始终使用 `self.serde` 序列化 Checkpoint、Write 和 Metadata，而不是自行直接使用 `pickle`。默认 `JsonPlusSerializer` 已支持 LangGraph Native Type、Pydantic v2、Dataclass、NumPy、Datetime、Enum 等。

### 扩展能力

以下方法并非最基础契约的一部分，但可以启用更多 Agent Server 能力：

| 方法 | 能力 |
| --- | --- |
| `adelete_for_runs` | Multi-task Rollback Strategy |
| `acopy_thread` | 高效 Thread Fork |
| `aprune` | Thread History Pruning |
| `aget_delta_channel_history` | 高效重建 Delta Channel State |

Agent Server 会在启动时检测自定义 Checkpointer 支持哪些扩展能力。

### Delta Channel 支持

<Info>
`DeltaChannel` 仍处于 Beta，其 API 与磁盘表示未来可能变化。
</Info>

`DeltaChannel` 不在每个 Checkpoint Blob 中保存完整累计值，而是保留增量 Write，并在加载时回放祖先 Checkpoint 的 Write 来重建 Value。这样，对于 `messages` 这类不断增长的 Channel，单 Step Checkpoint 大小可以从 O(N) 降到接近 O(1)。

运行时需要获得：

- `writes`：从最近 Snapshot 到当前 Checkpoint 的所有相关写入，按时间从旧到新排列。
- `seed`：可选的最近 `_DeltaSnapshot`。

如果实现自定义 `get_delta_channel_history`，必须保证祖先链和 Write 顺序正确。尤其需要注意：默认实现会不断通过具体 `checkpoint_id` 调用 `get_tuple`；如果按 ID 查询路径错误，Delta State 可能静默重建为空。

#### Pruning

Delta Channel 的一个 Checkpoint 并不是自包含的，它依赖祖先 Write Chain。做 Prune / Delete 时不能删除仍被存活 Checkpoint 依赖的 Write。安全做法包括：

1. Prune 前遍历依赖链并保护必要 Write。
2. Prune 前强制写入完整 `_DeltaSnapshot`。
3. 暂时不对含 Delta Channel 的 Thread 做 History Pruning。

#### Copy Thread

实现 `copy_thread` 时，需要复制足够完整的祖先链，使每个 Delta Channel 都能追溯到至少一个 `_DeltaSnapshot`；仅复制 Head Checkpoint 会导致 State 无法正确重建。

### 使用一致性测试套件

`langgraph-checkpoint-conformance` 可以验证实现是否符合 Base Contract，包括 Delta Channel History：

```bash
pip install langgraph-checkpoint-conformance
```

```python
import asyncio
from langgraph.checkpoint.conformance import checkpointer_test, validate

@checkpointer_test(name="MyCheckpointer")
async def my_checkpointer():
    async with MyCheckpointer.create() as saver:
        yield saver

async def main():
    report = await validate(my_checkpointer)
    report.print_report()
    if not report.passed_all_base():
        raise RuntimeError("Checkpointer failed conformance suite")

asyncio.run(main())
```

建议把这套测试作为 CI Gate，在发布自定义 Checkpointer 前持续运行。
