Graph API 用显式的 **State + Node + Edge** 描述工作流。它适合需要复杂分支、并行执行、共享状态、可视化拓扑以及精细控制 Runtime 行为的智能体系统。

本页集中介绍最常用的 Graph API 实践模式。概念性说明参阅 [Graph API 概览](/oss/langgraph/graph-api)。

## 定义 State

Graph State 是所有 Node 之间共享的数据。Node 读取 State，并返回 **Partial Update**；LangGraph 再根据每个字段对应的 Reducer 把 Update 合并进当前 State。

:::python
```python
from typing_extensions import TypedDict

class State(TypedDict):
    topic: str
    draft: str
    score: float
```
:::

:::js
```typescript
import * as z from "zod";
import { StateSchema } from "@langchain/langgraph";

const State = new StateSchema({
  topic: z.string(),
  draft: z.string().optional(),
  score: z.number().optional(),
});
```
:::

Node 不需要返回完整 State：

```python
def write_draft(state: State):
    return {"draft": f"Draft about {state['topic']}"}
```

<a id="define-input-and-output-schemas"></a>
## 定义不同的输入和输出 Schema

大型应用中，内部 State 往往包含很多字段，但调用者只应该看到少量输入和输出。可以分别定义 Input / Output / Internal Schema。

:::python
```python
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class InputState(TypedDict):
    user_input: str

class OutputState(TypedDict):
    answer: str

class OverallState(InputState, OutputState):
    internal_notes: str


def prepare(state: InputState):
    return {"internal_notes": f"Analyze: {state['user_input']}"}


def respond(state: OverallState):
    return {"answer": state["internal_notes"]}

builder = StateGraph(
    OverallState,
    input_schema=InputState,
    output_schema=OutputState,
)
builder.add_node("prepare", prepare)
builder.add_node("respond", respond)
builder.add_edge(START, "prepare")
builder.add_edge("prepare", "respond")
builder.add_edge("respond", END)

graph = builder.compile()
```
:::

Input / Output Schema 控制外部接口，但并不意味着内部 Channel 会自动从 Streaming 中脱敏。如果某个字段具有敏感性，需要在 Streaming 层显式限制 `output_keys` 或设计单独的输出通道。

<a id="use-pydantic-models-for-graph-state"></a>
## 使用 Pydantic Model 作为 Graph State

Python 中除了 `TypedDict`，也可以使用 Pydantic `BaseModel` 获得 Runtime Validation 和默认值。

```python
from pydantic import BaseModel, Field

class State(BaseModel):
    topic: str
    retries: int = Field(default=0, ge=0)
```

Pydantic 会增加额外校验开销。若不需要 Runtime Validation，`TypedDict` 通常更轻量。

## 为 State 字段定义 Reducer

默认情况下，同一个字段的新 Update 会覆盖旧值。若要累加、合并或执行自定义逻辑，应为字段定义 Reducer。

:::python
```python
from operator import add
from typing import Annotated
from typing_extensions import TypedDict

class State(TypedDict):
    messages: Annotated[list[str], add]
```
:::

:::js
```typescript
import { ReducedValue, StateSchema } from "@langchain/langgraph";
import * as z from "zod";

const State = new StateSchema({
  messages: new ReducedValue(
    z.array(z.string()).default(() => []),
    {
      inputSchema: z.array(z.string()),
      reducer: (left, right) => left.concat(right),
    }
  ),
});
```
:::

Reducer 对并行执行尤其重要：同一个 Super-step 中多个 Node 如果同时写同一字段，而该字段又没有支持多写入的 Reducer，Runtime 可能抛出 `InvalidUpdateError`。

<a id="bypass-reducers-with-overwrite"></a>
## 使用 Overwrite 绕过 Reducer

有时字段通常使用累加 Reducer，但某一次更新希望**完全替换**旧值。Python 可以使用 `Overwrite`：

```python
from langgraph.types import Overwrite


def reset_messages(state: State):
    return {"messages": Overwrite([])}
```

注意：返回空列表本身并不会清空带追加 Reducer 的字段，因为 Reducer 会把空列表与旧值合并。

## 使用 MessagesState

聊天智能体最常见的 State 是消息列表。Python 可直接使用 `MessagesState`：

```python
from langgraph.graph import MessagesState

class State(MessagesState):
    user_id: str
```

`messages` 字段使用 Message-aware Reducer `add_messages`，支持按 Message ID 更新已有消息，而不只是简单追加。

JavaScript 可以使用 `MessagesValue`：

```typescript
import { StateSchema, MessagesValue } from "@langchain/langgraph";

const State = new StateSchema({
  messages: MessagesValue,
});
```

## 添加 Node

Node 是接收 State 并返回 State Update 的函数。

:::python
```python
from langgraph.graph import StateGraph

builder = StateGraph(State)

def node_a(state: State):
    return {"value": state["value"] + 1}

builder.add_node("node_a", node_a)
```
:::

:::js
```typescript
const nodeA: typeof State.Node = async (state) => {
  return { value: state.value + 1 };
};

builder.addNode("nodeA", nodeA);
```
:::

一个好的 Node 通常对应一个有意义的业务阶段，并且值得独立 Trace、Retry 或 Resume。

### Async Node

I/O 密集型操作建议使用 Async Node：

:::python
```python
async def call_api(state: State):
    result = await client.fetch(state["query"])
    return {"result": result}
```
:::

### 在 Node 中访问 Config

:::python
```python
from langchain_core.runnables import RunnableConfig


def node(state: State, config: RunnableConfig):
    thread_id = config["configurable"]["thread_id"]
    return {}
```
:::

Config 适合放一次 Invocation 的执行参数，例如 Thread ID、Tag、Metadata 等。

<a id="add-runtime-configuration"></a>
## 添加 Runtime Context

Model Client、数据库连接、Tenant ID 等依赖不应该塞进持久化 State。可以通过 Runtime Context 注入。

:::python
```python
from dataclasses import dataclass
from langgraph.graph import StateGraph
from langgraph.runtime import Runtime

@dataclass
class Context:
    user_id: str
    model_name: str = "gpt-5.4-mini"

builder = StateGraph(State, context_schema=Context)


def node(state: State, runtime: Runtime[Context]):
    user_id = runtime.context.user_id
    return {"owner": user_id}

# Later
graph.invoke(
    input,
    context=Context(user_id="u-123"),
)
```
:::

:::js
```typescript
const Context = z.object({
  userId: z.string(),
  modelName: z.string().default("gpt-5.4-mini"),
});

const builder = new StateGraph(State, Context);
```
:::

Runtime 还可以提供 `store`、Stream Writer、Heartbeat 等运行时能力。

## 添加 Edge

普通 Edge 表示固定控制流：

:::python
```python
from langgraph.graph import START, END

builder.add_edge(START, "node_a")
builder.add_edge("node_a", "node_b")
builder.add_edge("node_b", END)
```
:::

:::js
```typescript
builder
  .addEdge(START, "nodeA")
  .addEdge("nodeA", "nodeB")
  .addEdge("nodeB", END);
```
:::

如果一个 Node 有多条普通出边，下一个 Super-step 中会并行执行这些目标 Node。

## 条件 Edge

Routing Function 读取 State，并返回目标 Node 名称：

:::python
```python
from typing import Literal


def route(state: State) -> Literal["retry", "finish"]:
    if state["score"] < 0.8:
        return "retry"
    return "finish"

builder.add_conditional_edges("evaluate", route)
```
:::

:::js
```typescript
builder.addConditionalEdges("evaluate", (state) => {
  return state.score < 0.8 ? "retry" : "finish";
});
```
:::

Routing Function 最好保持纯函数，不要在其中执行昂贵副作用。

## 使用 Command 同时更新 State 和路由

如果一个 Node 需要同时返回 State Update 和下一个目标，可以返回 `Command`。

:::python
```python
from typing import Literal
from langgraph.types import Command


def node(state: State) -> Command[Literal["approved", "rejected"]]:
    if state["score"] > 0.8:
        return Command(
            update={"status": "approved"},
            goto="approved",
        )
    return Command(
        update={"status": "rejected"},
        goto="rejected",
    )
```
:::

:::js
```typescript
return new Command({
  update: { status: "approved" },
  goto: "approved",
});
```
:::

不要在同一个 Node 上同时配置固定 Edge 和 `Command(goto=...)`，否则两条路径都可能被调度。

<a id="map-reduce-and-the-send-api"></a>
## Map-Reduce 与 Send API

当并行 Worker 数量在 Runtime 才能确定时，使用 `Send` 动态创建执行分支。

:::python
```python
from operator import add
from typing import Annotated
from langgraph.types import Send

class State(TypedDict):
    subjects: list[str]
    jokes: Annotated[list[str], add]

class WorkerState(TypedDict):
    subject: str
    jokes: Annotated[list[str], add]


def fan_out(state: State):
    return [
        Send("generate_joke", {"subject": subject})
        for subject in state["subjects"]
    ]


def generate_joke(state: WorkerState):
    return {"jokes": [f"Joke about {state['subject']}"]}

builder.add_conditional_edges("orchestrator", fan_out, ["generate_joke"])
```
:::

这正是 Orchestrator-Worker、动态 Map-Reduce 等模式的基础。

## 等待多个并行分支汇合

多个 Node 可以并行执行，并在同一个后继 Node 汇合：

```text
        ┌→ A ─┐
START ──┤     ├→ D → END
        └→ B ─┘
```

```python
builder.add_edge(START, "a")
builder.add_edge(START, "b")
builder.add_edge("a", "d")
builder.add_edge("b", "d")
```

LangGraph 会等 A 和 B 所在 Super-step 完成后，再调度 D。

如果并行分支写入同一个字段，请确保 Reducer 可以合并多份 Update。

## 控制并行度

动态 Fan-out 可能产生大量并发请求。生产环境中应结合：

- Model / API Provider 限流；
- Worker Semaphore；
- Agent Server 并发配置；
- Retry Backoff；
- Query Budget。

不要把“图支持并行”理解为“应该无限并行”。

## 从 Node 内调用 Task

如果一个 Node 包含多个昂贵步骤，但不希望把每一步都暴露为 Graph Node，可以使用 Functional API 的 `task`。

:::python
```python
from langgraph.func import task

@task
def fetch_profile(user_id: str):
    return db.fetch_profile(user_id)

@task
def fetch_orders(user_id: str):
    return db.fetch_orders(user_id)

async def prepare_context(state: State):
    profile = await fetch_profile(state["user_id"])
    orders = await fetch_orders(state["user_id"])
    return {"context": {"profile": profile, "orders": orders}}
```
:::

Task Result 可以独立 Checkpoint，因此 Node Resume 时无需重复已经成功完成的昂贵步骤。

## 添加 Retry Policy

对瞬时错误配置 Retry：

:::python
```python
from langgraph.types import RetryPolicy

builder.add_node(
    "call_api",
    call_api,
    retry_policy=RetryPolicy(
        max_attempts=3,
        initial_interval=1.0,
        backoff_factor=2.0,
    ),
)
```
:::

:::js
```typescript
builder.addNode("callApi", callApi, {
  retryPolicy: {
    maxAttempts: 3,
    initialInterval: 1000,
    backoffFactor: 2,
  },
});
```
:::

详见[容错](/oss/langgraph/fault-tolerance)。

## 添加 Timeout 与 Error Handler

高延迟外部调用可以设置 Timeout；Retry 耗尽后可以进入 Error Handler 做补偿。

:::python
```python
from langgraph.types import TimeoutPolicy

builder.add_node(
    "charge_payment",
    charge_payment,
    timeout=TimeoutPolicy(run_timeout=30),
    retry_policy=RetryPolicy(max_attempts=3),
    error_handler=payment_error_handler,
)
```
:::

对于支付、库存等工作流，可让 Error Handler 返回 `Command(goto="compensate")`，实现 Saga / Compensation Flow。

## Deferred Node

某些 Node 应该等当前 Graph 中其他可执行工作都完成后再运行，例如最终聚合器。可以配置 `defer=True`。

:::python
```python
builder.add_node("finalize", finalize, defer=True)
```
:::

:::js
```typescript
builder.addNode("finalize", finalize, { defer: true });
```
:::

这适合“最后统一收尾”的场景，而不是依赖手工维护大量汇合 Edge。

## Node 缓存

对于相同输入经常重复出现的昂贵 Node，可以配置缓存。

:::python
```python
from langgraph.cache.memory import InMemoryCache
from langgraph.types import CachePolicy

builder.add_node(
    "expensive",
    expensive,
    cache_policy=CachePolicy(ttl=60),
)

graph = builder.compile(cache=InMemoryCache())
```
:::

缓存适合纯函数或输入决定输出的操作。不要缓存包含不可预测副作用的 Node。

## 持久化图

向 `compile()` 传入 Checkpointer：

:::python
```python
from langgraph.checkpoint.memory import InMemorySaver

graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "1"}}
graph.invoke(input, config)
```
:::

:::js
```typescript
import { MemorySaver } from "@langchain/langgraph";

const graph = builder.compile({ checkpointer: new MemorySaver() });
const config = { configurable: { thread_id: "1" } };
await graph.invoke(input, config);
```
:::

生产环境应使用持久化后端。详见 [Checkpointer](/oss/langgraph/checkpointers)。

snapshot = graph.get_state(config)

## 更新 State

`update_state` 会创建新的 Checkpoint，而不是修改历史：

:::python
```python
new_config = graph.update_state(
    config,
    {"status": "manually corrected"},
)
```
:::

更新仍会经过对应 Reducer。若要从历史 Checkpoint 分叉，参阅[时间旅行](/oss/langgraph/use-time-travel)。

## 获取 State History

```python
for snapshot in graph.get_state_history(config):
    print(snapshot.config, snapshot.values, snapshot.next)
```

可以用它构建执行历史 UI、调试某个决策点，或选择一个 Checkpoint Replay / Fork。

## 人在回路

在 Node 中调用 `interrupt()`：

:::python
```python
from langgraph.types import interrupt, Command


def approve(state: State):
    decision = interrupt({
        "question": "Approve this action?",
        "action": state["action"],
    })
    return {"approved": decision}

config = {"configurable": {"thread_id": "1"}}
graph.invoke(input, config)
graph.invoke(Command(resume=True), config)
```
:::

Resume 时 Node 会从函数开头重新执行，Interrupt 之前的副作用必须幂等。完整说明参阅[中断](/oss/langgraph/interrupts)。

## Streaming

### State Update

```python
for chunk in graph.stream(input, stream_mode="updates"):
    print(chunk)
```

### 完整 State

```python
for state in graph.stream(input, stream_mode="values"):
    print(state)
```

### LLM Token

```python
for msg, metadata in graph.stream(input, stream_mode="messages"):
    print(msg.content, end="")
```

### Event Streaming

新应用优先考虑类型化 Event Streaming：

```python
stream = graph.stream_events(input, version="v3")
for message in stream.messages:
    print(message.text)

final_state = stream.output
```

详见[流式输出](/oss/langgraph/streaming)和[事件流](/oss/langgraph/event-streaming)。

## 使用 Subgraph

如果 Parent / Child Graph 共享 State Key，可以直接把编译后的 Subgraph 添加为 Node：

```python
subgraph = sub_builder.compile()
parent_builder.add_node("research", subgraph)
```

如果 Schema 不同，在 Parent Node 中调用 Subgraph 并手工转换输入输出：

```python
def call_research(state: ParentState):
    result = research_graph.invoke({"query": state["question"]})
    return {"research": result["answer"]}
```

详见[子图](/oss/langgraph/use-subgraphs)。

## 从 Subgraph 跳转到 Parent

Subgraph Node 可以返回：

```python
Command(
    update={"status": "done"},
    goto="parent_node",
    graph=Command.PARENT,
)
```

这常用于多智能体 Handoff。

## 设置递归限制

存在循环的图应配置合理的终止条件，并可额外设置 `recursion_limit`：

:::python
```python
graph.invoke(input, {"recursion_limit": 100})
```
:::

:::js
```typescript
await graph.invoke(input, { recursionLimit: 100 });
```
:::

Python 还可以通过 `RemainingSteps` 在 State 中读取剩余步数，并在接近上限时主动结束。

## 动态修改图结构与兼容性

图部署后仍可以新增 Edge、Node 或 State Field，但已有 Thread 可能正在从旧 Checkpoint Resume。

一般原则：

- 新增 Optional State Field 通常安全；
- 删除 / 重命名正在被旧 Thread 使用的 Node 可能破坏 Resume；
- 重命名 State Key 不会自动迁移历史数据；
- 行为语义发生变化时，可以在 State 中保存 `flow_version`，让旧 Thread 保持旧路径。

详见[向后兼容](/oss/langgraph/backward-compatibility)。

## 一个完整的 Agent Loop

下面是最典型的 LangGraph Agent 架构：

:::python
```python
from langchain.tools import tool
from langchain.chat_models import init_chat_model
from langgraph.graph import MessagesState, StateGraph, START, END
from langgraph.prebuilt import ToolNode

@tool
def search(query: str) -> str:
    """Search the knowledge base."""
    return f"Result for {query}"

model = init_chat_model("openai:gpt-5.4-mini").bind_tools([search])


def call_model(state: MessagesState):
    return {"messages": [model.invoke(state["messages"])]}


def route(state: MessagesState):
    return "tools" if state["messages"][-1].tool_calls else END

builder = StateGraph(MessagesState)
builder.add_node("model", call_model)
builder.add_node("tools", ToolNode([search]))
builder.add_edge(START, "model")
builder.add_conditional_edges("model", route, ["tools", END])
builder.add_edge("tools", "model")

graph = builder.compile()
```
:::

如果只需要标准 ReAct / Tool-calling Agent，优先使用 LangChain [`create_agent`](/oss/langchain/agents)。直接使用 Graph API 的价值在于：你可以精确控制特殊路由、审批、Subgraph、Memory、Fault Tolerance 与业务状态机。

## 设计建议

### Node 应代表有意义的执行边界

不要把每一行代码都拆成 Node。一个操作如果值得独立：

- Trace；
- Retry；
- Checkpoint；
- Interrupt；
- Route；

它通常才值得成为 Node。

### 把 Routing 与业务动作分开

纯 Routing 用 Conditional Edge；同时更新 State 和 Routing 用 `Command`。不要让一个函数同时承担太多职责。

### 副作用必须考虑 Resume

使用 Checkpointer 后，Node 可能因为 Retry 或 Interrupt 从开头重新执行。数据库写入、支付、发邮件等外部副作用应使用 Idempotency Key、Upsert 或独立 Task。

### State 保存事实，而不是所有局部变量

可以重新计算的临时值通常没必要进入 State。长期跨 Thread 数据使用 [Store](/oss/langgraph/stores)，外部业务权威数据仍留在数据库。
