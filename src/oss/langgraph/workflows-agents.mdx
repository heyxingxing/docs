LangGraph 可以同时构建**工作流（Workflow）**和**智能体（Agent）**，但二者在控制流上有一个关键区别：

- **工作流**拥有预先定义好的代码路径，LLM 和工具会按照固定结构执行。
- **智能体**的控制流是动态的：模型根据当前上下文决定下一步做什么、调用什么工具、什么时候结束。

现实系统通常会混合两者：关键业务约束由确定性工作流控制，而信息检索、规划、工具选择等步骤交给 Agent 动态决策。

## 配置模型

下面的示例使用 LangChain 的统一模型接口。你可以替换为自己使用的 Provider。

:::python
```python
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-5.4-mini")
```
:::

:::js
```typescript
import { initChatModel } from "langchain/chat_models/universal";

const model = await initChatModel("openai:gpt-5.4-mini");
```
:::

如果模型需要结构化决策，可以使用 Structured Output，而不是让程序解析自然语言。

## Prompt Chaining

**Prompt Chaining** 将一个任务拆成多个顺序执行的 LLM 调用，每一步都处理上一步的结果。

这种模式适合：

- 一个复杂任务可以自然拆成若干阶段；
- 希望每一步都能独立检查、重试或评估；
- 希望在不同阶段使用不同 Prompt 或模型。

例如：先生成内容，再判断其质量，最后根据判断决定继续还是终止。

```text
输入
 ↓
LLM 1：生成草稿
 ↓
质量检查
 ├─ 通过 → LLM 2：润色 → END
 └─ 不通过 → END / 重写
```

:::python
```python
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    topic: str
    draft: str
    final: str


def generate(state: State):
    response = model.invoke(f"Write a short draft about {state['topic']}")
    return {"draft": response.content}


def improve(state: State):
    response = model.invoke(
        f"Improve the following draft and make it concise:\n\n{state['draft']}"
    )
    return {"final": response.content}

builder = StateGraph(State)
builder.add_node("generate", generate)
builder.add_node("improve", improve)
builder.add_edge(START, "generate")
builder.add_edge("generate", "improve")
builder.add_edge("improve", END)

graph = builder.compile()
```
:::

:::js
```typescript
import * as z from "zod";
import { StateGraph, StateSchema, START, END } from "@langchain/langgraph";

const State = new StateSchema({
  topic: z.string(),
  draft: z.string().optional(),
  final: z.string().optional(),
});

const generate = async (state: typeof State.State) => ({
  draft: (await model.invoke(`Write a short draft about ${state.topic}`)).content,
});

const improve = async (state: typeof State.State) => ({
  final: (await model.invoke(
    `Improve the following draft and make it concise:\n\n${state.draft}`
  )).content,
});

const graph = new StateGraph(State)
  .addNode("generate", generate)
  .addNode("improve", improve)
  .addEdge(START, "generate")
  .addEdge("generate", "improve")
  .addEdge("improve", END)
  .compile();
```
:::

Prompt Chaining 的优势是控制流清晰、易调试；代价是灵活性较低，每一步都必须按预定义路径执行。

## 并行化（Parallelization）

如果多个步骤彼此独立，可以让它们在同一个 Super-step 中并行执行，再汇总结果。

常见模式有两类：

1. **Sectioning**：把任务拆成互相独立的子任务，并行处理。
2. **Voting / Ensemble**：让多个模型或 Prompt 独立完成同一任务，再聚合答案。

```text
                 ┌→ 分支 A ─┐
输入 → Fan-out ──┼→ 分支 B ─┼→ 聚合 → END
                 └→ 分支 C ─┘
```

:::python
```python
from operator import add
from typing import Annotated
from typing_extensions import TypedDict

class State(TypedDict):
    topic: str
    outputs: Annotated[list[str], add]


def joke(state: State):
    return {"outputs": [model.invoke(f"Write a joke about {state['topic']}").content]}


def story(state: State):
    return {"outputs": [model.invoke(f"Write a story about {state['topic']}").content]}


def poem(state: State):
    return {"outputs": [model.invoke(f"Write a poem about {state['topic']}").content]}

builder = StateGraph(State)
builder.add_node("joke", joke)
builder.add_node("story", story)
builder.add_node("poem", poem)
builder.add_node("aggregate", lambda state: {})

builder.add_edge(START, "joke")
builder.add_edge(START, "story")
builder.add_edge(START, "poem")
builder.add_edge("joke", "aggregate")
builder.add_edge("story", "aggregate")
builder.add_edge("poem", "aggregate")
builder.add_edge("aggregate", END)
```
:::

并行分支可能同时写同一个 State Key，因此该字段通常需要 [Reducer](/oss/langgraph/graph-api#reducers) 来定义合并语义。

## 路由（Routing）

**Routing** 让一个步骤根据输入内容选择后续的专用路径。

例如一个客服系统可以把请求分为退款、技术支持和一般咨询，再交给不同处理节点。

```text
                 ┌→ 技术支持
输入 → 分类器 ────┼→ 退款处理
                 └→ 一般咨询
```

推荐让分类模型返回结构化输出，使 Routing 可验证，而不是依赖脆弱的字符串匹配。

:::python
```python
from typing import Literal
from pydantic import BaseModel, Field

class Route(BaseModel):
    step: Literal["technical", "billing", "general"] = Field(
        description="The next step in the workflow"
    )

router = model.with_structured_output(Route)


def route_request(state):
    decision = router.invoke(state["input"])
    return decision.step

builder.add_conditional_edges(
    "router",
    route_request,
    {
        "technical": "technical_support",
        "billing": "billing_support",
        "general": "general_support",
    },
)
```
:::

如果路由步骤还需要同时更新 State，可以让 Node 返回 [`Command`](/oss/langgraph/graph-api#command)，把 `update` 和 `goto` 放在同一个操作中。

## Orchestrator-Worker

当任务需要动态拆分，而且事先不知道应该创建多少个子任务时，可以使用 **Orchestrator-Worker** 模式。

Orchestrator 负责：

1. 理解目标；
2. 动态生成子任务；
3. 把子任务分发给 Worker；
4. 汇总 Worker 结果。

```text
                 ┌→ Worker 1 ─┐
输入 → Orchestrator ─→ Worker 2 ─┼→ Synthesizer → END
                 └→ Worker N ─┘
```

这与固定并行化不同：Worker 的数量和输入由 Runtime 决定。

LangGraph 通过 [`Send`](/oss/langgraph/graph-api#send) 支持动态 Fan-out。

:::python
```python
from operator import add
from typing import Annotated
from langgraph.types import Send

class State(TypedDict):
    topic: str
    sections: list[str]
    completed_sections: Annotated[list[str], add]
    final_report: str


def orchestrator(state: State):
    plan = planner.invoke(
        f"Break this report topic into sections: {state['topic']}"
    )
    return {"sections": plan.sections}


def assign_workers(state: State):
    return [
        Send("worker", {"section": section})
        for section in state["sections"]
    ]


def worker(state):
    result = model.invoke(f"Write section: {state['section']}")
    return {"completed_sections": [result.content]}


def synthesize(state: State):
    return {"final_report": "\n\n".join(state["completed_sections"])}

builder.add_conditional_edges("orchestrator", assign_workers, ["worker"])
```
:::

Worker 并行写入的结果字段通常使用累加 Reducer。对于研究、报告生成、代码库分析、多文档处理等动态任务，这是一种常见模式。

## Evaluator-Optimizer

**Evaluator-Optimizer** 模式让一个 LLM 生成结果，另一个步骤对结果进行评价；如果不满足标准，就把反馈送回生成器继续迭代。

```text
输入 → Generator → Evaluator
                  ├─ ACCEPT → END
                  └─ REVISE → Generator → ...
```

它适合以下场景：

- 存在明确的质量标准；
- LLM 可以根据反馈显著改进答案；
- 可以接受多次模型调用带来的额外延迟和成本。

:::python
```python
from typing import Literal
from pydantic import BaseModel

class Evaluation(BaseModel):
    grade: Literal["pass", "fail"]
    feedback: str

critic = model.with_structured_output(Evaluation)


def generate(state):
    prompt = f"Write an answer about {state['topic']}"
    if state.get("feedback"):
        prompt += f"\nImprove it using this feedback: {state['feedback']}"
    return {"answer": model.invoke(prompt).content}


def evaluate(state):
    result = critic.invoke(
        f"Evaluate this answer:\n{state['answer']}"
    )
    return {"grade": result.grade, "feedback": result.feedback}


def route(state):
    return END if state["grade"] == "pass" else "generate"

builder.add_conditional_edges("evaluate", route, ["generate", END])
```
:::

需要为循环设置明确的终止条件，例如最大迭代次数、质量阈值或 [Recursion Limit](/oss/langgraph/graph-api#recursion-limit)，避免无限循环。

## 智能体（Agents）

工作流的控制路径由开发者决定，而智能体允许 LLM 自主决定下一步行动。

最常见的是 **Tool-calling Agent Loop**：

```text
用户输入
   ↓
  LLM
   ↓
是否调用工具？
 ├─ 是 → Tool → Observation ─┐
 │                           │
 └─ 否 → 最终回答            │
             ↑               │
             └───────────────┘
```

模型在每一轮决定：

- 是否调用工具；
- 调用哪个工具；
- 传什么参数；
- 根据 Tool Result 是否继续；
- 什么时候输出最终答案。

如果只需要标准 Tool-calling Agent，LangChain 的 [`create_agent`](/oss/langchain/agents) 已经提供了基于 LangGraph 构建的高层实现。只有在需要自定义控制流、额外审批、复杂 State 或非标准执行架构时，才需要直接使用 LangGraph 实现 Loop。

### 从零构建一个 Tool-calling Agent

:::python
```python
from langchain.tools import tool
from langgraph.graph import MessagesState, StateGraph, START, END
from langgraph.prebuilt import ToolNode

@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers."""
    return a * b

tools = [multiply]
model_with_tools = model.bind_tools(tools)


def call_model(state: MessagesState):
    response = model_with_tools.invoke(state["messages"])
    return {"messages": [response]}


def should_continue(state: MessagesState):
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "tools"
    return END

builder = StateGraph(MessagesState)
builder.add_node("model", call_model)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "model")
builder.add_conditional_edges("model", should_continue, ["tools", END])
builder.add_edge("tools", "model")

agent = builder.compile()
```
:::

:::js
```typescript
import * as z from "zod";
import { tool } from "@langchain/core/tools";
import {
  StateGraph,
  StateSchema,
  MessagesValue,
  START,
  END,
} from "@langchain/langgraph";
import { ToolNode } from "@langchain/langgraph/prebuilt";

const multiply = tool(
  async ({ a, b }) => a * b,
  {
    name: "multiply",
    description: "Multiply two integers",
    schema: z.object({ a: z.number(), b: z.number() }),
  }
);

const tools = [multiply];
const modelWithTools = model.bindTools(tools);

const State = new StateSchema({ messages: MessagesValue });

const callModel = async (state: typeof State.State) => ({
  messages: [await modelWithTools.invoke(state.messages)],
});

const shouldContinue = (state: typeof State.State) => {
  const last = state.messages.at(-1);
  return last?.tool_calls?.length ? "tools" : END;
};

const agent = new StateGraph(State)
  .addNode("model", callModel)
  .addNode("tools", new ToolNode(tools))
  .addEdge(START, "model")
  .addConditionalEdges("model", shouldContinue, ["tools", END])
  .addEdge("tools", "model")
  .compile();
```
:::

### 为什么智能体需要 LangGraph Runtime

一个简单的 `while tool_calls:` 循环就能实现最小 Agent，但真实应用通常还需要：

- **Checkpoint**：长任务失败后从中间恢复；
- **Interrupt**：高风险 Tool 调用前等待人工审批；
- **Streaming**：实时输出 Token、State 和 Tool Progress；
- **Memory**：跨 Turn / Thread 保存信息；
- **Retry / Timeout**：处理外部 API 与模型故障；
- **Subgraph**：拆分多智能体系统；
- **Observability**：查看每一步为什么发生。

LangGraph 的价值主要就在这些 Runtime Primitive，而不是替模型增加推理能力。

## 如何选择模式

| 场景 | 推荐模式 |
| --- | --- |
| 固定多阶段处理 | Prompt Chaining |
| 多个互不依赖的子任务 | Parallelization |
| 根据输入选择专用路径 | Routing |
| 动态生成数量未知的子任务 | Orchestrator-Worker |
| 根据反馈循环改进 | Evaluator-Optimizer |
| 下一步由模型动态决定 | Agent |

这些模式并不互斥。生产系统往往会把它们组合起来，例如：

```text
确定性 Router
   ↓
Orchestrator
   ↓
多个 Agent Worker
   ↓
Evaluator
   ↓
人工审批
   ↓
确定性执行
```
