**子图（Subgraph）**允许你把一个完整的 LangGraph 图嵌入另一个图。它是实现模块化设计、多智能体系统、复杂工作流拆分和局部持久化的重要机制。

典型场景包括：

- 多智能体系统：每个 Agent 可以拥有自己的独立 Subgraph。
- 大型 Workflow：把不同业务阶段拆成可独立理解、测试和复用的图。
- 不同团队维护不同模块，再通过 Parent Graph 组合。
- 希望为某一部分流程设置独立的 State、Checkpointer 或执行边界。

## 添加子图

最常见的两种方式是：

1. **把已编译 Subgraph 直接添加为 Node**。适合 Parent Graph 与 Subgraph 共享 State Key 的场景。
2. **在普通 Node 函数里调用 Subgraph**。适合两边 State Schema 不同，需要在调用前后做数据转换的场景。

Parent Node 的职责是：

1. 从 Parent State 取出 Subgraph 所需数据。
2. 转换成 Subgraph Input。
3. 调用 Subgraph。
4. 把 Subgraph Output 转换回 Parent State Update。

这种模式让两个图的内部表示保持解耦。

<Warning>
如果 Subgraph 内触发 `interrupt()`，Resume 时 Parent Node 会从函数开头重新执行，然后 Subgraph 中触发 Interrupt 的 Node 也会从开头重新执行。Interrupt 之前的副作用必须具备幂等性。参阅[中断与子图](/oss/langgraph/interrupts#与以函数方式调用的-subgraph-配合)。
</Warning>

## 子图持久化

Subgraph 的 Checkpointer 配置决定它如何保存状态。常见模式有三种：

| 模式 | 配置 | 语义 |
| --- | --- | --- |
| 默认继承 | `subgraph.compile()` | 继承 Parent Graph 的 Checkpointer；最常用。 |
| 独立 State History | `subgraph.compile(checkpointer=True)` | Subgraph 拥有独立 Checkpoint Namespace 和内部历史。 |
| Stateless | `subgraph.compile(checkpointer=False)` | 不持久化 Subgraph State。 |

### 默认：继承 Parent Checkpointer

通常**不要**在 Subgraph 编译时显式传 Checkpointer。当 Parent Graph 使用 Checkpointer 编译后，Runtime 会自动把它传播给 Subgraph。

:::python
```python
subgraph = subgraph_builder.compile()
parent = parent_builder.add_node("subgraph", subgraph).compile(
    checkpointer=checkpointer
)
```
:::

:::js
```typescript
const subgraph = subgraphBuilder.compile();
const parent = parentBuilder
  .addNode("subgraph", subgraph)
  .compile({ checkpointer });
```
:::

这样 Parent 和 Subgraph 使用同一持久化后端，但 Runtime 会通过 `checkpoint_ns` 区分不同 Graph Scope。

### Per-invocation：继承 Parent Checkpointer

默认模式下，每次 Subgraph Invocation 的内部状态只属于这一次调用。对于大多数独立工作流，这是最安全的设置。

### Per-thread：`checkpointer=True`

如果希望同一个 Subgraph 在同一 Thread 的多次 Invocation 之间保留自己的内部 State，可以在 Subgraph 上设置独立 Checkpointer Namespace：

:::python
```python
subgraph = subgraph_builder.compile(checkpointer=True)
```
:::

:::js
```typescript
const subgraph = subgraphBuilder.compile({ checkpointer: true });
```
:::

这适合“Subgraph 本身就是一个长期 Agent”的场景。例如多智能体系统中，每个 Agent 需要跨多轮 Handoff 保留独立 Memory。

<Warning>
如果同一个持久化 Subgraph 在一个 Super-step 中被并行调用多次，并且这些调用共享相同 Namespace，就会发生 Checkpoint 冲突。对于并行 Fan-out，应让每次 Invocation 使用独立 Scope，或使用默认的 Per-invocation 模式。
</Warning>

### Stateless：`checkpointer=False`

如果 Subgraph 的中间 State 不需要保存，可以显式关闭它的 Checkpoint：

:::python
```python
subgraph = subgraph_builder.compile(checkpointer=False)
```
:::

:::js
```typescript
const subgraph = subgraphBuilder.compile({ checkpointer: false });
```
:::

这样 Parent 仍然可以 Checkpoint，但 Subgraph 内部 Step 不会产生可恢复历史。

## 查看子图 State

当图在 Subgraph 内暂停时，可以通过 `get_state(..., subgraphs=True)` / `getState(..., { subgraphs: true })` 查看嵌套 State。

:::python
```python
state = graph.get_state(config, subgraphs=True)
print(state.tasks)
```
:::

:::js
```typescript
const state = await graph.getState(config, { subgraphs: true });
console.log(state.tasks);
```
:::

Parent `StateSnapshot.tasks` 中的 Task 会携带 Subgraph State Snapshot，因此可以逐层检查嵌套执行状态。

<Warning>
只有当 Subgraph **当前处于活跃 / 暂停状态**时，才能通过 Parent `get_state(..., subgraphs=True)` 读取它的内部 State。Subgraph 完成后，如果要回看它的历史，应使用其 Checkpoint Config 或时间旅行 API。
</Warning>

### 修改 Subgraph State

如果 Subgraph 暂停在 Interrupt，可以获取其内部 Config，再调用 `update_state`：

:::python
```python
parent_state = graph.get_state(config, subgraphs=True)
subgraph_config = parent_state.tasks[0].state.config

graph.update_state(
    subgraph_config,
    {"some_key": "new value"},
)
```
:::

:::js
```typescript
const parentState = await graph.getState(config, { subgraphs: true });
const subgraphConfig = parentState.tasks[0].state.config;

await graph.updateState(
  subgraphConfig,
  { someKey: "new value" },
);
```
:::

## 从子图跳转到 Parent Graph

Subgraph Node 可以返回 @[`Command`] 并指定 `graph=Command.PARENT`，从当前 Subgraph 直接路由到 Parent Graph 的 Node。

:::python
```python
from langgraph.types import Command
from typing import Literal

def subgraph_node(state: SubgraphState) -> Command[Literal["parent_node"]]:
    return Command(
        update={"foo": "bar"},
        goto="parent_node",
        graph=Command.PARENT,
    )
```
:::

:::js
```typescript
return new Command({
  update: { foo: "bar" },
  goto: "parentNode",
  graph: Command.PARENT,
});
```
:::

如果 Update 修改 Parent 和 Subgraph 共用的 State Key，请确保 Parent Graph 对应 Key 定义了正确的 [Reducer](/oss/langgraph/graph-api#reducers)。否则并行或多路 Handoff 可能覆盖彼此的值。

这种模式常用于[多智能体 Handoff](/oss/langchain/multi-agent/handoffs)。

在 Python Streaming v2 中，每个 StreamPart 都包含 `ns`：

```python

    inputs,
    subgraphs=True,
    stream_mode="updates",
    version="v2",

```

空 Namespace `()` 表示根图；Subgraph Event 则会携带类似 `("node_name:<runtime-id>",)` 的 Namespace。

对于更高层的类型化 API，可以使用 [Event Streaming](/oss/langgraph/event-streaming) 的 `stream.subgraphs` Projection。

## Subgraph 与 Memory

要理解 Subgraph Memory，区分两种持久化非常重要：

- **Checkpointer**：保存当前 Thread 中 Graph / Subgraph 的执行 State，属于短期记忆。
- **Store**：保存跨 Thread 的任意数据，属于长期记忆。

一个 Per-thread Subgraph 可以拥有自己的短期 State；多个 Agent 仍可以通过同一个 [Store](/oss/langgraph/stores) 共享长期 Memory。

例如，多智能体系统可以这样设计：

```text
Parent Orchestrator
├── Research Agent Subgraph   -> 独立 Checkpoint State
├── Coding Agent Subgraph     -> 独立 Checkpoint State
└── Shared Store              -> 用户偏好 / 跨 Agent 知识
```

## Subgraph 与 Interrupt

如果 Subgraph 直接作为 Node 添加，Interrupt 会自然向 Parent Graph 暴露。Resume 时使用同一个 Parent `thread_id` 即可继续。

如果 Subgraph 是在 Parent Node 函数内部调用的，则 Resume 时 Parent Node 会从开头重新执行，然后重新进入 Subgraph。参阅[Interrupt 使用规则](/oss/langgraph/interrupts#与以函数方式调用的-subgraph-配合)。

## Subgraph 与时间旅行

时间旅行粒度取决于 Subgraph Checkpointer：

- **默认继承 Parent Checkpointer**：Parent 把整个 Subgraph Invocation 视作一个 Super-step，因此只能从 Subgraph 之前 / 之后的 Parent Checkpoint 时间旅行。
- **`checkpointer=True`**：Subgraph 拥有独立 Checkpoint History，因此可以从 Subgraph 内部两个 Node 之间 Fork / Replay。

完整示例参阅[时间旅行中的子图](/oss/langgraph/use-time-travel#子图)。

## 动态调用多个 Subgraph

当你需要根据 Runtime Data 选择 Subgraph，可以在 Node 中动态调用：

:::python
```python
async def router_node(state: ParentState):
    if state["task_type"] == "research":
        result = await research_graph.ainvoke({"query": state["input"]})
    else:
        result = await coding_graph.ainvoke({"task": state["input"]})
    return {"result": result}
```
:::

:::js
```typescript
const routerNode = async (state: ParentState) => {
  const result = state.taskType === "research"
    ? await researchGraph.invoke({ query: state.input })
    : await codingGraph.invoke({ task: state.input });
  return { result };
};
```
:::

如果要并行执行动态数量的相同 Worker，更推荐结合 @[`Send`](/oss/langgraph/graph-api#send) 构造 Fan-out，而不是在一个 Node 内手动串行调用。

## 复用同一个 Subgraph

同一个已编译 Subgraph 可以被多个 Parent Graph 复用。需要注意的是：

- State Schema 要与每个 Parent 的连接方式兼容。
- 如果 Subgraph 使用 `checkpointer=True`，要理解它的 Namespace / Thread State 是否应该跨 Parent 共享。
- Subgraph 内依赖的 Runtime Context / Store 需要由调用它的 Parent Runtime 提供。

## 多智能体场景

子图是实现多智能体系统的自然原语。每个 Agent 可以拥有：

- 自己的 System Prompt；
- 自己的 Tool 集合；
- 自己的 State Schema；
- 自己的短期 Checkpoint State；
- 与其他 Agent 共享的长期 Store。

Parent Graph 负责路由、Handoff 和全局协调。对于更高层的多智能体模式，参阅 [LangChain Multi-agent](/oss/langchain/multi-agent)。

## 调试子图

调试时建议组合以下能力：

- `graph.get_state(config, subgraphs=True)`：检查当前嵌套 State。
- `stream(..., subgraphs=True)`：实时观察 Subgraph Update。
- [LangSmith](/langsmith/observability)：查看 Parent / Subgraph Trace Tree。
- [时间旅行](/oss/langgraph/use-time-travel)：从某个 Parent 或 Subgraph Checkpoint Replay / Fork。
- [Studio](/oss/langgraph/studio)：可视化整个 Graph / Subgraph 执行。

## 总结

选择 Subgraph 集成方式时，可以使用下面的判断：

| 需求 | 推荐方式 |
| --- | --- |
| Parent 与 Subgraph 共享 State Key | 直接把编译 Subgraph 添加为 Node |
| State Schema 不同 | 在 Parent Node 中手动调用并转换输入 / 输出 |
| Subgraph 每次调用彼此独立 | 默认继承 Parent Checkpointer |
| Subgraph 是长期 Agent，需要跨 Invocation 保留内部状态 | `checkpointer=True` |
| Subgraph 中间状态无需持久化 | `checkpointer=False` |
| 需要观察嵌套 Streaming | `subgraphs=True` |
| 需要从 Subgraph 跳转到 Parent | `Command(graph=Command.PARENT, ...)` |
