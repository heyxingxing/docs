description: 在生产环境中更新 LangGraph 图代码，同时不破坏正在执行中的 Run。
---

生产环境中的软件必然需要变化。新需求、Bug 修复和重构最终都会进入你的图代码。由于 LangGraph 会使用最新部署的图，去处理已有线程已经[持久化](/oss/langgraph/persistence)的状态，因此从现有 Checkpoint 的角度看，你发布的每一次变更，本质上都相当于一次需要保持向后兼容的 API 变更。

与那些将一个 Run 固定在启动时所用代码版本上的工作流引擎不同，LangGraph 会立即把最新版本的图应用到**所有**线程上，无论是新线程，还是从 Checkpoint 恢复的旧线程。这很方便：Bug 修复可以直接传播到正在进行的对话和智能体，而无需额外迁移流程。但这也意味着，你必须认真考虑每一次代码变更会如何影响那些在旧版本代码下启动的 Run。

需要关注的兼容性问题大致分为三类，通常也会按以下顺序遇到：

1. [技术兼容性](#technical-compatibility)：最常见。新代码必须仍然能够加载并基于已有 State 执行。
2. [业务兼容性](#business-compatibility)：相对少见。即使代码发生变化，已有 Run 仍应继续遵循旧版业务逻辑。
3. [非确定性](#non-determinism)：仅适用于 [Functional API](/oss/langgraph/functional-api)。

<Tip>
如需快速了解运行时默认支持哪些图拓扑和状态变更，请参阅[图迁移](/oss/langgraph/graph-api#graph-migrations)。本页其余部分介绍当变更超出默认支持范围时，可以采用哪些兼容模式。
</Tip>

## 技术兼容性

技术兼容性类似于微服务中的 API Breaking Change。这里的“API”是图代码与 [Checkpointer](/oss/langgraph/checkpointers#checkpointer-libraries) 已经为现有线程持久化的数据之间的契约。当线程恢复时，LangGraph 会反序列化已保存的状态，根据节点名称把状态分发给相应节点，并期望节点返回符合 State Schema 的值。

常见的技术性破坏包括：

- **重命名或删除节点**，而仍有线程暂停在该节点、或即将进入该节点。例如线程可能停在 @[`interrupt`] 上，或者某个已经 Checkpoint 的条件边仍然会路由到旧节点名。恢复时，LangGraph 无法通过保存的节点名找到对应节点，Run 就会失败。Run 恢复时会从停止执行的节点函数开头重新开始，因此如果节点已经不存在，也就无处可恢复。
- **重命名或删除 State Key**，而旧 Checkpoint 中仍保存这些 Key，或者下游节点仍然会读取它们。
- **收紧 State 字段约束**，例如把 `Optional` 字段改为必填字段、缩窄类型，或者添加没有默认值的新必填字段。旧 Checkpoint 将无法满足新的 Schema。

边的拓扑结构本身**不会**保存到 Checkpoint 中。只要相关节点仍然存在，新增、删除或重新路由节点之间的边，对正在执行的线程而言通常都是安全的。正如[图迁移](/oss/langgraph/graph-api#graph-migrations)中总结的那样，唯一可能破坏已中断线程的拓扑变更，就是重命名或删除节点。

### 推荐模式

:::python

- 将新的 State 字段定义为 `NotRequired`（或 `Optional[...] = None`），这样旧 Checkpoint 仍然能够通过校验：

  ```python
  from typing import NotRequired
  from typing_extensions import TypedDict

  class State(TypedDict):
      messages: list
      summary: NotRequired[str]  # [!code ++]
  ```

- 将字段删除视为“弃用”而不是立刻移除。即使已经没有节点读取该字段，也应至少保留一个旧 Run 排空周期，确保已有 Checkpoint 仍然能够加载。
- 重命名时采用**先新增、后删除**的方式。先让新字段或新节点与旧版本共存，在一段弃用窗口内双写或同时路由到二者；确认不再有正在执行的线程依赖旧版本后，再将其删除。
- 让节点函数能够容忍未知 Key。`TypedDict` 在运行时会忽略额外 Key，因此来自旧版本代码的遗留状态本身不会报错，除非节点显式读取了一个缺失的 Key。
- 在正式发布前，可以在 Staging 部署中使用[时间旅行](/oss/langgraph/use-time-travel)和 @[`graph.get_state`][get_state]，抽查已有线程在新代码下是否正常工作。

:::

:::js

- 将新的 State 字段标记为可选（`z.string().optional()` 或 `.nullish()`），这样旧 Checkpoint 仍然可以通过校验。
- 将删除操作视为弃用：至少保留一个旧 Run 排空周期，让已有 Checkpoint 能够继续加载。
- 重命名时采用先新增、后删除：让新字段或新节点和旧版本共存，在弃用窗口中双写或同时路由，等所有正在执行的线程都不再依赖旧版本后再删除旧版本。
- 在正式发布前，可以在 Staging 部署中使用[时间旅行](/oss/langgraph/use-time-travel)和 @[`graph.getState`][get_state] 抽查已有线程在新代码下的行为。

:::

### 检测正在执行中的线程

在删除节点、重命名 State Key，或进行其他旧线程无法容忍的变更之前，你通常需要先知道，是否仍有线程停留在即将被移除的代码版本上。LangGraph 本身不会为线程状态维护一个可搜索索引，因此具体做法取决于图运行在哪里。

**如果部署在 [LangSmith](/langsmith/deployment) 上。** 可以使用 Agent Server 的 Thread Search 按状态筛选线程。`status` 字段支持 `idle`、`busy`、`interrupted` 和 `error`，因此你可以批量查询 `interrupted` 或 `busy` 线程，也可以结合 Metadata 进一步缩小范围。参阅[按线程状态过滤](/langsmith/use-threads#filter-by-thread-status)和[列出线程](/langsmith/use-threads#list-threads)。

**无论 LangGraph 部署在哪里。** 都可以使用 [LangSmith Tracing](/oss/langgraph/observability) 监控生产环境中哪些节点正在被进入和退出。这通常是判断某个节点或 State 字段是否已经不再出现在任何活跃执行路径上的最可靠信号。

**如果你已经有 `thread_id`。** 可以直接检查单个线程：

:::python

- @[`graph.get_state(config)`][get_state] 返回最新 Checkpoint，其中包括线程当前暂停在哪个节点，以及是否存在待处理的 Interrupt。
- @[`graph.get_state_history(config)`][get_state_history] 返回该线程完整的 Checkpoint 时间序列。

:::

:::js

- @[`graph.getState(config)`][get_state] 返回最新 Checkpoint，其中包括线程当前暂停在哪个节点，以及是否存在待处理的 Interrupt。
- @[`graph.getStateHistory(config)`][get_state_history] 返回该线程完整的 Checkpoint 时间序列。

:::

如果无法确定，最稳妥的做法是继续保留已弃用的节点或字段，直到 Agent Server 的线程列表和 Tracing 都显示不再有相关活动。

## 业务兼容性

有些变更在技术上完全有效——所有已有 Checkpoint 都能正常加载、所有节点都仍能解析——但新版图的**业务语义**已经与旧版不同。新行为对于新线程是正确的，但你并不希望把它追溯应用到那些在旧逻辑下启动的线程。

例如，假设原图执行流程是 `intake → triage → respond`，现在你决定在 `triage` 和 `respond` 之间加入一个新的 `policy_check` 步骤：

- 已经通过 `triage` 的线程应继续直接进入 `respond`，保持旧流程。
- 新线程则应该执行完整的新流程。

推荐做法是在 Thread 启动时，将相关的**行为版本号**记录到 State 中，然后使用[条件边](/oss/langgraph/graph-api#conditional-edges)根据版本进行分支：

:::python

```python
from typing import NotRequired
from typing_extensions import TypedDict

from langgraph.graph import END, START, StateGraph


class State(TypedDict):
    request: str
    flow_version: NotRequired[int]
    response: NotRequired[str]


def intake(state: State) -> dict:
    # Stamp new threads with the current flow version. Existing threads
    # that resume past `intake` keep whatever value was already saved.
    return {"flow_version": state.get("flow_version", 2)}


def triage(state: State) -> dict: ...
def policy_check(state: State) -> dict: ...
def respond(state: State) -> dict: ...


def after_triage(state: State) -> str:
    if state.get("flow_version", 1) >= 2:
        return "policy_check"
    return "respond"


builder = StateGraph(State)
builder.add_node("intake", intake)
builder.add_node("triage", triage)
builder.add_node("policy_check", policy_check)
builder.add_node("respond", respond)
builder.add_edge(START, "intake")
builder.add_edge("intake", "triage")
builder.add_conditional_edges("triage", after_triage, ["policy_check", "respond"])
builder.add_edge("policy_check", "respond")
builder.add_edge("respond", END)

graph = builder.compile()
```

:::

旧线程如果在 `triage` 之后恢复，会从已保存的状态中读取 `flow_version`（如果没有该字段，则回退到 v1 默认值），因此会跳过 `policy_check`。新线程从 `intake` 开始，会被写入 `flow_version=2`，从而执行新路径。等所有 v1 线程都执行完毕后，就可以删除版本标记和这条条件边。

这个模式只有在版本号**在线程开始时就写入 State** 才有效，也就是必须早于任何需要版本分流的分支。如果到后面才设置版本号，那么旧线程真正需要使用这个字段时，它可能仍然不存在。

## 非确定性

这一类问题只适用于 [Functional API](/oss/langgraph/functional-api)，以及 [Graph API](/oss/langgraph/graph-api) **节点内部**的 [Task](/oss/langgraph/functional-api#task) 或 @[`interrupt`] 调用。普通 Graph API **节点**在恢复时会[从节点函数开头重新执行](/oss/langgraph/graph-api#re-execution-and-idempotency)；因此你需要让副作用具备幂等性，但除非该节点内部使用了 **Task** 或 @[`interrupt`]，否则并不需要保持 Task 调用顺序。

Functional API 的 **Entrypoint** 会编译成单个**节点**。当一个 Run 恢复时，Entrypoint 函数体会从头重放，并利用已经缓存的 @[`@task`][task] 结果跳过之前已经完成的工作。以下两类变更会破坏这种重放模型：

- **在恢复点之前新增、删除或重新排序 `@task` 调用或 @[`interrupt`] 调用。** LangGraph 会根据这些调用在重放中的位置，将缓存结果和 Resume Value 与对应调用匹配；如果位置发生变化，就可能把错误的缓存值重放给另一个调用。
- **在 `@task` 外部引入非确定性操作**，例如直接在 Entrypoint 函数体中调用 `time.time()`、`random.random()` 或执行网络请求。重放时，这些操作可能产生与第一次运行不同的值，从而改变控制流。

更多示例和深入解释，请参阅 Functional API 指南中的[确定性](/oss/langgraph/functional-api#determinism)和[常见陷阱](/oss/langgraph/functional-api#common-pitfalls)。

如果需要对仍有正在执行 Run 的 `@entrypoint` 做较大代码修改，最稳妥的选择包括：

- 等待正在执行中的 Run 全部完成，再部署变更。
- 将新增逻辑封装到新的 `@task` 中，使其结果可以独立 Checkpoint。
- 在 `langgraph.json` 中以新的 Graph Name 注册一个新的 Entrypoint 来承载新版行为，并将新线程路由到它。
