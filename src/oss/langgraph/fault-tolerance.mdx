LangGraph 提供了构建可靠智能体所需的一组容错原语：**Retry、Timeout、Error Handler、Checkpoint、Graceful Shutdown**。这些机制分别解决瞬时失败、卡死调用、补偿逻辑、恢复执行和进程优雅退出等问题，并且可以组合使用。

## Retry Policy

对于可能出现瞬时错误的 Node，可以配置 @[`RetryPolicy`]。失败后，LangGraph 会根据 Policy 判断是否重试、最多重试几次，以及等待多久。

:::python
```python
from langgraph.graph import StateGraph, START
from langgraph.types import RetryPolicy

builder = StateGraph(State)
builder.add_node(
    "call_api",
    call_api,
    retry_policy=RetryPolicy(
        max_attempts=3,
        initial_interval=1.0,
        backoff_factor=2.0,
        max_interval=10.0,
        jitter=True,
    ),
)
builder.add_edge(START, "call_api")
graph = builder.compile()
```
:::

:::js
```typescript
const graph = new StateGraph(State)
  .addNode("callApi", callApi, {
    retryPolicy: {
      maxAttempts: 3,
      initialInterval: 1000,
      backoffFactor: 2,
      maxInterval: 10000,
      jitter: true,
    },
  })
  .addEdge(START, "callApi")
  .compile();
```
:::

`retry_on` / `retryOn` 可以进一步控制哪些 Error 应重试。例如，只对 `ConnectionError`、Rate Limit 等瞬时错误重试，而不要自动重试参数错误和永久性业务错误。

:::python
```python
retry_policy = RetryPolicy(
    max_attempts=3,
    retry_on=ConnectionError,
)
```
:::

:::js
```typescript
retryPolicy: {
  maxAttempts: 3,
  retryOn: (err) => err instanceof ConnectionError,
}
```
:::

### 多个 Retry Policy

Python 可以给一个 Node 提供多个 Retry Policy。LangGraph 会按顺序检查，并使用第一个匹配的 Policy：

```python
builder.add_node(
    "call_api",
    call_api,
    retry_policy=[
        RetryPolicy(max_attempts=5, retry_on=RateLimitError),
        RetryPolicy(max_attempts=3, retry_on=ConnectionError),
    ],
)
```

### Retry 与持久化

当图配置了 Checkpointer 时，Retry 只针对**当前 Node Attempt**。之前已经完成的 Super-step 不会重新执行；同一 Super-step 中已经成功的并行 Node Write 也会通过 [Pending Writes](/oss/langgraph/checkpointers#pending-writes) 保留，因此 Resume 时只需要重新处理失败部分。

## Timeout

:::python
<Note>
需要 `langgraph>=1.2`。Node Timeout 仅支持 Async Node；对 Sync Node 配置 `timeout` 会在编译时被拒绝。
</Note>
:::

:::js
<Note>
需要 `@langchain/langgraph>=1.4.0`。
</Note>
:::

Timeout 用于限制单次 Node Attempt 的最长运行时间。LangGraph 支持两类 Timeout：

- **Run Timeout**：从 Node Attempt 开始起计算的硬上限。
- **Idle Timeout**：如果一段时间内没有可观察到的进展，则认为 Node 卡住。

:::python
```python
from langgraph.types import TimeoutPolicy

builder.add_node(
    "call_model",
    call_model,
    timeout=TimeoutPolicy(
        run_timeout=60,
        idle_timeout=30,
    ),
)
```
:::

:::js
```typescript
const graph = new StateGraph(State)
  .addNode("callModel", callModel, {
    timeout: {
      runTimeout: 60_000,
      idleTimeout: 30_000,
    },
  })
  .compile();
```
:::

### Idle Timeout 与进度信号

Idle Timeout 不是简单的“函数没有返回”。只要 Runtime 观察到有进展，就可以刷新 Idle Timer。可以通过 `refresh_on` / `refreshOn` 选择哪些事件视为活动，也可以在 Node 内手动调用 `runtime.heartbeat()` / `runtime.heartbeat?.()`。

这对于长时间批处理、模型 Streaming 或持续收到外部事件的 Node 很重要：只要 Node 仍在推进，就不应该因为总运行时间很长而被误判为卡死。

:::python
```python
from langgraph.runtime import Runtime
from langgraph.types import TimeoutPolicy

async def long_running_node(state: State, runtime: Runtime):
    async for batch in fetch_batches():
        process(batch)
        runtime.heartbeat()
    return {"result": "done"}

builder.add_node(
    "long_running_node",
    long_running_node,
    timeout=TimeoutPolicy(idle_timeout=30, refresh_on="heartbeat"),
)
```
:::

:::js
```typescript
const longRunningNode = async (state, runtime) => {
  for await (const batch of fetchBatches()) {
    process(batch);
    runtime.heartbeat?.();
  }
  return { result: "done" };
};

builder.addNode("longRunningNode", longRunningNode, {
  timeout: { idleTimeout: 30_000, refreshOn: "heartbeat" },
});
```
:::

`runtime.heartbeat()` 在没有启用 Idle Timeout 时是 No-op，因此可以无条件调用。

### `NodeTimeoutError`

Timeout 触发后，LangGraph 抛出 @[`NodeTimeoutError`]，其中包含具体是哪个限制被触发。

:::python
| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `node` | `str` | 超时 Node 名称 |
| `elapsed` | `float` | 触发 Timeout 前已经运行的秒数 |
| `kind` | `"idle" \| "run"` | 触发的是 Idle 还是 Run Timeout |
| `idle_timeout` | `float \| None` | 配置的 Idle Timeout |
| `run_timeout` | `float \| None` | 配置的 Run Timeout |
:::

:::js
| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `node` | `string` | 超时 Node 名称 |
| `elapsed` | `number` | 已运行毫秒数 |
| `kind` | `"idle" \| "run"` | 超时类型 |
| `timeout` | `number` | 实际触发的 Timeout 值 |
| `idleTimeout` | `number \| undefined` | 配置的 Idle Timeout |
| `runTimeout` | `number \| undefined` | 配置的 Run Timeout |
:::

`NodeTimeoutError` 默认被视为可重试错误。因此 Timeout 可以直接与 Retry Policy 组合：每次新 Attempt 都会重置 Timeout Clock，而超时 Attempt 已缓冲的 Write 会在下一次 Retry 前清除。

:::python
```python
from langgraph.types import RetryPolicy, TimeoutPolicy

builder.add_node(
    "call_model",
    call_model,
    timeout=TimeoutPolicy(idle_timeout=30),
    retry_policy=RetryPolicy(max_attempts=3),
)
```
:::

:::js
```typescript
builder.addNode("callModel", callModel, {
  timeout: { idleTimeout: 30_000 },
  retryPolicy: { maxAttempts: 3 },
});
```
:::

### 使用 `Send` 动态覆盖 Timeout

通过 @[`Send`] 动态 Fan-out 时，可以为某一次 Push 单独指定 Timeout，并覆盖目标 Node 的静态配置：

:::python
```python
from langgraph.types import Send, TimeoutPolicy

def fan_out(state: OverallState):
    return [
        Send(
            "process_item",
            {"item": item},
            timeout=TimeoutPolicy(idle_timeout=15),
        )
        for item in state["items"]
    ]
```
:::

:::js
```typescript
const fanOut = (state) =>
  state.items.map(
    (item) => new Send(
      "processItem",
      { item },
      { timeout: { idleTimeout: 15_000 } }
    )
  );
```
:::

如果 `Send` 没有传 Timeout，则使用目标 Node 在 `add_node` / `addNode` 时配置的默认值。

## Error Handler

:::python
<Note>
需要 `langgraph>=1.2`。
</Note>
:::

:::js
<Note>
需要 `@langchain/langgraph>=1.4.0`。
</Note>
:::

当 Node 失败且 Retry 已全部耗尽后，可以运行 Error Handler。Handler 会接收当前 State，并可以：

- 返回普通 State Update；
- 返回 @[`Command`] 同时更新 State 并跳转到补偿节点；
- 实现 Saga / Compensation Flow，而不是让整个 Graph 立即失败。

:::python
```python
from langgraph.errors import NodeError
from langgraph.types import Command, RetryPolicy
from langgraph.graph import StateGraph, START
from typing_extensions import TypedDict

class State(TypedDict):
    status: str

def charge_payment(state: State) -> State:
    raise RuntimeError("payment gateway timeout")

def payment_error_handler(state: State, error: NodeError) -> Command:
    return Command(
        update={"status": f"compensated: {error.error}"},
        goto="finalize",
    )

def finalize(state: State) -> State:
    return state

graph = (
    StateGraph(State)
    .add_node(
        "charge_payment",
        charge_payment,
        retry_policy=RetryPolicy(max_attempts=3, retry_on=ConnectionError),
        error_handler=payment_error_handler,
    )
    .add_node("finalize", finalize)
    .add_edge(START, "charge_payment")
    .compile()
)
```
:::

:::js
```typescript
const paymentErrorHandler = (state, error: NodeError) =>
  new Command({
    update: { status: `compensated: ${error.error.message}` },
    goto: "finalize",
  });

const graph = new StateGraph(State)
  .addNode("chargePayment", chargePayment, {
    retryPolicy: {
      maxAttempts: 3,
      retryOn: (err) => err instanceof ConnectionError,
    },
    errorHandler: paymentErrorHandler,
  })
  .addNode("finalize", finalize)
  .addEdge(START, "chargePayment")
  .compile();
```
:::

Handler 只有在 Retry Policy 耗尽后才触发；如果没有配置 Retry，则首次失败就进入 Handler。因此“什么时候重试”和“重试失败后如何补偿”是两套解耦策略。

### `NodeError`

Handler 可以通过类型标注请求 `NodeError`：

:::python
```python
from langgraph.errors import NodeError

def my_handler(state: State, error: NodeError) -> Command:
    print(f"Node {error.node} failed with: {error.error}")
    return Command(update={"status": "recovered"}, goto="next_step")
```

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `node` | `str` | 失败 Node 名称 |
| `error` | `BaseException` | 原始异常 |
:::

:::js
```typescript
const myHandler = (state, error: NodeError) => {
  console.log(`Node ${error.node} failed with: ${error.error.message}`);
  return new Command({ update: { status: "recovered" }, goto: "nextStep" });
};
```
:::

如果 Handler 不需要 Error Context，也可以只接收 `state`。

### 使用 `Command` 路由到补偿流程

典型 Saga 模式：库存已预留、支付失败，此时 Error Handler 更新 State 并跳转到 `finalize` / `refund` / `release_inventory` 等补偿节点，而不是让整个 Graph Abort。

Retry 与 Handler 可以独立配置。例如，支付只对 `ConnectionError` 重试三次；如果不是可重试错误，或者三次都失败，则立即进入补偿 Handler。

### Resume-safe Failure

Failure Provenance 也会进入 Checkpoint。如果 Node 已失败，但 Handler 尚未执行完成时进程崩溃或 Graph 被中断，恢复后 Handler 仍会收到相同的 `NodeError` 上下文。

### 与 `interrupt()` 的关系

<Warning>
Node 内的 `interrupt()` **不会**进入 Error Handler。Interrupt 使用 `GraphBubbleUp` 机制暂停 Graph，用于人在回路流程，会绕过 Retry Policy 和 Error Handler。
</Warning>

### Subgraph Failure

如果 Parent Node 调用 Subgraph，而 Subgraph 抛出了未处理异常，该异常会向上冒泡到 Parent Node。如果 Parent Node 配置了 Error Handler，那么 Handler 中的 `error.error` 就是来自 Subgraph 的异常。

## Graph Defaults

:::python
<Note>
需要 `langgraph>=1.2`。
</Note>

如果大量 Node 使用相同的 Retry、Handler、Timeout 或 Cache Policy，可以通过 @[`set_node_defaults`] 配置 Graph-wide Default，而不必在每个 `add_node` 中重复：

```python
from langgraph.errors import NodeError
from langgraph.types import RetryPolicy, TimeoutPolicy


def default_error_handler(state: State, error: NodeError) -> State:
    return {"status": f"handled: {error.error}"}

graph = (
    StateGraph(State)
    .set_node_defaults(
        retry_policy=RetryPolicy(max_attempts=3),
        error_handler=default_error_handler,
        timeout=TimeoutPolicy(run_timeout=30),
    )
    .add_node("step_a", step_a)
    .add_node("step_b", step_b)
    .add_edge(START, "step_a")
    .compile()
)
```
:::

:::js
<Note>
需要 `@langchain/langgraph>=1.4.0`。
</Note>

```typescript
const graph = new StateGraph(State)
  .setNodeDefaults({
    retryPolicy: { maxAttempts: 3 },
    errorHandler: defaultErrorHandler,
    timeout: { runTimeout: 30_000 },
    cachePolicy: { ttl: 60 },
  })
  .addNode("stepA", stepA)
  .addNode("stepB", stepB)
  .addEdge(START, "stepA")
  .compile();
```
:::

### 优先级

Node 自己在 `add_node` / `addNode` 上配置的值永远覆盖 Graph Default。Default 在 `compile()` 时解析，因此 `set_node_defaults` 可以写在添加 Node 之前或之后。

### 默认 Error Handler

当每个 Graph Run 对应一个外部 Process，例如后台任务表的一行，Graph-wide Default Error Handler 特别有价值：所有未处理的 Node Failure 都可以统一把外部 Process 标记为失败，而不必在每个 Node 上重复 Handler。

某些高风险 Node 仍然可以单独覆盖 Default，例如 `charge_payment` 使用退款补偿 Handler，而普通 Node 使用统一的 `mark_process_failed`。

### 适用矩阵

| Default 参数 | 普通 Node | Error-handler Node | 原因 |
| --- | --- | --- | --- |
| `retry_policy` / `retryPolicy` | ✅ | ✅ | Handler 的瞬时失败也可以重试 |
| `timeout` | ✅ | ✅ | 卡死的 Handler 同样需要取消 |
| `error_handler` / `errorHandler` | ✅ | ❌ | Handler 不能捕获自己 |
| `cache_policy` / `cachePolicy` | ✅ | ❌ | 缓存 Handler Result 不安全 |

Graph Default **不会被 Subgraph 继承**。每张图独立维护自己的 Default。

## Functional API

:::python
Functional API 的 `@task` 与 `@entrypoint` 同样支持 Timeout；Task 还支持 Retry Policy：

```python
from langgraph.func import entrypoint, task
from langgraph.types import RetryPolicy, TimeoutPolicy

@task(
    timeout=TimeoutPolicy(idle_timeout=30),
    retry_policy=RetryPolicy(max_attempts=3),
)
async def call_api(url: str) -> str:
    response = await fetch(url)
    return response.text

@entrypoint(timeout=60)
async def my_workflow(inputs: dict) -> str:
    result = await call_api("https://api.example.com/data")
    return result
```
:::

:::js
```typescript
const callApi = task(
  {
    name: "callApi",
    timeout: { idleTimeout: 30_000 },
    retry: { maxAttempts: 3 },
  },
  async (url: string) => {
    const response = await fetch(url);
    return response.text();
  }
);

const myWorkflow = entrypoint(
  { name: "myWorkflow", timeout: 60_000 },
  async (inputs: { url: string }) => await callApi(inputs.url)
);
```

JS / TS 的 `task` / `entrypoint` 目前不提供 Error Handler；需要补偿逻辑时使用 `StateGraph.addNode(..., { errorHandler })`。
:::

## Graceful Shutdown

Cooperative Shutdown 允许外部 Supervisor 请求当前 Run **在当前 Super-step 完成后停止**，并保存一个可恢复 Checkpoint。这非常适合处理 SIGTERM、Pod Eviction 或 Worker 回收：尽量不丢失已经完成的工作。

:::python
<Note>
需要 `langgraph>=1.2`。
</Note>

```python
from langgraph.runtime import RunControl
from langgraph.errors import GraphDrained

control = RunControl()

# From a signal handler or supervisor:
# control.request_drain("sigterm")

try:
    result = graph.invoke(inputs, config, control=control)
except GraphDrained as e:
    print(f"Drained: {e.reason}")
    # Resume later with the same config
```
:::

:::js
<Note>
需要 `@langchain/langgraph>=1.4.0`。
</Note>

```typescript
import { RunControl, GraphDrained } from "@langchain/langgraph";

const control = new RunControl();
// control.requestDrain("sigterm");

try {
  const result = await graph.invoke(inputs, { ...config, control });
} catch (e) {
  if (e instanceof GraphDrained) {
    console.log(`Drained: ${e.reason}`);
  } else {
    throw e;
  }
}
```
:::

### Drain 语义

Drain 是**协作式**的，只在 Super-step Boundary 生效，不会抢占正在运行的 Node：

| 场景 | 行为 |
| --- | --- |
| Node 正在执行 | Node 正常完成；下一 Super-step 前 Drain 生效 |
| Node 正处于 Retry Loop | Retry 继续直到成功或耗尽，然后 Drain |
| Graph 恰好在同一 Tick 自然结束 | 正常返回，可通过 `drain_requested` / `drainRequested` 区分 |
| 后续仍有 Super-step | 抛出 `GraphDrained(reason)`；已保存可恢复 Checkpoint |
| Subgraph 请求 Drain | `GraphDrained` 向 Parent 冒泡，Parent 在自己的下一 Super-step Boundary 停止 |

### Drain 后恢复

:::python
使用相同 `thread_id` 调用：

```python
result = graph.invoke(None, config)
```
:::

:::js
```typescript
const result = await graph.invoke(null, config);
```
:::

### Node 内感知 Drain

Node 可以从 Runtime 读取 Drain State，在真正到达 Super-step Boundary 前主动跳过昂贵工作：

:::python
```python
from langgraph.runtime import Runtime

async def my_node(state: State, runtime: Runtime) -> State:
    if runtime.drain_requested:
        return {"status": "skipped", "reason": runtime.drain_reason}
    return {"status": await do_work()}
```
:::

:::js
```typescript
const myNode = async (state, runtime) => {
  if (runtime.control?.drainRequested) {
    return { status: "skipped", reason: runtime.control.drainReason };
  }
  return { status: await doWork() };
};
```
:::

### SIGTERM 模式

:::python
```python
import signal
from langgraph.runtime import RunControl
from langgraph.errors import GraphDrained

control = RunControl()
signal.signal(signal.SIGTERM, lambda *_: control.request_drain("sigterm"))

try:
    result = graph.invoke(inputs, config, control=control)
except GraphDrained as e:
    log.info("graph drained: %s", e.reason)
```

<Note>
`request_drain()` 不会强制取消正在运行的 Async Task 或杀死 Thread。如果还需要硬上限，应结合 Graceful Timeout 与任务取消机制。
</Note>
:::

:::js
```typescript
import process from "node:process";
import { RunControl, GraphDrained } from "@langchain/langgraph";

const control = new RunControl();
process.on("SIGTERM", () => control.requestDrain("sigterm"));

try {
  const result = await graph.invoke(inputs, { ...config, control });
} catch (e) {
  if (e instanceof GraphDrained) {
    console.log(`graph drained: ${e.reason}`);
  } else {
    throw e;
  }
}
```

<Note>
`requestDrain()` 不会自动取消正在执行的 Async Work；如果需要硬上限，可结合 Graceful Timeout 与 `AbortSignal`。
</Note>
:::

## 限制

:::python
- **Timeout 仅支持 Async Node**：Sync Node 配置 `timeout` 会在编译时被拒绝。
- **每个 Node 最多一个 Error Handler**。
- **Handler 自己失败时异常会继续向上冒泡**，行为等价于没有 Handler。
- **`set_node_defaults` 不会被 Subgraph 继承**。
:::

:::js
- **`setNodeDefaults` 不会被 Subgraph 继承**。
- **Error Handler 仅支持 `StateGraph` Node**，不适用于基础 `Graph`、`task` 或 `entrypoint`。
- **每个 Node 最多一个 Error Handler**。
- **Handler 自身抛错时异常会继续冒泡**。
:::
