LangGraph 提供构建可靠智能体所需的一组容错原语：**Retry、Timeout、Error Handler、Checkpoint、Graceful Shutdown**。这些机制分别解决瞬时失败、卡死调用、补偿逻辑、恢复执行以及进程优雅退出等问题，并且可以组合使用。

一个实用的心智模型是：

```text
Node 执行
   │
   ├─ 瞬时失败 ─→ Retry Policy
   │
   ├─ 执行卡死 ─→ Timeout Policy
   │
   ├─ 重试耗尽 ─→ Error Handler / Compensation
   │
   ├─ 进程崩溃 ─→ Checkpoint → Resume
   │
   └─ 外部要求退出 ─→ Graceful Drain → Resume
```

## Retry Policy

对于可能出现瞬时错误的 Node，可以配置 @[`RetryPolicy`]。失败后，LangGraph 会根据 Policy 判断是否重试、最多重试多少次，以及每次重试之间等待多久。

:::python
```python
from langgraph.graph import StateGraph
from langgraph.types import RetryPolicy

builder = StateGraph(State)
builder.add_node(
    "call_api",
    call_api,
    retry_policy=RetryPolicy(max_attempts=3),
)
```
:::

:::js
```typescript
const graph = new StateGraph(State)
  .addNode("callApi", callApi, {
    retryPolicy: { maxAttempts: 3 },
  })
  .compile();
```
:::

### Retry Policy 参数

常见参数包括：

- `max_attempts` / `maxAttempts`：总 Attempt 数，包括第一次执行。
- `initial_interval` / `initialInterval`：第一次 Retry 前等待时间。
- `backoff_factor` / `backoffFactor`：指数退避系数。
- `max_interval` / `maxInterval`：单次等待上限。
- `jitter`：是否加入随机抖动，避免大量 Worker 同时重试形成 Thundering Herd。
- `retry_on` / `retryOn`：决定哪些 Error 应该重试。

Retry 适合：

- 网络抖动；
- Rate Limit；
- 暂时性的 5xx；
- 数据库锁竞争；
- 可恢复 Provider Error。

Retry **不应该**被用来掩盖确定性 Bug，例如 Schema 不匹配、非法参数、业务校验失败。对于不会因为“再试一次”而消失的问题，应该立即向上抛出或交给 Error Handler。

### 自定义 `retry_on`

:::python
```python
import sqlite3
from langgraph.types import RetryPolicy

policy = RetryPolicy(
    max_attempts=5,
    retry_on=sqlite3.OperationalError,
)
```

也可以传入 Predicate Function：

```python
def should_retry(error: Exception) -> bool:
    return isinstance(error, ConnectionError)

policy = RetryPolicy(max_attempts=3, retry_on=should_retry)
```
:::

:::js
```typescript
const retryPolicy = {
  maxAttempts: 3,
  retryOn: (error: unknown) => error instanceof ConnectionError,
};
```
:::

### Retry 与 Checkpoint

Retry 发生在 Node Attempt 层级。失败 Attempt 的 Buffered State Write 不会提交；只有 Node 成功完成后，对 State 的更新才会进入 Superstep Commit。

这意味着失败后重试不会把“半完成”的 State 泄漏到后续 Node。

如果同一个 Superstep 中存在多个并行 Node，而只有一个 Branch 失败：

- 成功 Branch 的 Pending Write 会被 Checkpoint 保存；
- 失败 Branch 可以单独 Retry；
- Resume 后已经成功的 Branch 不必重新执行。

这也是 LangGraph Durable Execution 的核心价值之一。

## Timeout

Retry 解决“失败”，Timeout 解决“迟迟不返回”。

当外部 API、Tool 或 Model Call 可能永久挂起时，可以给 Async Node 配置 Timeout。

:::python
<Note>
Per-node Timeout 需要较新的 LangGraph 版本；Timeout 只支持 Async Node，因为 Python 无法在同一进程内安全取消正在运行的同步函数。
</Note>

```python
import asyncio
from langgraph.errors import NodeTimeoutError

async def call_model(state: State):
    await asyncio.sleep(2)
    return {"status": "done"}

builder.add_node(
    "call_model",
    call_model,
    timeout=1.0,
)
```

超时后会抛出 `NodeTimeoutError`：

```python
try:
    await graph.ainvoke(inputs)
except NodeTimeoutError:
    print("Node timed out")
```
:::

:::js
```typescript
const graph = new StateGraph(State)
  .addNode("callModel", callModel, {
    timeout: 1_000,
  })
  .compile();
```
:::

### Timeout + Retry

Timeout 本身也是一种 Failure。如果 Retry Policy 会匹配 `NodeTimeoutError` / `TimeoutError`，那么超时 Attempt 可以自动 Retry。

:::python
```python
from langgraph.errors import NodeTimeoutError
from langgraph.types import RetryPolicy

builder.add_node(
    "call_api",
    call_api,
    timeout=1.0,
    retry_policy=RetryPolicy(
        max_attempts=3,
        retry_on=NodeTimeoutError,
    ),
)
```
:::

每一次 Retry 都会重新开始自己的 Timeout Timer。

和普通失败一样，超时 Attempt 的 Buffered Write 会被清理，不会把不完整 State 写入 Graph。

## `TimeoutPolicy`

除了简单数字 Timeout，还可以使用更细粒度的 `TimeoutPolicy`：

:::python
```python
from langgraph.types import TimeoutPolicy

builder.add_node(
    "call_model",
    call_model,
    timeout=TimeoutPolicy(
        run_timeout=120,
        idle_timeout=30,
    ),
)
```
:::

两个概念：

- **Run Timeout**：单次 Attempt 的总最长执行时间。
- **Idle Timeout**：多久没有观察到活动就视为卡死。

对于长时间运行、但会不断报告进度的 Node，Idle Timeout 往往比一个很短的固定 Run Timeout 更合理。

### Heartbeat

长任务可以主动报告自己仍然存活，以刷新 Idle Timeout。

:::python
```python
from langgraph.runtime import Runtime

async def long_running_node(state: State, runtime: Runtime):
    for item in work_items:
        await process(item)
        runtime.heartbeat()
    return {"status": "done"}
```
:::

Heartbeat 的意义不是输出业务 Progress，而是告诉 Runtime：这个 Node 虽然运行很久，但并没有卡死。

## Error Handling

Retry 最终可能仍然失败。对于需要业务补偿、Fallback 或降级的 Node，可以配置 `error_handler` / `errorHandler`。

Handler 在：

1. Node 抛出 Error；
2. Retry Policy 已经耗尽，或该 Error 不符合 Retry 条件；
3. Runtime 决定不再重新执行 Node；

之后运行。

:::python
<Note>
Node-level Error Handler 需要 `langgraph>=1.2`。
</Note>

```python
from langgraph.errors import NodeError
from langgraph.types import Command, RetryPolicy


def charge_payment(state: State):
    return payment_provider.charge(state["order_id"])


def payment_error_handler(
    state: State,
    error: NodeError,
) -> Command:
    return Command(
        update={"status": f"compensated: {error.error}"},
        goto="finalize",
    )

builder.add_node(
    "charge_payment",
    charge_payment,
    retry_policy=RetryPolicy(
        max_attempts=3,
        retry_on=ConnectionError,
    ),
    error_handler=payment_error_handler,
)
```
:::

:::js
```typescript
import { Command, NodeError } from "@langchain/langgraph";

const paymentErrorHandler = (
  state: typeof State.State,
  error: NodeError,
) =>
  new Command({
    update: { status: `compensated: ${error.error.message}` },
    goto: "finalize",
  });

const graph = new StateGraph(State)
  .addNode("chargePayment", chargePayment, {
    retryPolicy: {
      maxAttempts: 3,
      retryOn: (e) => e instanceof ConnectionError,
    },
    errorHandler: paymentErrorHandler,
  })
  .compile();
```
:::

`chargePayment` 对 `ConnectionError` 最多尝试 3 次。如果所有 Retry 都失败，或者错误根本不是 `ConnectionError`，Handler 会更新 State 并路由到 `finalize`，而不是让整个 Graph 直接终止。

## `NodeError`

Error Handler 接收的不是裸 Exception，而是包含执行上下文的 `NodeError`。

它让 Handler 能够知道：

- 哪个 Node 失败；
- 原始 Error 是什么；
- 当前 Attempt / Runtime Context；
- 从哪个失败点进行补偿。

典型用法：

```python
def handler(state: State, error: NodeError):
    return {
        "status": "failed",
        "failure_node": error.node,
        "error_message": str(error.error),
    }
```

## Saga / Compensation

真实 Workflow 里，已经发生的 Side Effect 往往不能简单“回滚内存 State”。例如：

```text
创建订单 ✓
   ↓
扣款 ✓
   ↓
创建物流单 ✗
```

此时需要执行补偿动作：退款、取消订单、标记人工处理等。

LangGraph 的 Error Handler + `Command` 很适合实现 Saga Pattern：

```python
def shipping_error_handler(state: State, error: NodeError) -> Command:
    refund_payment(state["payment_id"])
    cancel_order(state["order_id"])

    return Command(
        update={"status": "compensated"},
        goto="finalize",
    )
```

<Warning>
补偿操作本身也应该是**幂等的**。如果 Handler 执行到一半进程崩溃，恢复时 Handler 可能再次运行，因此 Refund / Cancel API 应使用 Idempotency Key 或先查询当前状态。
</Warning>

## Resume-safe Failure

<Note>
Failure Provenance 会写入 Checkpoint。如果 Node 已经失败，但进程在 Error Handler 完成之前崩溃或被中断，那么从 Checkpoint 恢复后，Handler 仍然会看到同一份 `NodeError` Context。
</Note>

这意味着补偿逻辑可以和其他 Graph State 一样受 Durable Execution 保护。

## `interrupt()` 与 Error Handler

<Warning>
Node 内部调用的 `interrupt()` **不会**进入 Error Handler。

Interrupt 使用 `GraphBubbleUp` 机制暂停 Graph，用于人在回路；它会绕过 Retry Policy 与 Error Handler。Graph 会像正常 HITL Workflow 一样暂停。
</Warning>

因此不要把 Interrupt 当成 Error，也不要试图通过 Error Handler 捕获审批请求。

## Subgraph Failure

如果 Parent Node 包装了一个 Subgraph，而 Subgraph 抛出未处理异常：

- Error 会冒泡到 Parent Node；
- Parent Node 如果配置了 Error Handler，该 Handler 会执行；
- `NodeError.error` 中包含 Subgraph 原始 Exception。

这允许 Parent Workflow 对整个 Subgraph 做降级或补偿。

:::python
## Graph Defaults

<Note>
需要 `langgraph>=1.2`。
</Note>

如果很多 Node 使用相同的 Retry / Timeout / Error Handler / Cache Policy，可以通过 @[`set_node_defaults`] 一次性设置：

```python
from langgraph.errors import NodeError
from langgraph.types import RetryPolicy, TimeoutPolicy
from langgraph.graph import StateGraph, START


def default_error_handler(state: State, error: NodeError):
    return {"status": f"handled: {error.error}"}


graph = (
    StateGraph(State)
    .set_node_defaults(
        retry_policy=RetryPolicy(max_attempts=3),
        error_handler=default_error_handler,
        timeout=TimeoutPolicy(run_timeout=30),
    )
    .add_node("step_a", step_a)
    .add_node("step_b", step_b)
    .add_edge(START, "step_a")
    .compile()
)
```

`step_a` 与 `step_b` 共享这些默认配置。

### 优先级

传给 `add_node()` 的 Per-node Value 总是覆盖 `set_node_defaults()`：

```python
graph = (
    StateGraph(State)
    .set_node_defaults(error_handler=default_error_handler)
    .add_node("step_a", step_a)
    .add_node(
        "step_b",
        step_b,
        error_handler=custom_error_handler,
    )
    .compile()
)
```

Default 在 `compile()` 时解析，因此 `set_node_defaults()` 写在 `add_node()` 前后都可以。

### Default Error Handler

当每个 Graph Run 都对应外部 Process，例如后台 Job Row，Graph-wide Error Handler 很方便：任何没有被局部处理的 Node Failure 都可以统一把外部 Process 标记失败。

```python
from langchain_core.runnables import RunnableConfig


def mark_process_failed(
    state: State,
    error: NodeError,
    config: RunnableConfig,
):
    thread_id = config["configurable"].get("thread_id")
    return {
        "status": f"failed on thread {thread_id}: {error.error}"
    }
```

### Applicability Matrix

不是所有 Default 都适用于 Error-handler Node：

| `set_node_defaults` 参数 | 普通 Node | Error-handler Node | 原因 |
| --- | --- | --- | --- |
| `retry_policy` | ✅ | ✅ | Handler 也可能出现瞬时失败 |
| `timeout` | ✅ | ✅ | 卡死 Handler 同样应被取消 |
| `error_handler` | ✅ | ❌ | Handler 不能捕获自己 |
| `cache_policy` | ✅ | ❌ | 缓存 Handler Result 不安全 |

### Scope

Parent Graph 的 Defaults **不会**自动继承给 Subgraph。每张 Graph 维护自己的 Defaults。
:::

:::js
## Graph Defaults

<Note>
需要较新的 `@langchain/langgraph` 版本。
</Note>

JavaScript / TypeScript 使用 `setNodeDefaults`：

```typescript
const graph = new StateGraph(State)
  .setNodeDefaults({
    retryPolicy: { maxAttempts: 3 },
    errorHandler: defaultErrorHandler,
    timeout: { runTimeout: 30_000 },
    cachePolicy: { ttl: 60 },
  })
  .addNode("stepA", stepA)
  .addNode("stepB", stepB)
  .addEdge(START, "stepA")
  .compile();
```

Per-node Option 优先于 Default；`errorHandler` 与 `cachePolicy` 不会应用到 Error-handler Node。
:::

## Functional API

:::python
Functional API 中 `@task` 和 `@entrypoint` 同样支持 Timeout 与 Retry：

```python
from langgraph.func import entrypoint, task
from langgraph.types import RetryPolicy, TimeoutPolicy

@task(
    timeout=TimeoutPolicy(idle_timeout=30),
    retry_policy=RetryPolicy(max_attempts=3),
)
async def call_api(url: str) -> str:
    response = await fetch(url)
    return response.text

@entrypoint(timeout=60)
async def my_workflow(inputs: dict) -> str:
    return await call_api(inputs["url"])
```

行为与 `add_node` 一致：Timeout 抛出 `NodeTimeoutError`、Buffered Write 被清除、Retry Policy 决定是否重试。
:::

:::js
JavaScript / TypeScript 中 `task` 使用 `timeout` 与 `retry`：

```typescript
const callApi = task(
  {
    name: "callApi",
    timeout: { idleTimeout: 30_000 },
    retry: { maxAttempts: 3 },
  },
  async (url: string) => {
    const response = await fetch(url);
    return response.text();
  }
);

const myWorkflow = entrypoint(
  { name: "myWorkflow", timeout: 60_000 },
  async (inputs: { url: string }) => {
    return await callApi(inputs.url);
  }
);
```

JavaScript Functional API 的 Task / Entrypoint 不提供 Error Handler；需要补偿逻辑时，使用 `StateGraph.addNode(..., { errorHandler })`。
:::

## Graceful Shutdown

Graceful Shutdown（协作式优雅关闭）允许外部 Supervisor 请求一个正在运行的 Graph：**完成当前 Superstep 后停止，并保存一个可恢复 Checkpoint**。

典型场景：

- Kubernetes Pod 收到 SIGTERM；
- Worker 需要缩容；
- Deployment 要升级；
- Supervisor 需要回收资源；
- 长时间 Run 需要迁移到其他 Worker。

它与直接 Kill Process 的区别是：不会丢掉当前已经完成的工作。

:::python
<Note>
需要 `langgraph>=1.2`。
</Note>

```python
from langgraph.runtime import RunControl
from langgraph.errors import GraphDrained

control = RunControl()

# 例如在 signal handler / supervisor 中：
# control.request_drain("sigterm")

try:
    result = graph.invoke(
        inputs,
        config,
        control=control,
    )
except GraphDrained as e:
    print(f"Drained: {e.reason}")
```
:::

:::js
```typescript
import { RunControl, GraphDrained } from "@langchain/langgraph";

const control = new RunControl();

// control.requestDrain("sigterm");

try {
  const result = await graph.invoke(inputs, {
    ...config,
    control,
  });
} catch (e) {
  if (e instanceof GraphDrained) {
    console.log(`Drained: ${e.reason}`);
  } else {
    throw e;
  }
}
```
:::

### Drain 语义

Drain 是**协作式的**，只会在 Superstep Boundary 生效，不会暴力抢占已经正在执行的 Node：

| 场景 | 行为 |
| --- | --- |
| Node 正在执行 | 当前 Node 正常跑完；下一个 Superstep 前停止 |
| Node 正处于 Retry Loop | Retry 直到成功或耗尽；之后再 Drain |
| Graph 在 Drain 同一 Tick 自然结束 | 正常返回，不抛 `GraphDrained` |
| 后面仍有 Superstep | 抛 `GraphDrained(reason)`，并保存可恢复 Checkpoint |
| Subgraph 请求 Drain | `GraphDrained` 冒泡到 Parent，并在 Parent 的下一个 Boundary 停止 |

### 在 Node 内观察 Drain

Node 可以读取 Runtime：

:::python
```python
from langgraph.runtime import Runtime


def my_node(state: State, runtime: Runtime):
    if runtime.drain_requested:
        return {
            "status": "skipped",
            "reason": runtime.drain_reason,
        }

    return {"status": do_expensive_work()}
```
:::

这样长流程在收到 Drain 后，可以主动跳过非必要昂贵步骤。

### Drain 后恢复

:::python
使用**同一个 `thread_id`**，传 `None` 恢复：

```python
result = graph.invoke(None, config)
```
:::

:::js
```typescript
const result = await graph.invoke(null, config);
```
:::

恢复后 Graph 从已保存 Checkpoint 继续，而不是重新从 START 执行。

## 与 Checkpoint 的关系

Retry、Error Handler、Interrupt、Drain 最终都依赖相同的持久化基础：Checkpoint。

```text
Execution
   │
   ├─ success ─────────────→ next step
   │
   ├─ transient failure ───→ retry
   │
   ├─ terminal failure ────→ error handler
   │
   ├─ interrupt ───────────→ checkpoint + wait
   │
   └─ drain ───────────────→ checkpoint + stop

                         later
                           ↓
                        resume
```

没有 Checkpointer 时，你仍可以使用基本 Retry / Error Handling，但无法获得完整的 Durable Resume 能力。

## 设计建议

### 1. Retry 只处理真正瞬时的错误

不要对所有 Exception 一律重试。确定性 Bug 重试只会浪费时间和 Token。

### 2. Side Effect 必须幂等

任何可能在 Retry / Resume 后重新执行的动作都应该有 Idempotency Strategy：

- Payment 使用 Idempotency Key；
- DB 使用 Upsert；
- Email 使用发送记录去重；
- Ticket Creation 先检查是否已经存在。

### 3. 把补偿作为显式 Control Flow

不要只在 `except` 中偷偷做大量业务逻辑。使用 Error Handler + `Command(goto=...)` 把恢复路径变成 Graph 的一部分，便于观测、测试和追踪。

### 4. Timeout 与 Retry 一起设计

没有 Timeout 的 Retry 可能永远等不到第一次 Failure；没有 Retry 的 Timeout 可能把一次偶发慢请求直接升级为业务失败。

### 5. 把 HITL 与 Error 分开

人工审批是正常工作流，不是异常。使用 `interrupt()`，而不是通过抛 Error 模拟暂停。

### 6. 为长 Run 支持 Graceful Drain

如果 Agent 可能运行数分钟甚至数小时，应考虑 Worker Shutdown、Deployment Rollout、资源回收等场景，并通过 Checkpointer + Drain 确保 Run 可以迁移和恢复。
