本教程展示如何使用 LangGraph 构建一个自定义 **SQL 智能体**。智能体接收自然语言问题，自主检查数据库结构、生成 SQL、校验查询、执行查询，并在发生错误时根据反馈继续修正。

与简单的“自然语言 → SQL”单次调用不同，SQL 智能体通常需要一个循环：

```text
用户问题
   ↓
查看可用表
   ↓
读取相关 Schema
   ↓
生成 SQL
   ↓
检查 SQL
   ↓
执行查询
   ├─ 成功 → 根据结果回答
   └─ 失败 → 根据错误修正 SQL ─┐
                               │
                 ←─────────────┘
```

<Warning>
SQL 智能体能够生成数据库查询。生产环境中应使用**最小权限原则**：数据库账号只授予任务真正需要的权限，并尽可能限制为只读访问。不要让模型直接连接具有 DROP、DELETE、UPDATE 等高风险权限的生产数据库，除非你已经建立了额外的审批与安全控制。
</Warning>

## 前置条件

安装 LangGraph、LangChain 以及数据库相关集成：

:::python
```bash
pip install -U langgraph langchain langchain-community langchain-openai
```
:::

:::js
```bash
npm install @langchain/langgraph @langchain/core @langchain/openai
```
:::

本教程使用 SQLite 示例数据库。你也可以替换为 PostgreSQL、MySQL 或其他 LangChain 支持的 SQL 数据库。

## 1. 连接数据库

:::python
```python
from langchain_community.utilities import SQLDatabase

# Replace this URI with your own database in production.
db = SQLDatabase.from_uri("sqlite:///Chinook.db")

print(db.get_usable_table_names())
```
:::

连接成功后，首先应该让智能体能够发现数据库中有哪些表，而不是直接让模型猜测 Schema。

## 2. 定义 SQL 工具

SQL Agent 通常至少需要以下能力：

1. **列出表**：知道数据库中有哪些可用实体。
2. **查看 Schema**：读取候选表的字段、类型和部分样例。
3. **执行查询**：执行最终 SQL 并获得结果。
4. **检查查询**：在执行前让模型检查常见 SQL 错误。

:::python
```python
from langchain_community.tools.sql_database.tool import (
    InfoSQLDatabaseTool,
    ListSQLDatabaseTool,
    QuerySQLCheckerTool,
    QuerySQLDatabaseTool,
)
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-5.4-mini")

list_tables_tool = ListSQLDatabaseTool(db=db)
get_schema_tool = InfoSQLDatabaseTool(db=db)
run_query_tool = QuerySQLDatabaseTool(db=db)
check_query_tool = QuerySQLCheckerTool(db=db, llm=model)
```
:::

工具描述非常重要。模型会根据 Tool Name、Description 和 Input Schema 决定何时以及如何调用工具。

## 3. 定义 State

SQL Agent 的核心状态通常就是消息历史。使用 `MessagesState` 可以自动获得适合消息列表的 Reducer。

:::python
```python
from langgraph.graph import MessagesState

class State(MessagesState):
    pass
```
:::

:::js
```typescript
import { StateSchema, MessagesValue } from "@langchain/langgraph";

const State = new StateSchema({
  messages: MessagesValue,
});
```
:::

如果还需要保存 SQL 审批状态、数据库租户、查询预算等额外信息，可以继续向 State 中添加字段。

## 4. 列出数据库表

第一步让 Agent 查看可用表。这一步可以确定性执行，而不是让模型决定是否调用。

:::python
```python
from langchain.messages import AIMessage


def list_tables(state: State):
    tool_call = {
        "name": list_tables_tool.name,
        "args": {},
        "id": "list_tables",
        "type": "tool_call",
    }
    tool_message = list_tables_tool.invoke(tool_call)
    return {
        "messages": [
            AIMessage(content="", tool_calls=[tool_call]),
            tool_message,
        ]
    }
```
:::

在真实系统中，这种“必须执行”的步骤很适合写成确定性 Node。不要把所有控制权都交给 LLM。

## 5. 选择并读取相关 Schema

看到表列表后，让模型判断哪些表可能与问题相关，并调用 Schema Tool。

:::python
```python
model_with_schema_tool = model.bind_tools([get_schema_tool])


def call_get_schema(state: State):
    response = model_with_schema_tool.invoke(state["messages"])
    return {"messages": [response]}
```
:::

然后使用预构建的 `ToolNode` 执行模型产生的 Tool Call：

:::python
```python
from langgraph.prebuilt import ToolNode

get_schema_node = ToolNode([get_schema_tool], name="get_schema")
```
:::

这样，模型负责**选择哪些表**，LangGraph Runtime 负责真正执行 Tool。

## 6. 生成 SQL 查询

Schema 已经进入消息上下文后，可以让模型生成 SQL。

一个可靠的 Prompt 应明确：

- 只生成合法 SQL；
- 不查询不相关字段；
- 默认限制返回行数；
- 不执行 DML / DDL 等写操作；
- 遇到错误时根据 Error Message 修正；
- 在真正回答用户前必须基于 Tool Result，而不是猜测结果。

:::python
```python
query_prompt = """
You are a SQL expert. Given the conversation and database schema,
write a syntactically correct SQL query that answers the user's question.

Rules:
- Do not make any DML statements (INSERT, UPDATE, DELETE, DROP, etc.).
- Unless the user asks for a specific number of examples, limit results.
- Only select columns relevant to the question.
- Never invent table or column names.
- Use the database schema and tool errors to repair mistakes.
"""

model_with_query_tool = model.bind_tools([run_query_tool])


def generate_query(state: State):
    response = model_with_query_tool.invoke(
        [{"role": "system", "content": query_prompt}] + state["messages"]
    )
    return {"messages": [response]}
```
:::

这里可以直接绑定执行 Tool，也可以将“生成 SQL”和“真正执行 SQL”拆开，以便在中间加入 Query Checker 或人工审批。

## 7. 在执行前检查 SQL

生产级 SQL Agent 最好不要直接执行模型第一次生成的 SQL。可以额外加入 Query Checker：

:::python
```python
from langchain.messages import AIMessage


def check_query(state: State):
    last_message = state["messages"][-1]
    tool_call = last_message.tool_calls[0]
    query = tool_call["args"]["query"]

    checked_query = check_query_tool.invoke({"query": query})

    checked_call = {
        "name": run_query_tool.name,
        "args": {"query": checked_query},
        "id": tool_call["id"],
        "type": "tool_call",
    }
    return {"messages": [AIMessage(content="", tool_calls=[checked_call])]}
```
:::

Query Checker 可以发现很多常见问题，例如：

- `NOT IN` 与 `NULL` 组合造成的逻辑错误；
- `UNION` 与 `UNION ALL` 误用；
- 数据类型不匹配；
- 错误的 Join Column；
- 函数参数数量错误；
- 不必要的复杂查询。

它不是数据库安全边界。真正的安全仍然应该通过数据库权限、Allowlist、Query Parser、Policy Check 和人工审批实现。

## 8. 执行 SQL

使用 `ToolNode` 执行检查后的查询：

:::python
```python
run_query_node = ToolNode([run_query_tool], name="run_query")
```
:::

如果 SQL 执行失败，Tool Result 会包含 Error Message。随后把控制流交回模型，让它基于错误修正 Query。

这正是 Agent Loop 的价值：

```text
错误 SQL
  ↓
数据库返回错误
  ↓
错误进入消息上下文
  ↓
LLM 修正 SQL
  ↓
重新检查并执行
```

## 9. 根据查询结果回答用户

查询成功后，不应该直接把原始数据库输出作为最终回答。让模型根据查询结果生成用户可读的解释：

:::python
```python

def generate_answer(state: State):
    response = model.invoke(
        [
            {
                "role": "system",
                "content": (
                    "Answer the user's question using the SQL query result. "
                    "Do not invent facts not present in the result."
                ),
            }
        ]
        + state["messages"]
    )
    return {"messages": [response]}
```
:::

## 10. 组装 Graph

最终 Graph 可以组织为：

```text
START
  ↓
list_tables
  ↓
call_get_schema
  ↓
get_schema
  ↓
generate_query
  ↓
check_query
  ↓
run_query
  ↓
成功？
 ├─ 否 → generate_query
 └─ 是 → generate_answer → END
```

:::python
```python
from langgraph.graph import StateGraph, START, END

builder = StateGraph(State)

builder.add_node("list_tables", list_tables)
builder.add_node("call_get_schema", call_get_schema)
builder.add_node("get_schema", get_schema_node)
builder.add_node("generate_query", generate_query)
builder.add_node("check_query", check_query)
builder.add_node("run_query", run_query_node)
builder.add_node("generate_answer", generate_answer)

builder.add_edge(START, "list_tables")
builder.add_edge("list_tables", "call_get_schema")
builder.add_edge("call_get_schema", "get_schema")
builder.add_edge("get_schema", "generate_query")
builder.add_edge("generate_query", "check_query")
builder.add_edge("check_query", "run_query")

# In a complete implementation, route based on the tool result:
# errors -> generate_query, successful results -> generate_answer.

builder.add_edge("run_query", "generate_answer")
builder.add_edge("generate_answer", END)

graph = builder.compile()
```
:::

实际实现中，应通过 Conditional Edge 判断 Tool Result 是否是 Error；如果是，返回 `generate_query` 进行修复，否则进入 `generate_answer`。

## 11. 运行智能体

:::python
```python
question = "Which genre has the most tracks?"

for chunk in graph.stream(
    {"messages": [{"role": "user", "content": question}]},
    stream_mode="updates",
):
    print(chunk)
```
:::

如果希望逐 Token 展示模型输出，可以使用 `messages` Stream Mode，或者使用更高层的 [Event Streaming](/oss/langgraph/event-streaming)。

## 加入人工审批

SQL 查询即使是只读操作，也可能代价非常高，例如扫描整张大表。对于生产环境，可以在执行前增加 [`interrupt()`](/oss/langgraph/interrupts)：

:::python
```python
from langgraph.types import interrupt


def approve_query(state: State):
    last_message = state["messages"][-1]
    query = last_message.tool_calls[0]["args"]["query"]

    decision = interrupt({
        "action": "execute_sql",
        "query": query,
        "message": "Approve this SQL query?",
    })

    if not decision:
        raise ValueError("Query rejected by reviewer")

    return {}
```
:::

更成熟的系统可以让人工：

- 批准查询；
- 修改 SQL 后继续；
- 拒绝查询；
- 要求 Agent 重新规划。

## 生产环境安全建议

SQL Agent 的安全不能只靠 Prompt。建议把控制分成多个层次：

1. **数据库权限**：使用只读、最小权限账号。
2. **数据库隔离**：不要直接暴露生产主库；优先使用 Replica / Analytics Warehouse。
3. **SQL Parser / AST Policy**：在执行前拒绝 DML、DDL、多语句查询和危险函数。
4. **资源限制**：设置 Statement Timeout、Row Limit、扫描预算和并发限制。
5. **Schema Allowlist**：只向 Agent 暴露允许访问的表和字段。
6. **人工审批**：高成本或敏感查询使用 Interrupt。
7. **审计与 Tracing**：记录用户问题、生成 SQL、Tool Result 和最终回答。

## 为什么用 LangGraph，而不是简单 Agent Loop

最小 SQL Agent 可以用一个 Tool-calling Loop 实现，但 LangGraph 让每个重要阶段拥有明确边界：

- Schema Discovery 可以确定性执行；
- SQL Generation 与 SQL Execution 可以分离；
- Query Check 可以成为强制步骤；
- Error Recovery 可以显式循环；
- 高风险查询可以 Interrupt；
- 长时间查询可以配置 Timeout / Retry；
- Checkpoint 可以让失败后的长流程从中间恢复；
- LangSmith 可以观察每一步 State 和 Tool Call。

因此，LangGraph 特别适合“**模型负责部分决策，但系统必须保持强控制和可审计性**”的数据库智能体。
