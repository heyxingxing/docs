## 图

LangGraph 的核心思想是把智能体工作流建模为**图（Graph）**。你通过三个关键组件来定义智能体行为：

1. [`State`](#state)：表示应用当前快照的共享数据结构。它可以是任意数据类型，但通常会通过共享 State Schema 定义。
2. [`Node`](#nodes)：编码智能体逻辑的函数。节点接收当前 State，执行计算或副作用，并返回 State Update。
3. [`Edge`](#edges)：根据当前 State 决定下一步执行哪个 Node。Edge 可以是固定跳转，也可以是条件分支。

通过组合 Node 和 Edge，可以构建复杂、循环执行，并随着时间持续演化 State 的工作流。而 LangGraph 真正重要的能力之一，就是对这份 State 的管理。

需要强调：`Node` 和 `Edge` 本质上都只是函数。函数内部可以调用 LLM，也完全可以只是普通代码。

一句话概括：**Node 负责做事，Edge 决定接下来做什么。**

LangGraph 底层的图算法通过[消息传递](https://en.wikipedia.org/wiki/Message_passing)描述通用程序。一个 Node 执行完成后，会沿一条或多条 Edge 把 Message 发送到其他 Node；接收方执行自己的函数，再继续向后传递。受到 Google [Pregel](https://research.google/pubs/pregel-a-system-for-large-scale-graph-processing/) 系统启发，程序以离散的 **Super-step（超步）**推进。

一个 Super-step 可以理解为图的一轮执行。并行运行的 Node 属于同一个 Super-step，顺序运行的 Node 则属于不同 Super-step。图开始执行时，所有 Node 都处于 `inactive` 状态；当某个 Node 在任意入边（或 Channel）上收到新的 Message（State）时，它会变为 `active`，运行函数并返回 Update。每个 Super-step 结束时，没有收到新 Message 的 Node 会通过将自身标记为 `inactive` 来“投票停止”。当所有 Node 都处于 `inactive`，且没有 Message 仍在传输时，图执行结束。

### StateGraph

@[`StateGraph`] 是最主要的 Graph 类。它由用户定义的 `State` 对象参数化。

### 编译图

构建图时，先定义 [State](#state)，再添加 [Node](#nodes) 和 [Edge](#edges)，最后进行编译。为什么还需要编译？

编译本身很直接：它会对图结构进行一些基础检查，例如是否存在孤立节点；同时也是配置 [Checkpointer](/oss/langgraph/persistence)、Breakpoint 等 Runtime 参数的位置。

## State

:::python
定义图时，第一件事就是定义图的 `State`。State 包含图的 [Schema](#schema)，以及指定如何应用 State Update 的 [`Reducer`](#reducers)。State Schema 会成为所有 Node 和 Edge 的输入 Schema，可以使用 `TypedDict` 或 Pydantic Model 定义。所有 Node 都返回 State Update，再由对应 Reducer 把这些 Update 应用到当前 State。
:::

:::js
定义图时，第一件事就是定义图的 `State`。State 包含图的 [Schema](#schema)，以及指定如何应用 State Update 的 [`Reducer`](#reducers)。你通过 `StateSchema` 定义 State；单个字段可以使用任意 [Standard Schema](https://standardschema.dev/)（例如 [Zod](https://zod.dev/)），也可以使用 `ReducedValue`、`MessagesValue` 等特殊 Value Type。所有 Node 都返回 State Update，再由对应 Reducer 把这些 Update 应用到当前 State。
:::

### Schema

:::python
官方主要推荐使用 [`TypedDict`](https://docs.python.org/3/library/typing.html#typing.TypedDict) 指定 Graph Schema。如果 State 需要默认值，可以使用 [`dataclass`](https://docs.python.org/3/library/dataclasses.html)。如果需要递归数据校验，也支持使用 Pydantic [`BaseModel`](/oss/langgraph/use-graph-api#use-pydantic-models-for-graph-state)，但 Pydantic 的性能通常低于 `TypedDict` 或 `dataclass`。

默认情况下，图的输入和输出使用相同 Schema。也可以显式指定不同的 Input Schema 和 Output Schema；当 State Key 很多，并且某些只应该作为输入、另一些只应该作为输出时，这非常实用。详见[定义输入和输出 Schema](/oss/langgraph/use-graph-api#define-input-and-output-schemas)。

<Info>
`langchain` 中更高层的 [`create_agent`](/oss/langchain/agents) Factory 不支持 Pydantic State Schema。
</Info>
:::

:::js
Graph Schema 主要通过 `StateSchema` 定义。Schema 中的每个字段可以是：

- **Standard Schema**：普通字段，默认是“Last Value”语义，Update 会覆盖旧值。
- **`ReducedValue`**：需要自定义 Reducer 的字段，尤其适合多个并行 Node 同时更新。
- **`MessagesValue`**：聊天消息列表，内置 Message-aware Reducer。
- **`UntrackedValue`**：不进入 Checkpoint 的临时 State。

```typescript
import {
  StateSchema,
  ReducedValue,
  MessagesValue,
  UntrackedValue
} from "@langchain/langgraph";
import { z } from "zod/v4";

const AgentState = new StateSchema({
  messages: MessagesValue,
  currentStep: z.string(),
  retryCount: z.number().default(0),
  allSteps: new ReducedValue(
    z.array(z.string()).default(() => []),
    {
      inputSchema: z.string(),
      reducer: (current, newStep) => [...current, newStep],
    }
  ),
  tempCache: new UntrackedValue(z.record(z.string(), z.unknown())),
});

type State = typeof AgentState.State;
type Update = typeof AgentState.Update;

const graph = new StateGraph(AgentState)
  .addNode("myNode", ...)
  .compile();
```

默认情况下，图的 Input / Output Schema 相同；也可以显式指定不同的输入和输出 Schema。
:::

#### 多个 Schema

一般情况下，所有 Graph Node 都通过同一个 Schema 通信，也就是读取和写入同一组 State Channel。但有些场景需要更精细的控制：

- 内部 Node 需要传递一些并不应该暴露在 Graph Input / Output 中的信息。
- Graph 的 Input Schema 与 Output Schema 可能不同，例如最终只需要返回一个输出 Key。

可以定义 `PrivateState`，让 Node 在图内部写入私有 State Channel。也可以定义一个包含所有内部 Key 的 Overall / Internal Schema，再额外提供它的子集作为 Input Schema 和 Output Schema。详见[定义输入和输出 Schema](/oss/langgraph/use-graph-api#define-input-and-output-schemas)。

### Reducer

Reducer 决定 Node 返回的 Update 如何应用到 `State`。State 中**每个 Key 都有自己独立的 Reducer**。如果没有显式配置 Reducer，该 Key 默认使用覆盖语义：新 Update 直接替换旧值。

#### Reducer 参数

每个 Reducer 都是接收两个位置参数的二元函数：

- **左参数**：当前已经保存在 State 中的值。
- **右参数**：Node 为该 Key 返回的 Update。

Reducer 返回新的 State Value。

### UntrackedValue

`UntrackedValue` 用于“执行过程中需要，但**永远不应该进入 Checkpoint**”的 State 字段。Graph Resume 时，这些 Value 会回到初始状态或变为不可用。

典型场景：
- 无法序列化的**数据库连接**
- Resume 后应该重建的**临时缓存**
- 不希望持久化的**大型对象**
- 每次运行都应重新注入的**仅 Runtime 配置**

```typescript
import { StateSchema, UntrackedValue, MessagesValue } from "@langchain/langgraph";
import { z } from "zod/v4";

const State = new StateSchema({
  messages: MessagesValue,
  dbConnection: new UntrackedValue<DatabaseConnection>(),
  tempCache: new UntrackedValue(
    z.record(z.string(), z.unknown()),
    { guard: false }
  ),
  runtimeConfig: new UntrackedValue(),
});
```

行为：
- 执行期间：像普通 State 一样可读写。
- Checkpoint 时：不会写入持久化数据。
- Resume 时：重新从空值或默认值开始。
- `guard: true`（默认）：同一 Step 多个 Node 写入会报错。
- `guard: false`：允许多次写入，最后一次生效。

<Warning>
如果数据必须跨 Interrupt 或 Time Travel 保留，不要使用 `UntrackedValue`；应使用普通 State Field 或 `ReducedValue`。
</Warning>

### 类型工具

LangGraph 提供若干 TypeScript 类型工具，帮助定义 Node 和 Conditional Edge。

#### `GraphNode`

```typescript
import { GraphNode, StateSchema, Command } from "@langchain/langgraph";
import { z } from "zod/v4";

const State = new StateSchema({
  count: z.number().default(0),
  result: z.string(),
});

const incrementNode: GraphNode<typeof State> = (state) => {
  return { count: state.count + 1 };
};

const fetchNode: GraphNode<typeof State> = async (state, config) => {
  const response = await fetch(`/api/data/${state.count}`);
  return { result: await response.text() };
};

const routerNode: GraphNode<{ InputSchema: typeof State; Nodes: "process" | "done" }> = (state) => {
  if (state.count >= 10) {
    return new Command({ goto: "done" });
  }
  return new Command({ update: { count: state.count + 1 }, goto: "process" });
};
```

每个 `StateSchema` 都提供 `Node` 属性作为简写：

```typescript
const myNode1: GraphNode<typeof State> = (state) => ({ step: "done" });
const myNode2: typeof State.Node = (state) => ({ step: "done" });
```

#### `ConditionalEdgeRouter`

用于只负责路由、不负责 State Update 的 Conditional Edge 函数。

#### `StateSchema.State` 与 `StateSchema.Update`

可以从 Schema 中提取完整 State 类型和 Partial Update 类型，用于自定义类型定义。

### 在 Graph State 中使用消息

#### 为什么使用 Message？

现代 LLM Provider 通常以消息列表作为 Chat Model 输入。LangChain 的 [Chat Model 接口](/oss/langchain/models)接收一系列 Message Object，例如 @[`HumanMessage`] 和 @[`AIMessage`]。概念说明参阅 [Messages](/oss/langchain/messages)。

#### 在图中保存消息

:::python
常见做法是在 Graph State 中维护一个历史 Message 列表。可以为 `messages` Channel 指定 Reducer。若不指定 Reducer，每次 Update 都会覆盖整个列表；若使用 `operator.add`，则只能简单追加。

但人在回路等场景还需要根据 Message ID 修改已有消息。为此，LangGraph 提供预构建的 @[`add_messages`] Reducer：新 Message 会被追加，具有相同 ID 的已有 Message 则会被正确更新。
:::

:::js
JavaScript 可直接使用 `MessagesValue`，它内置 Message-aware Reducer，自动处理 Message ID、更新和删除。`MessagesValue` 本质上是预配置 `messagesStateReducer` 的特殊 `ReducedValue`。
:::

#### 序列化

:::python
@[`add_messages`] 除了处理 Message ID，也会在 `messages` Channel 收到 State Update 时把输入反序列化为 LangChain Message Object。因此下列两种输入都支持：

```python
{"messages": [HumanMessage(content="message")]}
{"messages": [{"type": "human", "content": "message"}]}
```

使用 `add_messages` 后，State 中保存的是 LangChain Message，应使用 `state["messages"][-1].content` 等属性访问。

```python
from langchain.messages import AnyMessage
from langgraph.graph.message import add_messages
from typing import Annotated
from typing_extensions import TypedDict

class GraphState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
```
:::

:::js
`MessagesValue` 同样会把输入反序列化为 LangChain Message Object，因此可以接受 Message 实例或普通对象。访问时使用 `state.messages.at(-1).content`。

```typescript
import { StateGraph, StateSchema, MessagesValue } from "@langchain/langgraph";

const State = new StateSchema({
  messages: MessagesValue,
});
```
:::

:::python
#### MessagesState

由于消息列表非常常见，LangGraph 内置 `MessagesState`。它包含单个 `messages` Key，并使用 @[`add_messages`] Reducer。通常还会继续扩展更多字段：

```python
from langgraph.graph import MessagesState

class State(MessagesState):
    documents: list[str]
```

## Node

:::python
LangGraph 中的 Node 是同步或异步 Python 函数，可接收：

1. `state`：当前 Graph [State](#state)。
2. `config`：@[`RunnableConfig`]，其中包含 `thread_id`、Tracing Tag 等配置。
3. `runtime`：`Runtime` 对象，包含 Runtime `context`、`store`、`stream_writer`、`execution_info`、`server_info`、用于 Idle Timeout Refresh 的 `heartbeat`，以及用于[优雅关闭](/oss/langgraph/fault-tolerance#graceful-shutdown)的 `control` 等。

可通过 @[`add_node`] 添加 Node。函数在内部会被转换为 @[`RunnableLambda`]，因此自动获得 Batch、Async、原生 Tracing 与 Debugging 能力。
:::

:::js
LangGraph 中的 Node 通常是同步或异步函数，接收 `state` 和 `config`。可以通过 `addNode` 添加 Node，并使用 `GraphNode` 或 `State.Node` 提高类型安全。

函数在内部会被转换为 @[`RunnableLambda`]，因此自动获得 Batch、Async 与[原生 Tracing / Debugging](/langsmith/observability)能力。
:::

如果添加 Node 时不显式指定名称，默认会使用函数名作为 Node Name。

### 重新执行与幂等性

当图使用 [Checkpointer](/oss/langgraph/persistence) 编译时，Checkpoint 保存在 [Super-step](#graphs) 边界，而不是 Node 函数执行到一半的位置。如果执行停止并在之后恢复，例如经过 [Interrupt](/oss/langgraph/interrupts) 或 Retry，受影响的 **Node 会从函数开头重新执行**，暂停点之前的代码与副作用也会再次运行。

**幂等性。** Node Logic 应设计成可安全重复执行。比如 Node 插入数据库行时，运行两次不应该意外生成重复数据。可使用 Idempotency Key、Upsert 或 Read-before-write。

**图结构变化。** Functional API 对代码顺序的[确定性](/oss/langgraph/functional-api#determinism)要求并不等同于 Graph Structure。已有 Thread Resume 时会基于已保存 State 使用当前编译的图。

**Node 内的 Task 和 Interrupt。** 如果 Node 调用 [Task](/oss/langgraph/functional-api#task) 或 @[`interrupt`]，Resume 时需要遵循更严格的确定性规则。已完成 Task Result 会从 Checkpointer 恢复，但如果修改了 Resume Point 之前 Task 或 Interrupt 的顺序，就可能错配缓存值。

### 在 Node 中使用 Task

如果一个 Node 内部包含多个操作，可以把每个操作实现为 [Task](/oss/langgraph/functional-api#task)，而不一定拆成多个 Node。Graph 使用 Checkpointer 时，Task Result 会被独立 Checkpoint，因此 Resume 时可以跳过已完成的 Task。

### `START` Node

@[`START`] 是特殊虚拟 Node，代表用户输入进入图的位置。它主要用于指定最先执行哪些 Node。

:::python
```python
from langgraph.graph import START
graph.add_edge(START, "node_a")
```
:::

:::js
```typescript
import { START } from "@langchain/langgraph";
graph.addEdge(START, "nodeA");
```
:::

### `END` Node

`END` 是特殊终止 Node，用于标记某条路径执行完成后不再有后续动作。

### Node 缓存

LangGraph 支持根据 Node Input 缓存 Task / Node 结果。使用方式：

- 编译 Graph（或定义 Entrypoint）时配置 Cache。
- 为 Node 配置 Cache Policy。
- Cache Policy 可以定义用于生成 Cache Key 的 `key_func` / `keyFunc`，以及秒级 TTL。

:::python
```python
import time
from typing_extensions import TypedDict
from langgraph.graph import StateGraph
from langgraph.cache.memory import InMemoryCache
from langgraph.types import CachePolicy

class State(TypedDict):
    x: int
    result: int

def expensive_node(state: State) -> dict[str, int]:
    time.sleep(2)
    return {"result": state["x"] * 2}

builder = StateGraph(State)
builder.add_node("expensive_node", expensive_node, cache_policy=CachePolicy(ttl=3))
builder.set_entry_point("expensive_node")
builder.set_finish_point("expensive_node")
graph = builder.compile(cache=InMemoryCache())
```

<Note>
`set_entry_point(node)` 等价于 `builder.add_edge(START, node)`；`set_finish_point(node)` 等价于 `builder.add_edge(node, END)`。两种写法都有效，但现在更推荐 `add_edge`。
</Note>
:::

:::js
```typescript
import { StateGraph, StateSchema, GraphNode, START } from "@langchain/langgraph";
import { InMemoryCache } from "@langchain/langgraph-checkpoint";
import { z } from "zod/v4";

const State = new StateSchema({ x: z.number(), result: z.number() });
const expensiveNode: GraphNode<typeof State> = async (state) => {
  await new Promise((resolve) => setTimeout(resolve, 3000));
  return { result: state.x * 2 };
};

const graph = new StateGraph(State)
  .addNode("expensive_node", expensiveNode, { cachePolicy: { ttl: 3 } })
  .addEdge(START, "expensive_node")
  .compile({ cache: new InMemoryCache() });
```
:::

## Edge

Edge 定义控制流如何路由，以及图在什么条件下停止。这是智能体行为与 Node 协作方式的核心部分。

主要包括：

- **普通 Edge**：从一个 Node 固定跳转到下一个 Node。
- **Conditional Edge**：执行路由函数，根据结果决定下一个或多个 Node。
- **Entry Point**：用户输入到来后先执行哪些 Node。
- **Conditional Entry Point**：通过函数动态决定最先执行哪些 Node。

一个 Node 可以拥有多条出边。如果存在多条普通出边，**所有目标 Node 都会在下一个 Super-step 中并行执行**。

<Warning>
每个 Node 最好只选择一种 Routing Mechanism：静态路由使用普通 Edge；动态路由使用 Conditional Edge 或 @[`Command`]。不要从同一 Node 同时配置普通 Edge 和动态路由，否则两类路径都可能执行，行为会很难推理。
</Warning>

### 普通 Edge

如果 Node A **总是**进入 Node B，直接添加 Edge：

:::python
```python
graph.add_edge("node_a", "node_b")
```
:::

:::js
```typescript
graph.addEdge("nodeA", "nodeB");
```
:::

### Conditional Edge

如果要根据条件决定是否进入一个或多个 Node，或直接结束，可以添加 Conditional Edge。Routing Function 接收当前 State 并返回目标 Node 名称（或名称列表）。列表中的多个 Node 会在下一 Super-step 中并行执行。

:::python
```python
graph.add_conditional_edges("node_a", routing_function)

graph.add_conditional_edges(
    "node_a", routing_function,
    {True: "node_b", False: "node_c"}
)
```
:::

:::js
```typescript
graph.addConditionalEdges("nodeA", routingFunction, {
  true: "nodeB",
  false: "nodeC",
});
```
:::

<Tip>
如果希望在同一个函数中同时完成 State Update 和 Routing，可以使用 [`Command`](#command)。
</Tip>

### Entry Point

Entry Point 是 Graph 启动时最先执行的 Node。通过从虚拟 @[`START`] Node 添加 Edge 指定：

```python
graph.add_edge(START, "node_a")
```

### Conditional Entry Point

也可以从 `START` 添加 Conditional Edge，根据自定义逻辑动态决定图从哪个 Node 开始。

## `Send`

默认情况下，Node 和 Edge 都提前定义，并在同一份共享 State 上工作。但 Map-Reduce 等场景中，运行前可能并不知道到底需要多少条 Edge，或者同一时刻需要让多个下游 Node 分别处理不同 State。

LangGraph 支持从 Conditional Edge 返回 @[`Send`] Object。`Send` 接收两个参数：目标 Node 名称，以及传给该 Node 的 State。

:::python
```python
from langgraph.types import Send

def continue_to_jokes(state: OverallState):
    return [Send("generate_joke", {"subject": s}) for s in state['subjects']]

graph.add_conditional_edges("node_a", continue_to_jokes)
```
:::

:::js
```typescript
import { Send } from "@langchain/langgraph";

graph.addConditionalEdges("nodeA", (state) => {
  return state.subjects.map(
    (subject) => new Send("generateJoke", { subject })
  );
});
```
:::

## `Command`

@[`Command`] 是控制 Graph Execution 的通用 Primitive，支持四个参数：

- `update`：应用 State Update。
- `goto`：跳转到指定 Node，类似 Conditional Edge。
- `graph`：从 [Subgraph](/oss/langgraph/use-subgraphs) 跳转时指定目标 Parent Graph。
- `resume`：在 [Interrupt](/oss/langgraph/interrupts) 后提供 Resume Value。

主要使用场景：

- **[从 Node 返回](#return-from-nodes)**：用 `update`、`goto` 和 `graph` 同时控制 State 与控制流。
- **作为 `invoke` / `stream` 输入**：用 `resume` 在 Interrupt 后继续执行。
- **[从 Tool 返回](#return-from-tools)**：从 Tool 内部更新 Graph State 和控制流。

### 从 Node 返回

#### `update` 与 `goto`

Node 可以返回 @[`Command`]，在一步内同时修改 State 并选择下一个 Node。

:::python
```python
def my_node(state: State) -> Command[Literal["my_other_node"]]:
    return Command(
        update={"foo": "bar"},
        goto="my_other_node"
    )
```

如果只需要路由、不需要 State Update，优先使用 Conditional Edge。

<Note>
Python 中返回 `Command` 的 Node 应在返回类型中标出可能跳转到的 Node，例如 `Command[Literal["my_other_node"]]`，这样 Graph Renderer 才能知道动态 Edge。
</Note>
:::

:::js
```typescript
import { Command } from "@langchain/langgraph";

graph.addNode("myNode", (state) => {
  return new Command({
    update: { foo: "bar" },
    goto: "myOtherNode",
  });
});
```

JavaScript 中添加 Node 时，通过 `ends` 指定它可能路由到哪些 Node：

```typescript
builder.addNode("myNode", myNode, {
  ends: ["myOtherNode", END],
});
```
:::

<Warning>
`Command` 只会添加动态 Edge，并不会覆盖已有静态 Edge。如果 `node_a` 返回 `Command(goto="my_other_node")`，同时又存在 `graph.add_edge("node_a", "node_b")`，那么 `node_b` 与 `my_other_node` 都会运行。因此同一个 Node 应选择静态 Edge 或 `Command` 动态路由中的一种。
</Warning>

#### `graph`

在 [Subgraph](/oss/langgraph/use-subgraphs) 内，可以通过 `graph=Command.PARENT` 跳转到最近的 Parent Graph：

:::python
```python
def my_node(state: State) -> Command[Literal["other_subgraph"]]:
    return Command(
        update={"foo": "bar"},
        goto="other_subgraph",
        graph=Command.PARENT
    )
```
:::

:::js
```typescript
return new Command({
  update: { foo: "bar" },
  goto: "otherSubgraph",
  graph: Command.PARENT,
});
```
:::

如果 Subgraph 向 Parent Graph 更新双方共享的 State Key，Parent State 中该 Key **必须**定义合适的 [Reducer](#reducers)。这类模式也常用于[多智能体 Handoff](/oss/langchain/multi-agent/handoffs)。

### 作为 `invoke` 或 `stream` 的输入

<Warning>
`Command(resume=...)` 是 `Command` 作为 `invoke()` / `stream()` 输入时的主要用途（也可同时带 `update`）。不要使用只有 `Command(update=...)` 的输入来继续已经结束的多轮对话，因为任何 Command Input 都会从最新 Checkpoint 恢复，而不是重新从 `__start__` 进入图。继续正常对话时，应传普通输入字典 / 对象。
</Warning>

#### `resume`

使用 `Command(resume=...)` 在 [Interrupt](/oss/langgraph/interrupts) 后恢复执行。传入 `resume` 的 Value 会成为暂停 Node 中 `interrupt()` 调用的返回值。

:::python
<LanggraphGraphApiResumeV2Py />
:::

:::js
```typescript
import { Command, interrupt } from "@langchain/langgraph";

const humanReview = async (state: typeof StateAnnotation.State) => {
  const answer = interrupt("Do you approve?");
  return { messages: [{ role: "user", content: answer }] };
};

const result = await graph.invoke({ messages: [...] }, config);
const resumed = await graph.invoke(new Command({ resume: "yes" }), config);
```
:::

### 从 Tool 返回

Tool 也可以返回 @[`Command`]，通过 `update` 修改 Graph State，并通过 `goto` 控制 Tool 完成后进入哪个 Node。与 Node 相同，Tool-driven Routing 与调用它的 Node 上已有静态 Edge 会同时生效，因此同一处应避免混用两种 Routing Mechanism。

## Graph Migration

即使使用 Checkpointer 跟踪 State，LangGraph 仍支持对 Graph Definition（Node、Edge、State）进行演进：

- 对已经执行结束、当前未处于 Interrupt 的 Thread，可以修改整个 Graph Topology，包括增删、重命名 Node 与 Edge。
- 对当前处于 Interrupt 的 Thread，除“删除 / 重命名它即将进入的 Node”外，大多数 Topology 变更都支持。
- State Key 的新增和删除具有较好的前后兼容性。
- State Key 重命名后，旧 Thread 中该字段已保存的 Value 不会自动迁移到新 Key。
- 如果 State Key 的类型发生不兼容修改，已有旧 State 的 Thread 可能出现问题。

<Tip>
如果技术上兼容，但业务逻辑本身发生变化，例如重写 Tool Set 或重构 Conversation Flow，请参阅[业务兼容性](/oss/langgraph/backward-compatibility#business-compatibility)，通过在 State 中保存行为版本，让旧 Thread 保持旧路径，而新 Thread 使用新逻辑。
</Tip>

## Runtime Context

Runtime Context 用于向 Node 传递**不属于 Graph State**的信息，例如 Model Name、Database Connection 或其他依赖。

:::python
```python
@dataclass
class ContextSchema:
    llm_provider: str = "openai"

graph = StateGraph(State, context_schema=ContextSchema)

graph.invoke(inputs, context={"llm_provider": "anthropic"})
```

Node 中通过 `Runtime` 访问：

```python
from langgraph.runtime import Runtime

def node_a(state: State, runtime: Runtime[ContextSchema]):
    llm = get_llm(runtime.context.llm_provider)
```
:::

:::js
```typescript
const ContextSchema = z.object({
  llm: z.union([z.literal("openai"), z.literal("anthropic")]),
});

const graph = new StateGraph(State, ContextSchema);
```
:::

完整说明参阅[添加 Runtime 配置](/oss/langgraph/use-graph-api#add-runtime-configuration)。

### Recursion Limit

Recursion Limit 限制一次 Graph Execution 最多运行多少个 [Super-step](#graphs)。超过限制后 LangGraph 会抛出 `GraphRecursionError`。

:::python
从 1.0.6 起，Python 默认 Recursion Limit 为 1000 Step。它是顶层 Config Key，不应放入 `configurable`：

```python
graph.invoke(inputs, config={"recursion_limit": 5}, context={"llm": "anthropic"})
```
:::

:::js
JavaScript 默认值为 25 Step，可通过顶层 `recursionLimit` 设置：

```typescript
await graph.invoke(inputs, {
  recursionLimit: 5,
  context: { llm: "anthropic" },
});
```
:::

### 访问和处理递归计数器

Node 内可以访问当前 Step Counter，并在真正触发 Recursion Limit 前主动降级。

:::python
当前 Step 位于 `config["metadata"]["langgraph_step"]`。此外，LangGraph 提供 `RemainingSteps` Managed Value，让 State 直接知道距离限制还剩多少 Step：

```python
from typing import Annotated, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.managed import RemainingSteps

class State(TypedDict):
    messages: Annotated[list, lambda x, y: x + y]
    remaining_steps: RemainingSteps

def reasoning_node(state: State) -> dict:
    remaining = state["remaining_steps"]
    if remaining <= 2:
        return {"messages": ["Approaching limit, wrapping up..."]}
    return {"messages": ["thinking..."]}
```
:::

:::js
JavaScript 中应优先在 Graph Logic 中设计明确的 Termination Condition，并把捕获 `GraphRecursionError` 作为最后的安全网。
:::

#### 主动处理与被动处理

主要有两种策略：

:::python
| 方法 | 检测时机 | 处理位置 | 控制流 |
| --- | --- | --- | --- |
| 主动（`RemainingSteps`） | 达到限制前 | Graph 内，通过 Conditional Routing | Graph 可以正常进入结束节点 |
| 被动（捕获 `GraphRecursionError`） | 超限后 | Graph 外部 try/catch | Graph Execution 已终止 |

主动方式可以在图内部优雅降级、保留中间 Checkpoint，并返回 Partial Result；被动方式实现更简单，适合统一 Error Handling。
:::

:::js
Reactive Approach 会在超限后捕获 `GraphRecursionError`。更推荐在图结构中首先设计显式终止条件，尽量避免触发限制。
:::
