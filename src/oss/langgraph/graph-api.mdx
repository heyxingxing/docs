## 图（Graphs）

LangGraph 的核心思想是把智能体工作流建模为**图（Graph）**。你通过三个关键组件定义智能体的行为：

1. [`State`](#state)：表示应用当前快照的共享数据结构。它可以是任意数据类型，但通常通过共享 State Schema 定义。
2. [`Nodes`](#nodes)：编码智能体逻辑的函数。Node 接收当前 State，执行计算或 Side Effect，并返回 State Update。
3. [`Edges`](#edges)：决定接下来执行哪个 Node 的连接与路由逻辑。它们既可以是固定转换，也可以是条件分支。

通过组合 Node 与 Edge，可以构建会随着 State 演进而循环、分支和汇聚的复杂工作流。真正的能力来自 LangGraph 如何管理和持久化这个 State。

需要强调的是：**Node 和 Edge 本质上都只是函数**。函数里可以调用 LLM，也可以只是普通业务代码。

一句话：**Node 负责做事，Edge 负责决定下一步做什么。**

LangGraph 底层使用[消息传递（message passing）](https://en.wikipedia.org/wiki/Message_passing)算法定义通用程序。某个 Node 执行完成后，会沿一条或多条 Edge 向其他 Node 发送消息（State Update）。接收消息的 Node 随后激活、执行，并继续把结果传递下去。这个执行模型受到 Google [Pregel](https://research.google/pubs/pregel-a-system-for-large-scale-graph-processing/) 系统启发，以离散的 **Superstep（超步）**推进。

可以把一个 Superstep 理解成对 Graph Node 的一次迭代：

- 同一时间并行运行的 Node 属于同一个 Superstep。
- 顺序运行的 Node 属于不同 Superstep。
- Graph 开始时所有 Node 都处于 `inactive` 状态。
- 当 Node 从任意入边（或 Channel）收到新消息时，它会变为 `active`。
- Active Node 执行函数并发出 Update。
- 每个 Superstep 结束时，没有新消息的 Node 会通过标记为 `inactive` 来“投票停止”。
- 当所有 Node 都为 `inactive` 且没有消息仍在传输时，Graph Execution 结束。

### StateGraph

@[`StateGraph`] 是最主要的 Graph Class。它由用户定义的 `State` 参数化。

### 编译 Graph

构建 Graph 的典型顺序是：先定义 [State](#state)，再添加 [Node](#nodes) 和 [Edge](#edges)，最后进行编译。

编译本身并不复杂，它主要做两件事：

- 对 Graph Structure 进行基本检查，例如发现孤立 Node。
- 接收运行时基础设施配置，例如 [Checkpointer](/oss/langgraph/persistence) 与 Breakpoint。

:::python
```python
graph = graph_builder.compile(...)
```
:::

:::js
```typescript
const graph = new StateGraph(StateAnnotation)
  .addNode("nodeA", nodeA)
  .addEdge(START, "nodeA")
  .addEdge("nodeA", END)
  .compile();
```
:::

<Warning>
在真正调用 Graph 之前，**必须**先编译它。
</Warning>

## State

:::python
定义 Graph 时，第一件事就是定义 `State`。State 同时包含 [Graph Schema](#schema) 与 [`Reducer`](#reducers)：Schema 决定所有 Node / Edge 可以看到的数据形状，Reducer 决定 Node 返回的 Update 应如何合并进当前 State。

Python 中 Schema 可以使用 `TypedDict` 或 Pydantic Model。所有 Node 都返回 State Update，然后由对应 Field 的 Reducer 应用这些 Update。
:::

:::js
定义 Graph 时，第一件事就是定义 `State`。State 同时包含 [Graph Schema](#schema) 与 [`Reducer`](#reducers)。JavaScript / TypeScript 通过 `StateSchema` 定义 State；每个 Field 可以使用任意 [Standard Schema](https://standardschema.dev/)（例如 [Zod](https://zod.dev/)），并可结合 `ReducedValue`、`MessagesValue`、`UntrackedValue` 等特殊 Value Type。
:::

### Schema

:::python
官方推荐主要使用 [`TypedDict`](https://docs.python.org/3/library/typing.html#typing.TypedDict) 指定 Graph Schema。如果希望 State Field 有默认值，可以使用 [`dataclass`](https://docs.python.org/3/library/dataclasses.html)。如果需要递归数据验证，也支持 Pydantic [`BaseModel`](/oss/langgraph/use-graph-api#use-pydantic-models-for-graph-state)，但性能通常不如 `TypedDict` 或 `dataclass`。

默认情况下 Graph 的 Input 与 Output Schema 相同；也可以显式定义不同的 Input / Output Schema，这对拥有大量内部字段、但只希望暴露少量输入输出字段的应用很有用。参见[定义输入和输出 Schema](/oss/langgraph/use-graph-api#define-input-and-output-schemas)。

<Info>
LangChain 的高层 [`create_agent`](/oss/langchain/agents) Factory 不支持 Pydantic State Schema。
</Info>
:::

:::js
JavaScript / TypeScript 推荐使用 `StateSchema`。每个 Field 可以是：

- **Standard Schema**：普通字段，默认使用 Last-value 语义，即新 Update 覆盖旧值。
- **`ReducedValue`**：需要自定义 Reducer 的字段，常用于并行 Node Update。
- **`MessagesValue`**：专门用于 Chat Message List，内置 Message-aware Reducer。
- **`UntrackedValue`**：只在当前执行中存在、不写入 Checkpoint 的临时 State。

```typescript
import {
  StateSchema,
  ReducedValue,
  MessagesValue,
  UntrackedValue
} from "@langchain/langgraph";
import { z } from "zod/v4";

const AgentState = new StateSchema({
  messages: MessagesValue,
  currentStep: z.string(),
  retryCount: z.number().default(0),
  allSteps: new ReducedValue(
    z.array(z.string()).default(() => []),
    {
      inputSchema: z.string(),
      reducer: (current, newStep) => [...current, newStep],
    }
  ),
  tempCache: new UntrackedValue(z.record(z.string(), z.unknown())),
});

type State = typeof AgentState.State;
type Update = typeof AgentState.Update;

const graph = new StateGraph(AgentState)
  .addNode("myNode", ...)
  .compile();
```

默认 Graph Input / Output Schema 相同，也可以单独定义。
:::

- 希望 Graph 使用不同的 Input / Output Schema，例如输出只暴露一个最终字段。

可以定义 `PrivateState` 作为内部 State Channel，也可以定义包含全部字段的 Overall State，再使用 Input / Output Schema 作为其子集约束 Graph 的外部接口。

### Reducer

Reducer 决定 Node 返回的 Update 如何应用到 State。State 中**每个 Key 都有自己独立的 Reducer**。如果没有显式指定，则默认认为新 Update 应该直接覆盖旧值。

#### Reducer 参数

每个 Reducer 都是接收两个位置参数的二元函数：

- **Left**：该 Key 当前已经累积在 State 中的值。
- **Right**：最新 Node Update 中对应 Key 的值。

:::python
```python
new_value = reducer(current_state[key], node_update[key])
```

const newValue = reducer(currentState[key], nodeUpdate[key]);

### UntrackedValue

:::js
`UntrackedValue` 用于执行期间需要存在、但**绝不应该写入 Checkpoint** 的 State Field。

典型用途：

- 无法序列化的数据库连接
- 恢复时应该重新构造的临时 Cache
- 不希望持久化的大对象
- 每次 Run 都应该重新注入的 Runtime-only 配置

```typescript
import { StateSchema, UntrackedValue, MessagesValue } from "@langchain/langgraph";
import { z } from "zod/v4";

const State = new StateSchema({
  messages: MessagesValue,
  dbConnection: new UntrackedValue<DatabaseConnection>(),
  tempCache: new UntrackedValue(
    z.record(z.string(), z.unknown()),
    { guard: false }
  ),
  runtimeConfig: new UntrackedValue(),
});
```

行为：

- 执行期间：像普通 State 一样可访问。
- 写 Checkpoint 时：被排除。
- 恢复执行时：重新从空值或默认值开始。
- `guard: true`（默认）：同一 Step 多个 Node 写入时抛错。
- `guard: false`：允许多个写入，最后一个值生效。

<Warning>
不要把需要跨 Interrupt 或 Time Travel 保存的数据放进 `UntrackedValue`。这些数据应使用普通 State Field 或 `ReducedValue`。
</Warning>
:::

### TypeScript 类型工具

:::js
LangGraph 提供一些辅助类型提升自定义 Node 与 Conditional Edge 的类型安全。

#### `GraphNode`

```typescript
import { GraphNode, StateSchema, Command } from "@langchain/langgraph";
import { z } from "zod/v4";

const State = new StateSchema({
  count: z.number().default(0),
  result: z.string(),
});

const incrementNode: GraphNode<typeof State> = (state) => {
  return { count: state.count + 1 };
};

const fetchNode: GraphNode<typeof State> = async (state, config) => {
  const response = await fetch(`/api/data/${state.count}`);
  return { result: await response.text() };
};

const routerNode: GraphNode<{ InputSchema: typeof State; Nodes: "process" | "done" }> = (state) => {
  if (state.count >= 10) return new Command({ goto: "done" });
  return new Command({ update: { count: state.count + 1 }, goto: "process" });
};
```

#### `State.Node`

每个 `StateSchema` 都有一个 `Node` Shorthand：

```typescript
const myNode1: GraphNode<typeof State> = (state) => ({ result: "done" });
const myNode2: typeof State.Node = (state) => ({ result: "done" });
```

#### `ConditionalEdgeRouter`

用于只负责路由、不更新 State 的 Conditional Edge：

```typescript
import { ConditionalEdgeRouter, END } from "@langchain/langgraph";

const router: ConditionalEdgeRouter<{ InputSchema: typeof State; Nodes: "process" | "summarize" }> = (state) => {
  if (!state.shouldContinue) return END;
  return state.step === "initial" ? "process" : "summarize";
};
```

#### `StateSchema.State` 与 `StateSchema.Update`

```typescript
type MyState = typeof MyStateSchema.State;
type MyUpdate = typeof MyStateSchema.Update;
```

### 在 Graph State 中使用 Message

#### 为什么使用 Message？

现代 LLM Provider 的 Chat Model 通常接受 Message List 作为输入。LangChain 的 [Chat Model Interface](/oss/langchain/models) 也使用 Message Object，例如 @[`HumanMessage`] 和 @[`AIMessage`]。

Message Object 的完整介绍参见 [Messages 概念指南](/oss/langchain/messages)。

#### 在 Graph 中保存 Message

:::python
很多应用会把对话历史保存为 State 中的 Message List。此时 Reducer 非常重要：如果没有 Reducer，每次 Node Update 都会覆盖整份 Message History。

简单追加可以使用 `operator.add`，但实际应用往往还需要支持 HITL 手动编辑既有 Message。此时最好使用 @[`add_messages`]：

- 新 Message 会追加。
- 如果 Message ID 已存在，则会正确覆盖对应 Message。
:::

:::js
JavaScript / TypeScript 可以直接使用 `MessagesValue`，它内置 Message-aware Reducer，能够自动处理 Message ID、Update 与删除。

<Tip>
`MessagesValue` 本质上是一个预配置了内部 `messagesStateReducer` 的特殊 `ReducedValue`。
</Tip>
:::

#### 序列化

:::python
@[`add_messages`] 还会在收到 State Update 时尝试把 Message 反序列化为 LangChain Message Object，因此既支持：

```python
{"messages": [HumanMessage(content="message")]}
```

也支持：

```python
{"messages": [{"type": "human", "content": "message"}]}
```

使用 `add_messages` 后，State 中的 Message 会被反序列化为真正的 LangChain Message，应使用 `state["messages"][-1].content` 等属性访问。

```python
from langchain.messages import AnyMessage
from langgraph.graph.message import add_messages
from typing import Annotated
from typing_extensions import TypedDict

class GraphState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
```
:::

:::js
`MessagesValue` 同样支持 Message Object 与简写对象：

```typescript
{ messages: [new HumanMessage("message")] }
{ messages: [{ role: "human", content: "message" }] }
```

收到 Update 后会自动反序列化为 LangChain Message Object。

```typescript
import { StateGraph, StateSchema, MessagesValue } from "@langchain/langgraph";

const State = new StateSchema({
  messages: MessagesValue,
});
```
:::

:::python
#### MessagesState

Message History 太常见，因此 LangGraph 内置了 `MessagesState`。它只包含一个 `messages` Key，类型为 `list[AnyMessage]`，并使用 @[`add_messages`] Reducer。

通常应用还需要更多 State，可以直接继承：

```python
from langgraph.graph import MessagesState

class State(MessagesState):
    documents: list[str]
```
:::

## Nodes

:::python
LangGraph Node 是同步或异步 Python Function，可以接收：

1. `state`：当前 [Graph State](#state)
2. `config`：@[`RunnableConfig`]，包含 `thread_id`、Tracing Tag 等配置
3. `runtime`：`Runtime` Object，包含 [Runtime Context](#runtime-context)、`store`、`stream_writer`、`execution_info`、`server_info`、`heartbeat` 与用于[优雅关闭](/oss/langgraph/fault-tolerance#graceful-shutdown)的 `control`

```python
from dataclasses import dataclass
from typing_extensions import TypedDict
from langgraph.graph import StateGraph
from langgraph.runtime import Runtime

class State(TypedDict):
    input: str
    results: str

@dataclass
class Context:
    user_id: str

builder = StateGraph(State)

def plain_node(state: State):
    return state

def node_with_runtime(state: State, runtime: Runtime[Context]):
    print("In node: ", runtime.context.user_id)
    return {"results": f"Hello, {state['input']}!"}

def node_with_execution_info(state: State, runtime: Runtime):
    print("In node with thread_id: ", runtime.execution_info.thread_id)
    return {"results": f"Hello, {state['input']}!"}

builder.add_node("plain_node", plain_node)
builder.add_node("node_with_runtime", node_with_runtime)
builder.add_node("node_with_execution_info", node_with_execution_info)
```
:::

:::js
Node 通常是同步或异步函数，主要接收 `state` 与 `config`。建议使用 `GraphNode` 或 `State.Node` 提升类型安全：

```typescript
import { StateGraph, StateSchema, GraphNode } from "@langchain/langgraph";
import * as z from "zod";

const State = new StateSchema({
  input: z.string(),
  results: z.string(),
});

const myNode: GraphNode<typeof State> = (state, config) => {
  console.log("In node: ", config?.configurable?.user_id);
  return { results: `Hello, ${state.input}!` };
};

const otherNode: typeof State.Node = (state) => state;
```
:::

函数在底层会被转换为 @[`RunnableLambda`]，因此自动获得 Batch / Async 能力，以及 LangSmith 的原生 Trace / Debug 支持。

如果添加 Node 时不指定名字，默认会使用函数名。

### 重新执行与幂等性

使用 [Checkpointer](/oss/langgraph/persistence) 编译后，LangGraph 在 **Superstep Boundary** 创建 Checkpoint，而不会在 Node Function 中间随意保存。

因此当执行因 [Interrupt](/oss/langgraph/interrupts)、Retry 或其他原因暂停并恢复时，受影响的 **Node 会从函数开头重新执行**。在暂停位置之前的代码和 Side Effect 也会再次发生。

**幂等性（Idempotency）**：Node Logic 应保证重复执行不会破坏数据。例如 Node 插入数据库 Row 时，应通过 Idempotency Key、Upsert 或 Read-before-write 避免恢复执行后重复插入。`interrupt()` 附近的 Side Effect 规则参见[Interrupt 前的 Side Effect 必须幂等](/oss/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent)。

**Graph Structure 变化**：Functional API 的某些 Determinism 约束并不要求 Graph Topology 永久固定。现有 Thread 恢复时会使用当前编译后的 Graph；添加或删除普通 Node / Edge 通常不会破坏已保存 State。

**Node 内的 Task / Interrupt**：如果 Node 调用了 [Task](/oss/langgraph/functional-api#task) 或 @[`interrupt`]，恢复时会应用更严格的 Determinism 规则。LangGraph 会从 Checkpointer 恢复已完成 Task Result，但如果修改恢复点之前 Task / Interrupt 的顺序，就可能与缓存值错位。详见 [Determinism](/oss/langgraph/functional-api#determinism) 与 [Idempotency](/oss/langgraph/functional-api#idempotency)。

### Node Cache

LangGraph 可以基于 Node Input 缓存 Task / Node 结果。启用 Cache 需要：

- 编译 Graph 时提供 Cache。
- 为对应 Node 配置 Cache Policy。

Cache Policy 支持：

- `key_func` / `keyFunc`：根据 Node Input 生成 Cache Key。
- `ttl`：Cache 生存时间；不设置则永不过期。

:::python
```python
import time
from typing_extensions import TypedDict
from langgraph.graph import StateGraph
from langgraph.cache.memory import InMemoryCache
from langgraph.types import CachePolicy

class State(TypedDict):
    x: int
    result: int

def expensive_node(state: State) -> dict[str, int]:
    time.sleep(2)
    return {"result": state["x"] * 2}

builder = StateGraph(State)
builder.add_node("expensive_node", expensive_node, cache_policy=CachePolicy(ttl=3))
builder.set_entry_point("expensive_node")
builder.set_finish_point("expensive_node")
graph = builder.compile(cache=InMemoryCache())
```

<Note>
`set_entry_point(node)` 等价于 `add_edge(START, node)`；`set_finish_point(node)` 等价于 `add_edge(node, END)`。两者都合法，但现代文档更推荐显式 `add_edge` 语法。
</Note>
:::

:::js
```typescript
const graph = new StateGraph(State)
  .addNode("expensive_node", expensiveNode, { cachePolicy: { ttl: 3 } })
  .addEdge(START, "expensive_node")
  .compile({ cache: new InMemoryCache() });
```
:::

## Edges

Edge 定义 Logic 如何路由，以及 Graph 何时停止。主要类型包括：

- **Normal Edge**：从一个 Node 固定进入另一个 Node。
- **Conditional Edge**：执行 Routing Function，根据 State 决定下一步。
- **Entry Point**：用户输入到来时最先执行的 Node。
- **Conditional Entry Point**：根据输入 / State 动态决定起始 Node。

一个 Node 可以拥有多个 Outgoing Edge；如果存在多个固定 Outgoing Edge，那么所有目标 Node 会在下一个 Superstep **并行执行**。

<Warning>
对同一个 Node，最好选择一种路由机制：固定路由使用 Normal Edge；动态路由使用 Conditional Edge 或 @[`Command`]。不要同时混用固定 Edge 与动态路由，否则两条路径都可能执行，使行为难以推理。
</Warning>

### 普通 Edge

如果 Node A **始终**进入 Node B：

:::python
```python
graph.add_edge("node_a", "node_b")
```
:::

:::js
```typescript
graph.addEdge("nodeA", "nodeB");
```
:::

### Conditional Edge

如果需要根据 State 可选地进入一个或多个 Node（或终止），可以使用 Conditional Edge。

:::python
```python
graph.add_conditional_edges("node_a", routing_function)
```

Routing Function 接收当前 State，其返回值默认直接被当作目标 Node Name，也可以一次返回多个 Node，让它们在下一个 Superstep 并行执行。

还可以显式提供 Output → Node Mapping：

```python
graph.add_conditional_edges("node_a", routing_function, {True: "node_b", False: "node_c"})
```
:::

:::js
```typescript
graph.addConditionalEdges("nodeA", routingFunction);

graph.addConditionalEdges("nodeA", routingFunction, {
  true: "nodeB",
  false: "nodeC",
});
```
:::

<Tip>
如果希望在同一个 Function 中同时完成 State Update 与 Routing，使用 [`Command`](#command) 比 Conditional Edge 更合适。
</Tip>

### Entry Point

Entry Point 是 Graph 启动后最先运行的 Node。通过虚拟 @[`START`] Node 添加 Edge 指定：

:::python
```python
from langgraph.graph import START
graph.add_edge(START, "node_a")
```
:::

:::js
```typescript
import { START } from "@langchain/langgraph";
graph.addEdge(START, "nodeA");
```
:::

### Conditional Entry Point

如果希望 Graph 根据输入从不同 Node 开始，可以从 `START` 添加 Conditional Edge：

:::python
```python
from langgraph.graph import START
graph.add_conditional_edges(START, routing_function)
graph.add_conditional_edges(START, routing_function, {True: "node_b", False: "node_c"})
```
:::

:::js
```typescript
import { START } from "@langchain/langgraph";
graph.addConditionalEdges(START, routingFunction);
```
:::

## `Send`

默认情况下，Graph 的 Node / Edge 在编译前已经确定，而且所有 Node 操作同一份共享 State。但在 Map-Reduce 等模式中：

- 分支数量可能直到运行时才知道。
- 每个下游 Node 需要接收不同的 Input State。

LangGraph 允许 Conditional Edge 返回 @[`Send`] Object 来支持这种动态 Fan-out。`Send` 接收两个参数：目标 Node Name 与传给该 Node 的 State。

:::python
```python
from langgraph.types import Send

def continue_to_jokes(state: OverallState):
    return [Send("generate_joke", {"subject": s}) for s in state['subjects']]

graph.add_conditional_edges("node_a", continue_to_jokes)
```
:::

:::js
```typescript
import { Send } from "@langchain/langgraph";

graph.addConditionalEdges("nodeA", (state) => {
  return state.subjects.map(
    (subject) => new Send("generateJoke", { subject })
  );
});
```
:::

## `Command`

@[`Command`] 是用于控制 Graph Execution 的通用 Primitive，支持四个主要参数：

- `update`：应用 State Update，等价于普通 Node 返回 Update。
- `goto`：跳转到指定 Node，类似 Conditional Edge。
- `graph`：从 Subgraph 中导航时指定目标 Parent Graph。
- `resume`：在 [Interrupt](/oss/langgraph/interrupts) 后提供恢复值。

`Command` 主要有三种使用位置：

- **[Node Return Value](#return-from-nodes)**：使用 `update`、`goto`、`graph` 同时做 State Update 与 Control Flow。
- **[`invoke` / `stream` Input](#input-to-invoke-or-stream)**：使用 `resume` 从 Interrupt 恢复。
- **[Tool Return Value](#return-from-tools)**：从 Tool 内更新 State 或动态路由。

### 从 Node 返回

#### `update` 与 `goto`

:::python
```python
def my_node(state: State) -> Command[Literal["my_other_node"]]:
    return Command(
        update={"foo": "bar"},
        goto="my_other_node"
    )
```

如果只需要 Routing、不需要更新 State，使用 Conditional Edge；如果两者都需要，使用 `Command`。

<Note>
Python Node 返回 `Command` 时，应通过 `Command[Literal[...]]` Return Type Annotation 声明可能的目标 Node，这对 Graph Rendering 很重要。
</Note>
:::

:::js
```typescript
import { Command } from "@langchain/langgraph";

graph.addNode("myNode", (state) => {
  return new Command({
    update: { foo: "bar" },
    goto: "myOtherNode",
  });
});
```

JavaScript / TypeScript 需要在 `.addNode` 中通过 `ends` 指定可能路由目标：

```typescript
builder.addNode("myNode", myNode, {
  ends: ["myOtherNode", END],
});
```
:::

<Warning>
`Command` 添加的是**动态 Edge**。如果同一个 Node 还定义了 `add_edge` / `addEdge` 固定 Edge，那么两条路径都会执行。对一个 Node 应选择一种 Routing Mechanism，而不是混用。
</Warning>

#### `graph`

在 Subgraph 内可以通过 `Command.PARENT` 跳转到最近的 Parent Graph：

:::python
```python
def my_node(state: State) -> Command[Literal["other_subgraph"]]:
    return Command(
        update={"foo": "bar"},
        goto="other_subgraph",
        graph=Command.PARENT
    )
```
:::

:::js
```typescript
return new Command({
  update: { foo: "bar" },
  goto: "otherSubgraph",
  graph: Command.PARENT,
});
```
:::

<Note>
如果 Subgraph Node 向 Parent Graph 更新一个双方共享的 State Key，那么 Parent State 中这个 Key **必须**定义 Reducer。参见[导航到 Parent Graph Node](/oss/langgraph/use-graph-api#navigate-to-a-node-in-a-parent-graph)。
</Note>

这对[多智能体 Handoff](/oss/langchain/multi-agent/handoffs)尤其有用。

### 作为 `invoke` / `stream` 输入

<Warning>
`Command(resume=...)` 是设计用来作为 `invoke()` / `stream()` Input 的主要 `Command` 模式，也可以与 `update=...` 一起用于“恢复并顺便更新 State”。

不要用单独的 `Command(update=...)` 来开启多轮对话下一轮。任何 `Command` Input 都会从最近 Checkpoint 位置恢复，而不是从 `__start__` 开始；如果上一轮已经完成，看起来就会像 Graph“卡住”。

继续同一 Thread 的普通新一轮对话，应传普通 State Dict / Object。
</Warning>

#### `resume`

使用 `Command(resume=...)` 从 `interrupt()` 暂停位置恢复；`resume` 里的值会成为暂停 Node 中 `interrupt()` Call 的 Return Value。

:::python
<LanggraphGraphApiResumeV2Py />
:::

:::js
```typescript
import { Command, interrupt } from "@langchain/langgraph";

const humanReview = async (state: typeof StateAnnotation.State) => {
  const answer = interrupt("Do you approve?");
  return { messages: [{ role: "user", content: answer }] };
};

const result = await graph.invoke({ messages: [...] }, config);
const resumed = await graph.invoke(new Command({ resume: "yes" }), config);
```
:::

完整 Interrupt Pattern 参见[中断概念指南](/oss/langgraph/interrupts)。

### 从 Tool 返回

Tool 也可以返回 @[`Command`] 来更新 Graph State 与控制 Flow。例如 Tool 查询到 Customer Info 后，可以直接保存进 State，再决定下一步 Routing。

<Warning>
Tool 中使用 `goto` 也是动态 Edge；调用这个 Tool 的 Node 如果还存在 Static Edge，Static Edge 同样会执行。不要混用两套 Routing Mechanism。
</Warning>

参见[在 Tool 内使用 Command](/oss/langgraph/use-graph-api#use-inside-tools)。

## Graph Migration

即使 Graph 使用 Checkpointer 保存 State，LangGraph 也支持大部分 Graph Definition Migration：

- **已经执行结束的 Thread**：可以修改完整 Topology，包括添加 / 删除 / 重命名 Node 和 Edge。
- **当前处于 Interrupt 的 Thread**：支持大多数 Topology Change，但不建议删除或重命名它接下来可能进入的 Node。
- **State Field 增删**：对添加和删除 Key 有完整前后兼容能力。
- **State Key 重命名**：已有 Thread 中旧 Key 保存的数据不会自动迁移到新 Key。
- **State Type 不兼容变化**：旧 Thread 中已保存的数据可能不再满足新 Type，需要额外 Migration。

<Tip>
如果技术结构仍兼容，但业务逻辑发生变化，例如 Tool Set、Conversation Flow 改写，可以参考[业务兼容性](/oss/langgraph/backward-compatibility#business-compatibility)，通过在 State 中固定 Behavior Version，让旧 Thread 继续走旧逻辑，新 Thread 使用新版本。
</Tip>

## Runtime Context

有些配置只在运行时使用，并不属于 Graph State，例如 Model Provider、数据库连接、Tenant / User Dependency 等。此时可以定义 `context_schema` / `contextSchema`。

:::python
```python
from dataclasses import dataclass

@dataclass
class ContextSchema:
    llm_provider: str = "openai"

graph = StateGraph(State, context_schema=ContextSchema)
graph.invoke(inputs, context={"llm_provider": "anthropic"})
```

Node / Conditional Edge 可以通过 `Runtime` 读取：

```python
from langgraph.runtime import Runtime

def node_a(state: State, runtime: Runtime[ContextSchema]):
    llm = get_llm(runtime.context.llm_provider)
```
:::

:::js
```typescript
const ContextSchema = z.object({
  llm: z.union([z.literal("openai"), z.literal("anthropic")]),
});

const graph = new StateGraph(State, ContextSchema);
await graph.invoke(inputs, { context: { llm: "anthropic" } });
```
:::

完整配置方式参见[添加 Runtime Configuration](/oss/langgraph/use-graph-api#add-runtime-configuration)。

### Recursion Limit

Recursion Limit 限制单次 Graph Execution 允许执行的最大 [Superstep](#graphs) 数量，超过后抛出 `GraphRecursionError`。

:::python
从 `langgraph 1.0.6` 起，Python 默认 Recursion Limit 为 1000。可以在 Runtime Config 中覆盖；注意 `recursion_limit` 是顶层 Config Key，不应放进 `configurable`：

```python
graph.invoke(inputs, config={"recursion_limit": 5}, context={"llm": "anthropic"})
```
:::

:::js
JavaScript 默认值为 25，可通过 `recursionLimit` 配置：

```typescript
await graph.invoke(inputs, {
  recursionLimit: 5,
  context: { llm: "anthropic" },
});
```
:::

### 访问和处理递归计数

当前 Step Counter 可以在 Node 内从 `config["metadata"]["langgraph_step"]`（JS 为 `config.metadata.langgraph_step`）读取，从而在真正触发限制之前主动降级。

:::python
```python
from langchain_core.runnables import RunnableConfig

def my_node(state: dict, config: RunnableConfig) -> dict:
    current_step = config["metadata"]["langgraph_step"]
    print(f"Currently on step: {current_step}")
    return state
```
:::

:::js
```typescript
const myNode: GraphNode<typeof State> = async (state, config) => {
  const currentStep = config.metadata?.langgraph_step;
  console.log(`Currently on step: ${currentStep}`);
  return state;
};
```
:::

#### 使用 `RemainingSteps` 主动处理

:::python
LangGraph 提供 `RemainingSteps` Managed Value，表示离 Recursion Limit 还剩多少 Step。这样可以在 Graph 内做 Graceful Degradation，而不是等到外层捕获 Exception。

```python
from typing import Annotated, Literal, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.managed import RemainingSteps

class State(TypedDict):
    messages: Annotated[list, lambda x, y: x + y]
    remaining_steps: RemainingSteps

def reasoning_node(state: State) -> dict:
    remaining = state["remaining_steps"]
    if remaining <= 2:
        return {"messages": ["Approaching limit, wrapping up..."]}
    return {"messages": ["thinking..."]}

def route_decision(state: State) -> Literal["reasoning_node", "fallback_node"]:
    if state["remaining_steps"] <= 2:
        return "fallback_node"
    return "reasoning_node"
```
:::

#### 主动 vs 被动处理

主要有两种策略：

| 策略 | 何时发现 | 在哪里处理 | Control Flow |
|---|---|---|---|
| 主动（`RemainingSteps`） | 到达 Limit 之前 | Graph 内 Conditional Routing | Graph 正常进入 Completion Node |
| 被动（捕获 `GraphRecursionError`） | Limit 已经超过 | Graph 外 try/catch | Graph Execution 已终止 |

**主动方式的优点：**

- 可以在 Graph 内优雅降级
- 可以把 Intermediate State 保存进 Checkpoint
- 能给用户返回 Partial Result
- Graph 正常结束而不是以 Exception 终止

**被动方式的优点：**

- 实现简单
- 不需要修改 Graph Logic
- Error Handling 集中在外部

:::python
```python
from langgraph.errors import GraphRecursionError

try:
    result = graph.invoke({"messages": []}, {"recursion_limit": 10})
except GraphRecursionError:
    result = {"messages": ["Fallback: recursion limit exceeded"]}
```
:::
